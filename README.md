# Сфера — компилятор (черновик)

Компилятор языка программирования «Сфера» (файлы `.код`).
Конвейер: лексер → парсер → LLVM IR (через inkwell) → машинный код.

## Установка зависимостей

Для сборки нужен установленный в системе **LLVM версии 18** (это отдельный
системный компилятор, не Rust-библиотека — `cargo` его не поставит сам).

### macOS

```bash
brew install llvm@18
```

После установки Homebrew сообщит путь установки (обычно
`/opt/homebrew/opt/llvm@18` на Apple Silicon или `/usr/local/opt/llvm@18`
на Intel). Нужно прописать переменную окружения, чтобы `llvm-sys` (от
которого зависит `inkwell`) нашёл LLVM:

```bash
export LLVM_SYS_180_PREFIX="$(brew --prefix llvm@18)"
```

Добавь эту строку в `~/.zshrc` (или `~/.bash_profile`), чтобы не вводить
её каждый раз заново, затем перезапусти терминал или выполни `source ~/.zshrc`.

### Ubuntu / Debian

```bash
wget https://apt.llvm.org/llvm.sh
chmod +x llvm.sh
sudo ./llvm.sh 18
export LLVM_SYS_180_PREFIX=/usr/lib/llvm-18
```

### Проверка

```bash
llvm-config-18 --version    # должно вывести 18.x.x
```

Если команда не найдена — LLVM не установился корректно или не попал в PATH.

## Сборка и запуск

```bash
cd sfera
cargo build
```

Компилятор принимает путь к `.код`-файлу как аргумент командной строки —
**и теперь сразу же запускает результат** (как `node файл.js` или `go run`),
не нужно отдельно вызывать `./привет`:

```bash
cargo run -- привет.код
```

(в проекте уже есть готовый пример `привет.код` в корне — можно сразу пробовать на нём)

Вывод — это результат работы твоей программы на "Сфере" напрямую (без
диагностических сообщений компилятора — они убраны, чтобы результат
ощущался как единая команда, а не пошаговый лог). Точный список строк
здесь не приводим — `привет.код` продолжает пополняться новыми
демонстрациями по ходу разработки языка, актуальнее один раз посмотреть
сам файл, чем держать список вывода синхронизированным в двух местах.

**Если нужно только собрать, не запуская** (например, чтобы потом
распространить готовый бинарник отдельно):
```bash
cargo run -- привет.код --только-собрать
```

**Собранный бинарник** (`cargo build --release` для отдельного запуска
компилятора без `cargo run`) работает так же:
```bash
./target/release/sfera привет.код
```

Без аргумента или с `-h`/`--help` компилятор печатает подсказку по использованию.

## Многофайловая сборка (`подключить`) — теперь реально работает

Раньше `подключить` парсился, но полностью игнорировался — теперь компилятор
рекурсивно находит и разбирает подключённые файлы, сливая их объявления
в одну программу. В проекте есть готовый пример из двух файлов:

```bash
cargo run -- тест_подключения.код
```

`тест_подключения.код` подключает `утилиты.код` (`подключить утилиты;`,
без расширения — компилятор сам ищет `утилиты.код` рядом с подключающим
файлом) и использует объявленные там функцию и структуру.

**Как это устроено:** это НЕ настоящая раздельная компиляция с изоляцией
пространств имён между файлами — все объявления из всех подключённых
файлов делят ОДНО общее пространство имён, как если бы весь код был
написан в одном файле (простое "текстовое склеивание" перед семантическим
анализом, а не отдельные единицы компиляции). Семантика и кодогенерация
вообще не знают, что программа могла состоять из нескольких файлов.

**Известные ограничения этой версии:**
- `подключить графика.окно;` (составное имя с точкой, по грамматике должно
  означать "зайди в папку `графика`, возьми файл `окно.код`") — пока НЕ
  поддержано; точка сейчас просто станет частью искомого имени файла
  буквально, что почти наверняка не найдётся. Работает только простое
  `подключить имя;` (файл рядом) и `подключить "путь/файл.код";` (явный путь).
- **НОВОЕ: дублирующиеся имена функций/структур/методов/полей теперь дают
  понятную ошибку компиляции** ("функция '...' объявлена повторно"), а не
  молчаливую подмену последним объявлением — работает и внутри одного файла,
  и между подключёнными файлами (поскольку к моменту семантического анализа
  все файлы уже слиты в один список, проверка одна и та же для обоих
  случаев). **Это НЕ настоящие пространства имён** — просто защита от самого
  опасного побочного эффекта их отсутствия (силентная подмена). Два файла
  всё ещё не могут использовать одинаковое имя для РАЗНЫХ вещей одновременно
  (например, оба объявить свою функцию `обработать`) — с настоящими
  пространствами имён это было бы возможно через квалификацию по модулю
  (`утилиты.обработать(...)`), но такой синтаксис пока не реализован.
- Циклические подключения (А подключает Б, Б подключает А) корректно
  обрабатываются — файл, уже разобранный, просто молча пропускается при
  повторной встрече.
- Путь для `подключить имя;` разрешается ОТНОСИТЕЛЬНО файла, который его
  подключает (не относительно текущей директории терминала) — так удобнее
  и предсказуемее, но стоит иметь это в виду при организации проекта.
- **НОВОЕ: запасной поиск в папке `пакеты/`** — если `подключить имя;` не
  находит `{имя}.код` рядом с подключающим файлом, компилятор пробует
  `{корень_проекта}/пакеты/{имя}.код` (корень проекта — папка входного
  файла, переданного в командной строке, вычисляется один раз, не для
  каждого подключённого файла отдельно). Это НЕ полноценная система
  пакетов (нет публикации, версий, реестра, автоматической загрузки) —
  просто предсказуемое локальное место, куда можно вручную положить
  чужой `.код`-файл. Пример — `пакеты/математика.код` в проекте,
  подключаемый из `тест_подключения.код`.

## ⚠️⚠️ Исправлен серьёзный, ранее незамеченный пробел: арифметика над `дробное`

**Это был не просто пробел в функциональности, а гарантированный крах
самого компилятора.** Тип `дробное` существовал в системе типов с самого
начала — парсился, проходил семантическую проверку — но `сгенерировать_бинарное`
и `сгенерировать_унарное` безусловно вызывали `.into_int_value()` для ЛЮБОЙ
нетекстовой операции. Для дробных чисел (`FloatValue`, не `IntValue`) это
была бы не аккуратная ошибка компиляции, а **паника Rust внутри `inkwell`**
при первой же попытке скомпилировать что-то вроде `3.5 + 2.5`.

Найдено и исправлено при плановой проверке: после долгой серии добавлений
в стандартную библиотеку решили перепроверить более старые, основательные
части компилятора — и обнаружили, что базовый тип языка практически не
был протестирован вообще (ни один из предыдущих тестов в `привет.код` не
использовал арифметику над `дробное`, только объявление переменных этого
типа).

**Исправлено:**
- `сгенерировать_бинарное` теперь определяет дробные операнды по РЕАЛЬНОМУ
  LLVM-типу (`is_float_type()`, тот же принцип, что уже применён для
  текста) и передаёт их в отдельный метод `сгенерировать_дробную_операцию`
  — через `build_float_add`/`build_float_sub`/и т.д. вместо `build_int_*`,
  и `FloatPredicate` (варианты `O...` — "ordered", стандартное поведение:
  сравнение `false`, если один из операндов `NaN`) вместо `IntPredicate`
  для сравнений.
- `сгенерировать_унарное` — та же находка и то же исправление для
  унарного минуса (`-3.5`).

**Тест в `привет.код`** — специально проверяет ВСЕ арифметические операции
над `дробное` (`+`, `-`, `*`, `/`, сравнения, унарный минус), а не только
компиляцию без падения — используя недавно добавленное сравнение через
`==` для проверки конкретных числовых результатов.

### Продолжение проверки: `вывести(дробное)` и интерполяция тоже были сломаны

После исправления арифметики решили не останавливаться на одной находке —
специально прошлись по всем местам, где значение приводится к конкретному
LLVM-типу без проверки (`.into_int_value()`/`.into_pointer_value()`/
`.into_float_value()` по всему `codegen.rs`), проверяя каждое на тот же
класс риска. Почти все места оказались защищены семантическими проверками
типа заранее (например, `абс`/`мин`/`макс` требуют целочисленный аргумент)
— но нашлись ещё два места с тем же классом проблемы, что и арифметика,
просто с более мягким исходом (аккуратная ошибка компиляции, а не паника):

- **`вывести(дробное_значение)`** — раньше падало с ошибкой "поддерживает
  только текст или целое число". Значит даже ПОСЛЕ исправления арифметики
  результат вычислений всё ещё нельзя было напечатать.
- **Интерполяция строк с дробной переменной** (`"$а"`, где `а` — `дробное`)
  — та же ошибка, в другом месте кода (`сгенерировать_вывести_с_интерполяцией`).

**Техническая деталь исправления**: variadic C-функции (как `printf`)
ВСЕГДА получают `float` (32-битный) как `double` (64-битный) — стандартное
правило C ABI "default argument promotion". Значения `дробное32` перед
передачей в `printf` теперь явно расширяются до 64 бит через
`build_float_ext` — без этого `printf` читал бы несовпадающий по размеру
мусор из variadic-аргументов.

**✅ ЗАКРЫТО в следующей же итерации**: `дробное_в_текст(дробное) -> текст`
теперь реализована — тот же принцип, что и `целое_в_текст` (через
`snprintf`), но с форматом `"%f"` и буфером побольше (64 байта вместо 32 —
вывод `%f` обычно длиннее) плюс то же расширение `f32 → f64` перед
передачей в variadic `snprintf`, что уже применено в `вывести(...)` и
интерполяции. Добавлена и функция `является_дробным` в семантике (по
аналогии с уже существующей `является_целочисленным`) для проверки типа
аргумента.

## Начало стандартной библиотеки

У языка почти ничего не было за пределами того, что мы сами построили как
часть ядра (структуры, `Список`/`Словарь`, `результат<тип>`). Три новые
функции закрывают самые критичные, реально блокирующие всё остальное дыры:

- **`длина(текст) -> целое`** — длина текста в байтах. Просто переиспользует
  уже объявленную `strlen` (та же функция, что используется для конкатенации
  текста) — самая безопасная, наименее рискованная из трёх новых функций.
- **`целое_в_текст(целое) -> текст`** — форматирует число в текст через
  `snprintf`, в буфер фиксированного размера (32 байта — i64 гарантированно
  умещается, максимум ~20 значащих символов). До этой версии превратить
  число в текст можно было ТОЛЬКО внутри интерполяции строк (`"$число"`) —
  то есть только для немедленного вывода через `вывести(...)`, не для
  сохранения в переменную или передачи в функцию.
- **`текст_в_целое(текст) -> результат<целое>`** — разбирает текст в число
  через `strtol`, возвращая `результат<тип>` (та же модель ошибок, что и
  везде в языке — `успех(число)` или `ошибка("не удалось разобрать...")`),
  а не падая тихо или крашась на нечисловом вводе. Реализация переиспользует
  уже написанные `построить_результат_успех`/`построить_результат_ошибка`
  (изначально созданные для `Словарь.получить(...)`).

**Как определяется удача/неудача разбора** — через классический для `strtol`
приём с "out-параметром": функция принимает указатель-на-указатель ("куда
дошёл разбор") и после вызова, если этот указатель НЕ сдвинулся от начала
строки, значит не было распознано ни одной цифры (текст не был числом).

**⚠️ Известное следствие, то же самое, что и у конкатенации текста**:
`целое_в_текст(...)` создаёт новый `malloc`-буфер, который никогда не
освобождается (текст пока вообще не участвует в ARC). Небольшая утечка при
каждом вызове — не хуже, чем уже было (текст и так никогда не управлялся
по памяти), просто честно задокументированное следствие того, что теперь
физически возможно создавать НОВЫЙ текст этим способом тоже, не только
через конкатенацию.

**Защита имён**: `длина`, `целое_в_текст`, `текст_в_целое`, `абс`, `мин`,
`макс`, `верно_в_текст` (как и `вывести`) теперь зарезервированы —
объявить свою функцию с таким именем нельзя, компилятор даст понятную
ошибку вместо молчаливого конфликта.

### Простая математика и преобразование верно (продолжение стандартной библиотеки)

Четыре новые функции — заметно ниже риском, чем первые три (не требуют
НИКАКИХ новых внешних `libc`-функций, только уже знакомые LLVM-операции
`build_int_compare`/`build_select`, которые уже применялись в других
местах компилятора):

- **`абс(целое) -> целое`** — модуль числа.
- **`мин(целое, целое) -> целое`**, **`макс(целое, целое) -> целое`** —
  минимум/максимум из двух чисел. Оба реализованы ОДНИМ общим методом
  (`сгенерировать_мин_макс`), различающимся только предикатом сравнения —
  без дублирования кода.
- **`верно_в_текст(верно) -> текст`** — `"да"`/`"нет"`, а не сырое
  числовое `0`/`1`. Полезно для осмысленного вывода булевых значений.

**Известное ограничение этой версии**: все четыре работают только с
базовым `целое` — не с другими размерами целых чисел (`целое8`/`целое16`
и т.д.) и не с `дробное`. Осознанное сужение объёма для первой версии, не
забытый случай.

### Поиск подстроки (продолжение стандартной библиотеки)

- **`содержит(текст, подстрока) -> верно`** — есть ли вхождение. Через
  `strstr` + `build_is_null` (тот же приём, что уже применён в буферах
  `Список<тип>`/`Словарь<Ключ, Значение>`) + инверсия через `build_not`.
- **`найти(текст, подстрока) -> результат<целое>`** — ИНДЕКС первого
  вхождения (в байтах), а не просто факт наличия. `успех(индекс)`, если
  нашлось, `ошибка("подстрока не найдена")`, если нет — та же модель
  ошибок, что и везде в языке, вместо "магического" `-1`, как это принято
  в классическом C. Индекс вычисляется как разница адресов: приводим оба
  указателя (начало строки и найденную позицию) к числу через
  `build_ptr_to_int` и вычитаем.

**⚠️ Новая техника**: `build_ptr_to_int` используется здесь впервые в этом
компиляторе — везде до этого мы работали с указателями напрямую, без
явного превращения в целое число.

**⚠️ Известное ограничение**: индекс — это смещение в БАЙТАХ, а не в
символах. Для текста, содержащего только латиницу/цифры, байты и символы
совпадают 1:1, но кириллица в UTF-8 занимает 2 байта на символ — значит
для строк с кириллицей индекс, возвращаемый `найти(...)`, не будет
совпадать с "номером буквы", если считать по-человечески. Осознанное
сужение объёма, не забытый случай — символьно-корректный поиск потребовал
бы разбора UTF-8, отдельная, более сложная задача.

### Чтение ввода — `прочитать_строку()` (продолжение стандартной библиотеки)

**Первый способ вообще что-либо ПРОЧИТАТЬ извне программы** — до этой
версии язык мог только выводить, весь ввод был жёстко зашит в код заранее.

`прочитать_строку() -> результат<текст>` читает одну строку со стандартного
ввода. Реализовано через `fdopen(0, "r")` + `fgets`, а не через прямое
обращение к глобальной переменной `stdin` — важное решение для
переносимости: имя этой переменной ПЛАТФОРМО-ЗАВИСИМО (`stdin` на Linux,
но `__stdinp` на macOS — другой символ!). `fdopen(0, "r")` даёт тот же
результат стандартным способом, работающим одинаково на обеих платформах.

**⚠️ Известные ограничения этой версии:**
- Перевод строки (Enter), если он был введён, ОСТАЁТСЯ в конце
  результата — не обрезается автоматически. Сравнение прочитанной строки
  с ожидаемым текстом через `==` может неожиданно не совпасть из-за этого
  лишнего символа, если про него не знать заранее.
- Буфер фиксированного размера (1024 байта) — более длинный ввод будет
  обрезан.
- Многократные вызовы подряд (например, в цикле) — каждый вызов заново
  открывает поток через `fdopen`; для одного-двух вызовов должно работать
  надёжно, но для частых повторных вызовов есть теоретический риск
  некорректной буферизации, не проверенный сборкой.

**Как проверить**: `прочитать_строку()` реально ждёт ввода с клавиатуры —
специально НЕ включена в демонстрационный `привет.код` (иначе обычный
`запустить привет.код` завис бы в ожидании ввода). Отдельный файл
`тест_ввода.код` — запускай его отдельно, когда готов(а) что-то ввести:
```bash
запустить тест_ввода.код
```

### Аргументы командной строки — `аргументы_командной_строки()` (продолжение стандартной библиотеки)

`аргументы_командной_строки() -> Список<текст>` — доступ к тому, что было
передано при запуске программы (`запустить программа.код аргумент1 аргумент2`).
В отличие от `прочитать_строку()`, НЕ блокирует выполнение — безопасно
включена прямо в `привет.код`.

**Архитектурная деталь**: сама `главная()` по-прежнему НЕ принимает
параметров (это не менялось) — доступ идёт через отдельную функцию,
вызываемую из ЛЮБОГО места программы. Реализовано через две глобальные
переменные модуля (`глобальный_argc`/`глобальный_argv`), которые обёртка
`main` заполняет из настоящих `argc`/`argv`, полученных от операционной
системы, ДО вызова `главная()` — `аргументы_командной_строки()` читает их
обратно оттуда, откуда бы её ни вызвали.

**Пропускается `argv[0]`** (имя самой программы) — по общепринятой в
большинстве языков конвенции: "аргументы" означают то, что передал
пользователь, а не имя программы, которое и так известно заранее.

**Более простая реализация, чем `Список.добавить(...)` в цикле**: поскольку
количество аргументов известно СРАЗУ (`argc`), буфер выделяется точного
нужного размера напрямую — постепенный рост буфера (как в обычном
`.добавить(...)`) здесь просто не нужен, не сокращённый путь, а
по-настоящему более простой случай.

### Работа с файлами — `прочитать_файл`/`записать_файл` (продолжение стандартной библиотеки)

Раньше язык мог сохранять данные только на время одного запуска — теперь
можно читать и писать на диск:

- **`прочитать_файл(путь) -> результат<текст>`** — читает файл целиком.
  Классический C-порядок действий: открыть, перепрыгнуть в конец (`fseek`),
  спросить позицию (`ftell` — это и есть размер файла), вернуться в начало
  (`fseek`), выделить буфер точного размера, прочитать (`fread`), закрыть
  (`fclose`). `ошибка("не удалось открыть файл")`, если файла нет или прав
  не хватает.
- **`записать_файл(путь, содержимое) -> результат<верно>`** — записывает
  текст в файл (режим `"w"` — создаёт файл, если его не было, ПЕРЕЗАПИСЫВАЕТ,
  если был). Проверяет, что записалось РОВНО столько байт, сколько
  просили (`fwrite` может записать МЕНЬШЕ при нехватке места на диске) —
  `ошибка("не удалось записать файл полностью")`, если запись оказалась
  неполной, а не молчаливая потеря данных.

**⚠️ Техническая деталь, о которой стоит знать**: `fread` НЕ завершает
прочитанные данные нулевым байтом сам по себе (в отличие от `fgets`) —
поэтому `прочитать_файл(...)` вручную дописывает нулевой байт в конец
буфера после чтения. Без этого шага текст "утекал" бы за пределы реальных
данных при любой операции, ожидающей null-terminated текст (`strlen`,
`printf` и так далее) — потенциальный источник неправильного вывода или
чтения мусора из памяти, если бы этот шаг был пропущен.

**Как проверить**: работа с файлами НЕ блокирует выполнение — включена
прямо в `привет.код`. Демонстрация записывает файл
`тест_привет_файл.txt` в текущую директорию, читает его обратно, сравнивает
содержимое (используя `текст == текст`, реализованное раньше — хорошая
проверка того, что сравнение текста работает и на данных, реально
прочитанных с диска, не только на литералах), и отдельно проверяет
`ошибка(...)` для несуществующего файла.

### Выполнение команд оболочки — `выполнить_команду()` (продолжение стандартной библиотеки)

`выполнить_команду(команда) -> результат<целое>` — запускает команду через
командный процессор (оболочку) операционной системы, ждёт её завершения,
возвращает код завершения. Через `system()` из стандартной библиотеки C.

**⚠️ Стоит использовать осторожно** — выполнение произвольных команд
оболочки мощно и потенциально опасно, если команда собирается из
непроверенного пользовательского ввода (классическая уязвимость command
injection). Это стандартная возможность практически любого языка общего
назначения (Python, Go, сам Rust), не что-то специфичное для "Сферы" —
просто как и в любом языке, ей стоит пользоваться обдуманно.

**Техническая деталь**: "сырой" код, который возвращает `system()`, НЕ
является напрямую кодом завершения самой команды — это код завершения
ОБОЛОЧКИ, запустившей команду, закодированный в специальном
POSIX-формате (тот же, что используют `wait()`/`waitpid()`). Реальный код
извлекается через стандартную конвенцию `WEXITSTATUS` — обычно это макрос
в заголовочном C-файле (не отдельная функция, значит её нельзя объявить и
вызвать напрямую), поэтому логика воспроизведена вручную: сдвиг на 8 бит
вправо и побитовое "И" с `0xFF`. Одинаковая конвенция на Linux и macOS —
в отличие от истории с именем переменной `stdin`, здесь платформенных
различий нет.

`ошибка("не удалось запустить команду")` — если саму команду не удалось
запустить вообще (например, не нашлось командного процессора ОС), что
отличается от "команда запустилась, но завершилась с ненулевым кодом" —
это уже `успех(код)`, где код может быть не 0, проверка смысла кода —
ответственность вызывающего кода, как и в большинстве языков.

**Как проверить**: включена прямо в `привет.код` — специально с командой
`echo` (максимально безобидная демонстрация, только выводит текст, не
трогает файловую систему).

## FFI (`внешняя функция`) и графика через SDL2 — первый шаг к UI

**Идея пользователя.** Кликер работал только в консоли — следующий
логичный вопрос был: можно ли добавить визуальный интерфейс, оформленный
как **отдельная, обычная библиотека**, а не что-то вшитое в компилятор?
Ответ — да, и именно так это и сделано.

### Архитектурное решение — общий FFI, а не графика внутри компилятора

Вместо того чтобы встраивать конкретную графическую библиотеку (SDL2)
прямо в код компилятора, в **сам язык** добавлена общая возможность —
привязка к любой функции из любой C-библиотеки:

```
внешняя функция SDL_Init(беззнак32 флаги) -> целое32;
```

Никакого тела — реализация приходит извне, из библиотеки, слинкованной
при сборке (новый флаг `--линковать ИМЯ`, добавляет `-lИМЯ` к линковке).
Это ценно само по себе, независимо от графики — открывает путь к **любым**
существующим C-библиотекам, не только SDL2.

**Привязки к SDL2 написаны как обычный `.код`-файл** — `графика.код`,
подключаемый как `подключить графика;`. Ровно то самое "импортировать
библиотеку любому пользователю", о котором шла речь — не встроенная
магия компилятора, а такой же код, какой может написать любой другой.

### ✅ Реально скомпилировано и запущено — настоящее графическое окно

Проверено пошагово, от простого к сложному:
1. Привязка к `sqrt()` из `libm` — базовый механизм FFI (числа, аргументы, возврат).
2. Привязка к `malloc`/`free` — указатели через FFI.
3. **Настоящее окно SDL2** — инициализация, создание окна и рендерера,
   закраска экрана цветом, показ, корректное завершение. Запущено под
   `Xvfb` (виртуальный дисплей — моя среда без физического экрана), с
   реальным кодом завершения `0` и полным логом выполнения каждого шага.

### ✅ Закрыто: явное приведение типов между числовыми размерами

**Новое.** Раньше приведение типов работало только при передаче
АРГУМЕНТА функции (литерал `32` корректно принимался параметром типа
`беззнак32`), но не при ПРИСВАИВАНИИ переменной или СРАВНЕНИИ (строгая
проверка типов) — для FFI, где точный размер типа критичен для ABI, это
было настоящим неудобством. Теперь есть явное приведение, переиспользующее
уже привычный синтаксис "имя(...)" (как у конструкторов структур), но для
встроенных числовых типов означающее приведение:

```
целое32 узкое = целое32(1000);
целое широкое = целое(узкое);
дробное дробь = дробное(широкое);
```

Понадобилось изменить все три уровня: лексер уже знал ключевые слова
типов, но **парсер** совсем не ожидал `(` сразу после токена типа (типы
— отдельные токены, не идентификаторы, значит без явной новой ветки
парсер падал с "ожидалось выражение"); **семантика** проверяет, что
аргумент — число, и определяет целевой тип; **кодогенерация** выбирает
между `build_int_cast_sign_flag`, `build_signed_int_to_float`,
`build_float_cast`, `build_float_to_signed_int`/`build_float_to_unsigned_int`
в зависимости от направления приведения. Реально скомпилировано и
запущено — вся цепочка `целое32 → целое → дробное → целое32 → целое`.

### ✅ Закрыто: обработка событий (клики мыши)

**Новое, самая ценная находка этого захода.** `SDL_PollEvent` требует
передать указатель на структуру `SDL_Event` — обойдено без полноценной
поддержки "C-совместимых структур" (которая остаётся отдельным, большим
шагом): добавлен общий примитив `прочитать_целое32(указатель, смещение)
-> целое32`, читающий 4 байта по произвольному смещению в памяти.
Точные байтовые смещения полей (`type=0`, `x=20`, `y=24`) и константы
(`SDL_QUIT=256`, `SDL_MOUSEBUTTONDOWN=1025`) получены не по памяти, а
**фактическим замером** — маленькая C-программа с `offsetof`/`sizeof`,
скомпилированная и запущенная против реально установленных заголовков SDL2.

**✅ Проверено симуляцией настоящего внешнего клика**, не просто
"программа не падает": через `xdotool` (эквивалент реального аппаратного
клика мыши с точки зрения X11/SDL2) отправлены два клика по точным
координатам под виртуальным дисплеем — программа поймала **оба**, с
координатами, совпадающими байт-в-байт с тем, что было реально послано:

```
Клик! Координаты х: 200  координаты у: 150
Клик! Координаты х: 100  координаты у: 100
Всего кликов зарегистрировано: 2
```

`⚠️ Это НЕБЕЗОПАСНАЯ операция по своей природе (как разыменование сырого
указателя в C) — компилятор не проверяет, что указатель реально
указывает на буфер нужного размера. Ответственность на программисте.`

### ⚠️ Честные ограничения, которые остаются

**Указатели представлены типом `текст`** — прагматичное переиспользование
уже существующего `i8*`-представления, не отдельный тип. Работает
корректно на уровне памяти, но не идеально семантически чисто.

**Нет C-совместимых структур по значению.** Наши структуры всегда несут
скрытый ARC-заголовок и используют 64-битные целые — не совпадает по
памяти с "голыми" C-структурами (`SDL_Rect` — четыре 32-битных `int`, без
заголовка). Значит рисование фигур (`SDL_RenderFillRect` и подобные) всё
ещё не включено в привязки — обойдено для событий через
`прочитать_целое32`, но для функций, ПРИНИМАЮЩИХ структуру по значению
(не только читающих байты уже существующего буфера), этого недостаточно.

### Побочная находка — давняя рассинхронизация LSP-сервера

Добавление нового бинарника стало поводом впервые за долгое время
собрать **весь** проект разом (`cargo build`, без `--bin`) — и это сразу
вскрыло: `сфера_lsp` не компилировался вообще, ломаясь на
`ВерхнийУзел::ВнешняяФункция` (добавленном много сессий назад, во время
работы над FFI, но не отражённом в LSP-сервере). Раньше это оставалось
незамеченным, поскольку каждая сессия собирала только `--bin sfera`
отдельно. Исправлено — заодно добавлена обработка внешних функций в
автодополнении LSP.

## Настоящая загрузка "на голом железе" — первый шаг, проверенный через QEMU

**Следующий, более глубокий шаг после автономного режима.** Раньше
программа работала без `libc`, но всё ещё запускалась ядром Linux как
обычный процесс. Здесь — попытка убрать и эту последнюю опору: пусть
программу загружает напрямую прошивка компьютера (BIOS/UEFI), без какой
бы то ни было операционной системы вообще.

### Архитектурное решение — Multiboot вместо своего загрузчика

Писать собственный загрузчик для BIOS с нуля (16-битный реальный режим,
чтение секторов диска вручную) — большая, отдельная тема, отвлекающая от
самой сути "ядра". Вместо этого использован стандарт **Multiboot** (тот
же, что понимает GRUB) — достаточно правильного заголовка (магическое
число + флаги + контрольная сумма) в начале файла, и `QEMU` умеет
загружать такое "ядро" напрямую (флаг `-kernel`), вообще без диска и
загрузчика.

### ✅ Проверено объективно — не на словах, а на экране

Собран простой `.s`-файл (`ядро_голое_железо.s`) с Multiboot-заголовком
и 32-битной точкой входа, пишущей текст напрямую в видеопамять (адрес
`0xB8000` — классический, с первых IBM PC способ вывести текст без
единого драйвера). Слинкован через собственный `linker script`
(`компоновка_ядра.ld`, стандартный адрес загрузки 1 МБ). Загружен через
`qemu-system-x86_64 -kernel ядро.bin` — и через встроенный механизм
QEMU (`screendump` через монитор) сделан снимок экрана, **объективно
подтверждающий**: текст "Sfera: bare metal OK" реально появился на
экране, ярко-зелёным цветом, ровно в заданном месте (см.
`скриншот_загрузки_голого_железа.png`).

### ✅ Закрыто: переход в 64-битный режим — настоящий код на Сфере работает без ОС вообще

**Прямое продолжение предыдущего шага**, реализованное в следующей же
сессии. Multiboot передаёт управление в 32-битном защищённом режиме
процессора, а наш компилятор генерирует 64-битный код — нужен был полный
переход между режимами (`long mode`), хорошо документированная, но
объёмная последовательность (см. `ядро_64.s`):

1. Настройка таблиц страниц (`PML4` → `PDPT` → `PD`, идентичное
   отображение первых 2 МБ памяти страницами по 2 МБ)
2. Включение `PAE` (бит в `CR4`)
3. Загрузка адреса таблиц страниц в `CR3`
4. Включение `long mode` через бит `LME` в модельно-специфичном регистре
   `EFER`
5. Включение самой страничной адресации (бит `PG` в `CR0`)
6. Загрузка 64-битной `GDT` и дальний переход (`jmp 0x08:метка`) — именно
   этот переход и переключает процессор в полноценное 64-битное
   выполнение

После перехода — прямой вызов (`call main`) уже готовой, скомпилированной
нашим языком функции `main`, без единого изменения в самом компиляторе.

### ⚠️ Реальная находка, обнаруженная попыткой загрузки

Первая попытка честно провалилась с понятной ошибкой QEMU: `"Cannot load
x86-64 image, give a 32bit one"`. Оказалось, что Multiboot 1
(традиционная спецификация, которую понимает `-kernel`) требует именно
**32-битный ELF-контейнер** — даже если сам машинный код внутри
64-битный. Решение — известная в сообществе разработки хобби-ОС техника:
`OUTPUT_FORMAT(elf32-i386)` прямо в `linker script`, оборачивающая
64-битный код в 32-битный формат заголовка файла.

### ✅ Проверено объективно — тем же способом, что и шагом раньше

Тестовая программа (`главная() { вернуть 12 + 18; }`) скомпилирована
обычным компилятором Сферы, слинкована вместе с `ядро_64.s`. Снимок
экрана QEMU показывает **"Sfera: 30"** — точный, правильный результат
вычисления, отображённый жёлтым цветом после того, как управление
вернулось из настоящего, скомпилированного нашим языком кода обратно в
ассемблер (см. `скриншот_64bit_голое_железо.png`).

### ✅ Закрыто: структуры и ARC работают и в настоящем "голом железе"

**Прямое продолжение — реализовано в следующей же сессии.** Тот же
самый bump allocator (`арена_распределитель.код`), что уже работал в
автономном Linux-режиме, заработал и здесь **без единого изменения в
своей логике** — понадобилось только выделить для него отдельную,
собственную область памяти прямо в `ядро_64.s` (и расширить отображение
памяти с 2 МБ до 4 МБ, чтобы её разместить — таблицы страниц теперь
покрывают две страницы по 2 МБ вместо одной).

**✅ Проверено объективно, тем же способом** — тестовая структура
`Точка(25, 17)`, созданная через собственный `malloc`, скомпилированный
Сферой в главный файл (не подключаемый модуль — то же самое ограничение
с манглированием имён, что и в Linux-режиме). Снимок экрана QEMU
показывает **"Sfera: 42"** — точный результат `25+17`.

### ✅ Закрыто: `вывести(...)` реально работает — собственный `printf` с нуля

**Прямое продолжение — доведено до конца в следующей же сессии.**
Написана собственная, ограниченная реализация `printf` на чистом
ассемблере (в `ядро_64.s`) — поддерживает ровно то, что реально
использует `вывести(...)` внутри компилятора (проверено напрямую в
исходниках): `%s` (текст), `%lld` (64-битное целое), `\n`, `%%`.

**Технически самое сложное** — вариативные аргументы по System V ABI:
целочисленные/указательные идут через `rsi, rdx, rcx, r8, r9` (поскольку
`rdi` уже занят самой форматной строкой), сохраняются на стек в начале
функции, чтобы можно было брать их по порядковому номеру, обходя
форматную строку слева направо. Плюс три вспомогательные функции,
переиспользуемые не только `printf` — запись одного символа с
отслеживанием позиции курсора и переносом строк, запись целой строки,
перевод знакового 64-битного числа в десятичную запись.

**⚠️ Реальная находка, обнаруженная тестом**: первая попытка дала
"сломанный" вывод — оказалось, старый код (выводивший результат `main`
напрямую по фиксированному адресу `0xB8000`) конфликтовал с новым
`printf`, использующим общий, продвигающийся курсор — оба писали, начиная
с одного и того же места, второй затирал первый. Решение — единый способ
вывода для всего: старый, отдельный код заменён на использование тех же
вспомогательных функций, что и `printf`.

**✅ Проверено объективно, тем же способом**: снимок экрана QEMU
показывает **"Hello from bare metal!"**, **"777"** и **"Result: 0"** —
все три вывода чёткие, без искажений, в правильном порядке.

### ⚠️ Честные, реальные ограничения этой версии

- **Нет `%f`** (дробные числа) — корректное преобразование `double` в
  десятичную строку с нуля на ассемблере (используя `SSE`-регистры
  `xmm`, отдельно индексируемые от целочисленных аргументов по той же
  ABI) — самостоятельный, более объёмный следующий шаг.
- **Кириллица всё ещё не отображается** — то же, уже известное
  ограничение классического текстового режима VGA (однобайтовая
  кодировка, не понимает многобайтовый UTF-8) — обнаружено снова при
  первой попытке теста (кириллический текст дал "сломанную"
  псевдографику), тестовые программы намеренно на латинице.
- **Нет прокрутки экрана** — если текста больше, чем помещается на
  экране (25 строк), новый вывод продолжит писать за пределами
  видимой (и отображённой в памяти) области — для маленьких тестовых
  программ не критично, для более сложной программы понадобилась бы
  логика прокрутки.

## Автономный режим (v1) — `--автономно РАНТАЙМ.o` — работа без операционной системы

**Ответ на вопрос "может ли этот язык быть основой для чего угодно"** —
включая ядро ОС, загрузчик, прошивку встраиваемого устройства. Всё, что
мы писали раньше, работало *поверх* операционной системы, полагаясь на
неё в самых базовых вещах — выделение памяти, вывод текста, даже саму
точку входа программы. Этот режим убирает эту опору целиком.

### Архитектурное решение — не менять компилятор, а написать замену снаружи

Вместо того чтобы встраивать поддержку ассемблерных вставок в сам язык
(чего у нас нет и не было), написан **отдельный, настоящий x86-64
ассемблерный файл** (`минимальный_рантайм.s`) — собирается через `as`,
подключается при линковке. Компилятору не потребовалось ни одного
изменения для генерации самого кода — только новый флаг для линковки.

**Ключевая находка**: компилятор уже генерирует настоящую
C-совместимую функцию `main` (вызывающую пользовательскую `главная`),
рассчитывая на цепочку `_start -> __libc_start_main -> main` из libc. В
автономном режиме этой цепочки нет — но саму `main` переписывать не
пришлось: собственная `_start` (в `минимальный_рантайм.s`) читает
`argc`/`argv` напрямую со стека (их туда кладёт само ядро Linux при
запуске **любого** ELF-файла, ещё до какого-либо участия `libc`) и
вызывает уже готовую `main` напрямую.

### Что даёт минимальный рантайм

- `_start` — точка входа, вызывает `main`, затем системный вызов
  `exit_group` с её результатом
- `sfera_write` — вывод текста напрямую через системный вызов `write`
  (номер 1 на x86-64), без `printf`
- `strlen` — **честная находка, обнаруженная реальным тестом линковки,
  не предвиденная заранее**: встроенная функция языка `длина(...)`
  внутри себя вызывает настоящий `strlen` из `libc`, которого в
  автономном режиме взять неоткуда

### ✅ Проверено объективно, не на словах

```
file программа  →  "statically linked"
ldd программа    →  "not a dynamic executable"
```

Запущена, дала правильный вывод текста и корректный код завершения —
**полностью без единого байта libc**, только прямые системные вызовы.

### ✅ Закрыто: структуры и ARC работают — распределитель памяти написан на самом языке Сфера

**Прямое продолжение находки выше.** Распределитель памяти
(`арена_распределитель.код`) — простейший "bump allocator" (никогда не
освобождает по-настоящему, только продвигает указатель вперёд),
написанный **полностью на языке Сфера**, без единой ассемблерной вставки
внутри самой логики — только `прочитать_целое32`/`записать_целое32`
поверх области памяти размером 1 МБ, зарезервированной в
`.bss`-секции рантайма (`минимальный_рантайм.s`).

**Архитектурная находка**: то же самое решение, что уже нашлось для
полностью кириллических имён FFI-функций (`как "РеальноеИмя"`),
сработало и в обратную сторону — обычная функция языка Сфера,
объявленная прямо в главном файле (не через `внешняя функция`), получает
ровно такое же, буквальное LLVM-имя, что и ждёт наш ARC. Функция,
названная `malloc` в коде программиста — это и есть тот самый `malloc`,
который ищет кодогенератор, без единого изменения в компиляторе.

**⚠️ Ещё одна реальная находка, обнаруженная тестом линковки**: функции
`malloc`/`free` **обязаны** находиться прямо в главном файле — если их
подключить через `подключить` (отдельным модулем), они манглируются
(см. пространства имён v2, `модуль__имя`), и ARC их не найдёт. Узкое,
честно задокументированное ограничение v1.

**✅ Проверено объективно**: тестовая структура `Точка(10, 20)` создана
через собственный `malloc`, её поля прочитаны и просуммированы —
программа завершилась с кодом `30`, точным ожидаемым результатом. `file`
и `ldd` подтверждают полную независимость от `libc`.

### ⚠️ Честные, реальные ограничения этой версии

- **`free` — пустая функция, память никогда не переиспользуется** —
  честное, намеренное ограничение "bump allocator" — достаточно для
  демонстрации и коротко живущих программ, не подходит для долго
  работающей программы с частыми выделениями/освобождениями. Настоящий,
  умеющий переиспользовать освобождённую память распределитель —
  самостоятельный, больший следующий шаг.
- **Только Linux x86-64** — `минимальный_рантайм.s` писан руками именно
  под эту архитектуру и её соглашение о системных вызовах. Для другого
  процессора (ARM для настоящего кнопочного телефона) понадобился бы
  отдельный ассемблерный файл со своими номерами вызовов и регистрами.
- **Это не настоящая загрузка "на голом железе"** — программа всё ещё
  запускается ядром Linux как обычный процесс (что и позволило её
  реально протестировать здесь) — для настоящего ядра ОС или загрузчика
  понадобился бы ещё один слой (переход из реального режима процессора,
  собственная таблица прерываний и так далее) — увлекательный, большой,
  честно отдельный следующий шаг.

## Многопоточность (v1) — `параллельно { тело }`

**Давно откладывалось** — ключевые слова `параллельно`/`канал` существовали
в грамматике с первой сессии (лексер, парсер уже частично разбирали
`параллельно { тело }` как `Оператор::Параллельно`), но кодогенерация
жёстко отклоняла это — та же ситуация, что раньше была со `слабая` и
`контракт`.

### Мотивация — не абстрактная, а из собственного проекта

Панель разработчика (`панель.код`) замирает на время сборки — весь код
выполняется последовательно, и пока `выполнить_команду` ждёт завершения
компилятора, окно физически не может обработать клик или перерисовать
экран. Многопоточность — прямое решение именно этой проблемы.

### Главная техническая сложность — ARC не защищён от гонок

Счётчик ссылок структур сейчас не атомарный — если два потока
одновременно меняют его для одной и той же структуры, это классическая
гонка данных (потерянный инкремент, преждевременное освобождение). Та же
проблема, с которой столкнулись Swift и Objective-C; у Rust для этого
два разных типа — `Rc<T>` (быстрый, один поток) и `Arc<T>` (чуть
медленнее, безопасен между потоками).

### Архитектура v1 — pthread, честно узкий охват

`параллельно { тело }` генерирует тело блока как **совершенно отдельную**
LLVM-функцию (сигнатура `i8* (i8*)`, ожидаемая `pthread_create` для
`start_routine`) и запускает её через `pthread_create`, не дожидаясь
завершения — родительская функция продолжает выполняться сразу.

**⚠️ Честное, намеренное ограничение**: тело блока генерируется с
**чистой** (пустой) таблицей переменных — тем же приёмом, что уже
используется для обычных функций языка. Это не "лень", а реальная защита
от опасной ошибки: если бы блок мог ссылаться на локальную переменную
родительской функции (её адрес в стеке), а родительская функция
завершилась бы раньше потока — поток обращался бы к уже освобождённой
памяти стека (use-after-return). Попытка использовать внешнюю переменную
внутри `параллельно` проваливается на этапе компиляции с "переменная не
найдена" — ограничение не тихое, компилятор его ловит, просто без
специального сообщения именно про потоки.

### ✅ Проверено объективно — не просто "не упало"

Установил и использовал `helgrind` (детектор гонок данных) — **0 ошибок,
0 контекстов**. Отдельный, более строгий тест: два потока с разной
задержкой (1 сек и 2 сек), запущенные в обратном порядке — быстрый поток
завершился раньше медленного, **несмотря на то, что был запущен вторым в
коде**. Это невозможно при последовательном выполнении — объективное,
неопровержимое доказательство реальной параллельности.

### ✅ Закрыто позже: `канал<T>` — безопасная передача значения между потоками

**Прямое продолжение** — реализовано в следующей сессии, отвечая на
честно названный пробел выше. `канал<T>` — простой, потокобезопасный
"почтовый ящик" для одного значения: `создать_канал()`, методы
`.отправить(значение)`/`.получить()` (блокирующий — ждёт, пока значение
не появится).

**Архитектурное решение** — единственное осознанное исключение из
"чистого контекста" `параллельно` (см. выше): раз канал — это указатель
на кучу, а не локальная переменная на стеке, его ЗНАЧЕНИЕ безопасно
скопировать в новый поток — риск use-after-return, из-за которого чистый
контекст и появился, тут не действует.

**⚠️ Реальная, поучительная ошибка, найденная тестом (не предвиденная
заранее)**: первая версия честно упала с segfault. `gdb` показал мусорный
адрес мьютекса внутри функции потока. Причина оказалась фундаментальной:
**LLVM-значения (SSA) не могут пересекать границы функций** — попытка
вычислить указатель на канал в родительской функции и напрямую
использовать это же значение в отдельной, независимой функции потока
нарушает базовое правило LLVM IR. Правильное решение — как и с самими
данными потока, передавать через настоящую память: значения каналов
пишутся в небольшой `malloc`-буфер в родительском коде, указатель на
буфер передаётся как штатный аргумент `pthread_create` (`arg`, до этого
момента им пренебрегали, всегда передавая `NULL`), сам поток читает из
него и освобождает буфер в начале своего выполнения.

**✅ Проверено объективно, тем же способом**, что и весь `параллельно`:
реальная программа (главный поток создаёт канал, `параллельно`
вычисляет `2+2` и отправляет результат, главный поток получает и
выводит) — вывела точное значение `4`. `helgrind` — **0 ошибок, 0
контекстов**, подтверждает корректность синхронизации через
`pthread_mutex`/`pthread_cond`. `valgrind` (утечки) показывает ровно
одну, честно ожидаемую: сама структура канала (272 байта) — у неё пока
нет команды закрытия, аналогично тому, что `параллельно` пока не умеет
`join`.

**⚠️ Честные ограничения `канал<T>` v1**:
- Поддерживает только целочисленные и указательные типы значения (не
  дробные и не встраиваемые напрямую структуры) — 8-байтный слот
  хранения рассчитан именно на эти два случая.
- Односторонняя передача одного значения ("bump", не очередь) — второй
  вызов `.получить()` без нового `.отправить()` вернёт то же самое,
  устаревшее значение, а не будет ждать заново.
- Нет команды закрытия/освобождения канала — намеренно узкий охват v1,
  та же честная утечка, что уже была принята для незавершаемых потоков.
- Размер области под `pthread_mutex_t`/`pthread_cond_t` выделен с
  запасом (128 байт на каждую) ради переносимости между Linux и macOS,
  чей точный `sizeof` отличается — не самое компактное решение, но
  безопасное на обеих платформах.

### ⚠️ Честные ограничения версии `параллельно`

- **Нет `join`/ожидания завершения** — `параллельно` только запускает,
  не даёт способа дождаться результата напрямую (частично компенсируется
  каналом — см. выше — для случая "получить одно значение обратно").
- **ARC остаётся не потокобезопасным** — структуры, реально
  разделяемые между потоками (что пока и невозможно из-за ограничения
  на захват переменных), были бы небезопасны при одновременном доступе.
- **Нет пула потоков** — каждый `параллельно` создаёт новый поток ОС
  напрямую, не самый дешёвый механизм при частом использовании.

## Пакетный менеджер (v1) — `сфера_пакеты`

**Отдельный инструмент, не расширение языка.** Новый бинарник (по той же
схеме, что и `сфера_lsp` — файл в `src/bin/`, cargo подхватывает
автоматически, без изменений в `Cargo.toml`).

### Архитектурное решение — git как реестр, без своей инфраструктуры

Нет и не будет своего центрального реестра пакетов (как crates.io/npm) —
содержать такую инфраструктуру нереалистично. Вместо этого: **зависимость
— это просто ссылка на git-репозиторий**. Тот же подход, с которого
начинались Go modules и ранний Cargo (до появления crates.io) —
полностью децентрализованно, не требует ни одного сервера в нашем
владении.

**Формат манифеста** (`сфера.зависимости`, простой построчный текст —
не JSON/TOML, специально: минимум кода, без новых зависимостей в
`Cargo.toml`, полный контроль над форматом):

```
геометрия = git https://github.com/кто-то/геометрия-сфера.git
графика_доп = git https://github.com/кто-то/графика-доп.git ветка=разработка
```

**Установка** (`сфера_пакеты установить`) клонирует каждый репозиторий во
временную папку и копирует из его **корня** все `.код` файлы прямо в
`пакеты/` проекта — тот же, уже существующий и работающий механизм
разрешения `подключить` используется **без единого изменения** в
компиляторе.

### ✅ Реально протестировано — полный цикл, не только компиляция инструмента

Создал настоящий git-репозиторий (`git init` + `commit`) с пакетом
`геометрия.код` (две функции), добавил его как зависимость через `file://`
URL, запустил `сфера_пакеты установить` — **реальный** `git clone`

## ✅ Частично закрыто: текст под ARC (v1)

**Вторая, более крупная часть закрытия ARC** — давно известная утечка,
найденная ещё во время работы над кликером: текстовые функции
(конкатенация `+`, `регистр_в_верхний`/`регистр_в_нижний`,
`целое_в_текст`, `дробное_в_текст`, `верно_в_текст`) создают `malloc`-буфер,
который никогда не освобождался — текст в языке не находился под
управлением ARC, в отличие от структур.

### Почему это сложнее, чем ARC для структур

Структуры **всегда** несут ARC-заголовок — с текстом иначе: строковый
**литерал** ("Привет") — это глобальная константа, которую **нельзя**
освобождать никогда, а **вычисленный** текст (результат конкатенации и
подобного) — это `malloc`-буфер, который **нужно** освобождать. Оба
неотличимы друг от друга во время выполнения программы (оба — обычный
`i8*`) — различить их можно только **статически**, глядя на то, каким
именно выражением была инициализирована переменная.

### Архитектура v1

Добавлен параллельный стек `стек_arc_областей_текста` (по образцу уже
существующего для структур) и функция `является_текст_порождающим`,
распознающая выражения, создающие новый буфер. При объявлении переменной
вида `текст имя = <текст-порождающее выражение>;` переменная помечается
как "владеющая" и освобождается при выходе из области видимости — та же
защита от освобождения возвращаемого значения, что уже была у структур.

### ✅ Проверено через `valgrind` — реальное, измеримое снижение утечки

```
Изолированный тест (конкатенация + регистр_в_верхний + целое_в_текст):
  112 байт (5 блоков) → 36 байт (2 блока)

Весь привет.код целиком:
  ~750 байт → 631 байт (311 definitely + 320 indirectly lost)
```

Не "0 утечек" — честно, реальный прогресс, не полное закрытие.

### Найденная по пути собственная ошибка — и как она была поймана

Первая попытка **не сработала вообще** — утечка не изменилась ни на байт,
несмотря на то, что логика пометки переменных была написана правильно.
Добавил временный отладочный вывод (`eprintln!`) прямо в кодогенератор —
он подтвердил, что переменные **реально** помечаются как владеющие.
Значит проблема была в другом месте — оказалось, стек инициализируется
для тела функции **не через `.push()`** (который я нашёл и обновил
первым), а через прямое присваивание `self.стек_arc_областей = vec![Vec::new()]`
в двух местах, которые не совпали с моим первым поиском. Без начального
фрейма `стек_arc_областей_текста` оставался пустым всю функцию —
`last_mut()` возвращал `None`, и пометка молча пропадала в никуда.
Нашёл и исправил оба места, подтвердил результат повторным прогоном
через `valgrind`.

### ✅ Закрыто позже: настоящий double-free, найденный при попытке расширить покрытие

При попытке закрыть ещё один узкий случай (переприсваивание уже
существующей переменной) обнаружилась куда более серьёзная, реальная
ошибка, чем просто утечка. Добавил безопасное, узкое улучшение —
освобождать старое значение при переприсваивании, но только если
переменная **уже** отслеживалась как владеющая — и решил проверить его
на переменной, объявленной **внутри цикла** (`текст временный = ...;` на
каждой итерации). `valgrind` показал не утечку, а **`Invalid free()`** —
настоящий double-free.

**Причина**: `push()` нового фрейма для текстового стека
(`стек_arc_областей_текста`) существовал в четырёх местах (`если`,
`пока`, `для каждого`), но соответствующий `pop()` при выходе из блока
был добавлен только для **структурного** стека — текстовый фрейм тела
цикла просто никогда не убирался. При каждом `вернуть` из функции,
`освободить_при_возврате` обходит **весь** стек фреймов — включая
"застрявший" фрейм цикла, из-за чего текстовая переменная, уже
освобождённая на последней итерации, освобождалась ещё раз.

**Исправление** — тривиальное по объёму (добавить `pop()` в
недостающих четырёх местах), но найдено только благодаря честной,
принципиальной проверке узкого улучшения через `valgrind`, а не
поверхностным "выглядит правильно". Подтверждено: `6 allocs, 6 frees`,
`0 errors`, включая отсутствие double-free.

**Заодно закрыт**, безопасно и без риска use-after-free, узкий случай
переприсваивания уже отслеживаемой переменной новым владеющим значением
(`текст а = вычислить(); ... а = другое_вычисление();`) — не расширяет
покрытие на переменные, стартовавшие с литерала (это потребовало бы
более глубокого архитектурного пересмотра — отслеживания владения в
масштабе всей функции, а не по вложенным блокам, поскольку `alloca`
физически живёт до конца функции, а не блока — честно отложено, риск
поспешного решения (use-after-free) серьёзнее пользы).

### ✅ Закрыто позже: промежуточные значения в цепочках конкатенации

**Прямое продолжение — реализовано в следующей сессии.** `а + б + в`
компилируется в два вложенных вызова конкатенации: сначала `а + б`
(промежуточный буфер), затем `(а+б) + в` (итоговый буфер) — промежуточный
результат раньше никогда не освобождался, честная утечка на каждой
цепочке из трёх и более слагаемых.

**Решение** — безопасное, локальное исправление внутри вычисления
одного выражения (не затрагивает более рискованную архитектуру
отслеживания по блокам, где раньше уже находился настоящий double-free
— см. выше): в `сгенерировать_бинарное`, сразу после того как оба
операнда были использованы (конкатенация их скопировала, сравнение
`==`/`!=` их прочитало) — если операнд сам **является** текст-порождающим
выражением (`является_текст_порождающим` — вложенная конкатенация или
вызов `регистр_в_верхний`/`целое_в_текст` и подобных), он немедленно
освобождается. Простая переменная или литерал как операнд не
освобождаются — ими Сфера не владеет.

**Проверено объективно**, тем же способом — три отдельных теста
(`а + б + в`, сравнение `(а + " " + б) == "..."`, `регистр_в_верхний(х) + "!"`)
— каждый через `valgrind`: `3 allocs, 3 frees`, `0 bytes in 0 blocks`,
`0 errors`. Полное отсутствие утечек там, где раньше они были
гарантированы при любой цепочке из трёх и более частей.

### ✅ Закрыто позже: текст внутри `результат<T>`

**Продолжение той же работы**, ещё в этой же сессии. `результат<текст> р
= подстрока(...);` (а также `прочитать_строку`/`прочитать_файл`) — тоже
может создавать свежий malloc'нутый буфер, но "внутри" обёртки {успешно,
значение, сообщение}, а не как голый указатель — раньше вообще не
отслеживалось.

**Архитектурное решение — осознанно не заводить отдельный параллельный
стек отслеживания** (риск повторить недавно найденный double-free от
забытого `pop()` в одном из мест — слишком реален) — переменные типа
`результат<текст>`, инициализированные известным, коротким списком
функций (`является_результат_текст_порождающим`), добавляются в **тот
же самый** список отслеживания, что и обычный текст. При освобождении
(`отпустить_список_текстовых_переменных`) логика различает два случая по
фактическому LLVM-типу переменной: простой указатель — освобождается как
раньше, безусловно; структура `результат<T>` — извлекается поле
"успешно", и **только если оно истинно**, извлекается и освобождается
поле "значение" (через настоящее ветвление в LLVM IR, не просто
проверку на этапе компиляции) — при неудаче поле значения не было
создано этим вызовом, освобождать нечего и нельзя.

**Проверено объективно**, тем же способом — три отдельных теста
(`подстрока` успешный случай, `подстрока` с заведомо неверными границами
— неуспешный случай, `прочитать_файл`) — каждый через `valgrind`: во всех
трёх `0 errors`, полное отсутствие утечек. Отдельно, специально
проверен неуспешный случай — ни одной попытки освободить несуществующий
указатель (что привело бы к падению, а не просто к утечке).

### ✅ Частично закрыто, и найден реальный use-after-free: переменная, стартовавшая с литерала

**Последний из четырёх изначальных пробелов текста под ARC**, доведённый
до честного, проверенного предела в этой сессии.

**Архитектурное решение**: `alloca` переменной физически живёт до конца
всей функции (не блока) в любом случае — значит безопасно добавлять её
в **самый внешний** (функциональный) фрейм стека областей видимости
вместо текущего вложенного, при первом же переприсваивании владеющим
значением. Естественный выход из вложенного блока эту запись не
затронет — она освободится либо при настоящем выходе из функции, либо
раньше, при следующем переприсваивании.

**⚠️ Реальный, серьёзный баг, найденный первым же тестом — не утечка, a
настоящий use-after-free**: `valgrind` показал `Invalid read` и мусор в
выводе программы вместо ожидаемого текста. Причина — порядок операций:
старое значение переменной освобождалось **до** вычисления нового, а
новое значение (`регистр_в_верхний(сообщение)`) само читает старое
значение той же переменной изнутри — к моменту чтения память уже была
освобождена. Исправлено — новое значение теперь всегда вычисляется
**первым**, до любого решения об освобождении старого.

**✅ Проверено объективно и подтверждено, что работает — для линейного
кода**: `текст а = "старт"; а = регистр_в_верхний(а);` (без цикла) —
`valgrind`: `2 allocs, 2 frees`, `0 errors`.

**⚠️ Честно найденный, реальный предел этого подхода — внутри циклов**:
тот же тест, но с переприсваиванием **внутри** `пока` (5 итераций) —
даёт `54 bytes in 4 blocks` утечки (было бы `135 bytes in 10 blocks` без
всех этих исправлений — реальное, но неполное улучшение). Причина
глубже, чем просто "недоделано": решение "генерировать ли код
освобождения" принимается компилятором **один раз**, в момент первой
(и единственной) генерации LLVM IR для конкретного узла AST — а внутри
цикла тот же самый узел выполняется многократно в рантайме, и уже
начиная со второй итерации переменная фактически владеющая, хотя на
момент компиляции этого узла она ещё не была таковой. Полное закрытие
требует не просто отслеживания на этапе компиляции, а настоящего
**рантайм-флага** ("владеет ли переменная прямо сейчас malloc'нутым
значением") — качественно другая, более объёмная задача, честно
отложенная, не решаемая "на глаз" в рамках уже выбранной архитектуры.

### ⚠️ Честные, узкие границы этой версии

Отслеживаются простые локальные переменные вида `текст имя =
<выражение>;`, промежуточные значения внутри цепочек `+`/`==`/`!=`, текст
внутри `результат<текст>` от `подстрока`/`прочитать_строку`/
`прочитать_файл`, и (с этой сессии) переменные, впервые становящиеся
владеющими через переприсваивание — но полностью корректно только вне
циклов (см. раздел выше). Вот что осталось **не покрыто**, честно:
- **Внутри циклов** — переменная, стартовавшая как литерал и
  переприсваиваемая на каждой итерации, течёт частично (см. раздел
  выше) — требует настоящего рантайм-флага владения, не просто
  компиляционного отслеживания.
- **Прямая передача результата без промежуточной переменной**
  (`вывести(целое_в_текст(42));`) — нет переменной, значит нечего
  пометить.
- **Текстовые поля структур** — структура может пережить функцию, где
  создан её текст — сложная семантика владения, отдельный следующий шаг.

## ✅ Закрыто: слабые ссылки (`слабая`) — разрыв циклов ARC

**Первая часть "закрытия ARC".** Ключевое слово `слабая` существовало в
грамматике с самой первой сессии (лексер, парсер уже разбирали его как
модификатор поля структуры), но семантика жёстко отклоняла любое его
использование: `"слабая" пока не поддержана — требует реализации ARC`.

```
структура Держатель {
    текст имя;
    слабая Цель цель;    // не увеличивает счётчик ссылок "Цель" при записи
}
```

**Архитектурная суть:** в кодогенераторе уже существовала карта
"структурные_поля" — список полей структуры, которые сами являются
структурами, используемая ОДНОВРЕМЕННО для двух целей: увеличения счётчика
ссылок при записи поля и рекурсивного освобождения при уничтожении
владельца. Достаточно **исключить** слабое поле из этой карты — оно
автоматически перестаёт участвовать в обеих операциях, что и разрывает
цикл (сильная ссылка А→Б не блокируется тем, что Б "как бы" ссылается
на А через слабое поле).

**Найденный по пути побочный эффект.** Та же карта оказалась
использована ещё для одной, не связанной с ARC цели — определения типа
поля при цепочке доступа (`держатель.цель.имя`). Исключение слабых полей
случайно сломало и эту функциональность. Решение: завести **вторую**,
полную карту (`все_структурные_поля`, без исключений) специально для
навигации по цепочкам, оставив урезанную версию только для ARC-логики.

**✅ Проверено через `valgrind`** — не просто "не упало": идеальный
баланс `3 allocs, 3 frees`, `0 bytes` в утечке, `0 errors` — включая
отсутствие double-free при последующем использовании цели через
оставшуюся сильную ссылку.

### ⚠️ Честные ограничения этой версии

**Не "настоящая" слабая ссылка с проверкой живости цели** — в отличие от
Swift/Objective-C, где слабая ссылка автоматически становится `nil`/`null`
при освобождении цели, здесь слабая ссылка **может стать висячей**
(указывать на уже освобождённую память), если использовать её после
освобождения цели. Правильная защита потребовала бы отдельного механизма
отслеживания "жива ли цель ещё" (side-table/индирекция) — самостоятельный,
больший следующий шаг.

**Попутно найден отдельный, не связанный со слабыми ссылками пробел ARC:**
обычное присваивание полю структуры **после** её создания
(`держатель.цель = новая_цель;`, в отличие от присваивания при
конструировании) вообще не делает retain/release — пишет значение
напрямую. Это существовало и раньше, независимо от слабых ссылок, просто
было обнаружено именно сейчас при проверке всех путей записи поля.
Честно названный, отдельный следующий шаг — не тронут в этой сессии.

## Работа со шрифтами — последний крупный кирпичик визуального интерфейса

**Завершает список UI-примитивов, поставленный пользователем**: кнопки,
ввод текста с клавиатуры, отрисовка прямоугольников, работа со шрифтами
— теперь всё это реально работает.

### Новая библиотека — SDL_ttf, найденная ABI-хитрость

Подключена `SDL_ttf` (`--линковать SDL2_ttf`), плюс системный шрифт
`DejaVuSans.ttf` (поддерживает кириллицу). `TTF_RenderUTF8_Solid`
принимает `SDL_Color` (4 байта — r,g,b,a) **по значению**, не по
указателю — впервые для нашего FFI. На x86-64 System V ABI (стандартная
архитектура Linux) структура такого размера передаётся упакованной в
один регистр — то же побитовое представление, что и у `беззнак32`.
**Реально проверено, а не только предположено** — тест подтвердил, что
это работает корректно.

**Приём для `NULL`-указателя** — SDL допускает необязательные указатели
(например, "область источника — вся текстура целиком"), а в языке нет
литерала для `NULL`. Решение: `getenv()` с заведомо несуществующим именем
переменной окружения **гарантированно** возвращает `NULL` — простой,
надёжный обходной путь без изменений в самом компиляторе.

**`нарисовать_текст`** в `графика.код` — снова обычная функция самого
языка Сфера, собирающая воедино весь путь: рендер в поверхность → создание
текстуры → запрос её размера → копия на холст в нужной позиции.

### ✅ Проверено объективно — тот же принцип, что и для прямоугольников

Не просто "не упало": нарисовал белый текст "Привет" на чёрном фоне,
прочитал цвет пикселя обратно с холста через `SDL_RenderReadPixels`.
Внутри буквы — `0xFFFFFFFF` (точно установленный белый цвет), далеко от
текста — `0x000000FF` (чёрный фон). **Кириллический текст реально
отрисован**, без искажений.

## Ввод текста с клавиатуры

**Следующий кирпичик визуальной среды** — фундамент для будущего
текстового редактора в среде разработки.

### Архитектурное решение — `SDL_TEXTINPUT`, не сырые коды клавиш

SDL2 сама разбирает раскладку клавиатуры и отдаёт **готовый UTF-8 текст**
через событие `SDL_TEXTINPUT` — не "коды клавиш", требующие
самостоятельного перевода в символы (что означало бы вручную разбираться
с раскладками, регистром, мёртвыми клавишами и так далее). Это идеально
ложится на язык, где текст везде UTF-8, а кириллица — не второстепенный
случай. Отдельно нужен `SDL_KEYDOWN` для специальных клавиш (Backspace,
Enter), которые не порождают текстовое событие вообще.

**Новый примитив** — `прочитать_текст_по_смещению(указатель, смещение) ->
текст`. Он проще, чем `прочитать_целое32`: просто **сдвигает адрес**
(без чтения памяти) — подходит для полей C-структур, которые сами
содержат готовую null-terminated строку (как поле `text` внутри
`SDL_TextInputEvent`), а не число для интерпретации.

```
если (тип_события == целое32(771)) {                        // SDL_TEXTINPUT
    текст кусочек = прочитать_текст_по_смещению(буфер_события, 12);
    накопленный_текст = накопленный_текст + кусочек;
} иначе если (тип_события == целое32(768)) {                 // SDL_KEYDOWN
    целое32 код_клавиши = прочитать_целое32(буфер_события, 20);
    если (код_клавиши == целое32(8)) { /* Backspace */ }
}
```

### ✅ Проверено симуляцией реального набора текста — с честным разбором результата

**Латиница — проверено идеально, побуквенно.** Симуляция набора "privet"
через `xdotool type` дала точное, посимвольное накопление (`p → pr → pri
→ priv → prive → privet`), корректную обработку Backspace (`privet →
prive`) и завершение по Enter.

**Кириллица — архитектурно работает, но честно ограничена возможностями
тестового инструмента.** Несколько попыток симулировать набор "привет"
через `xdotool` (с разной локалью, раскладкой, способом отправки
Unicode-кодов клавиш) каждый раз давали **частичный** результат — одна
или две буквы из шести терялись. Важная деталь: **каждая пойманная буква
всегда была правильной, не искажённой кириллической буквой** — наш код
не может исказить символ (он лишь передаёт указатель на уже готовый
UTF-8 текст, без интерпретации байтов), значит потери происходят на
уровне X11/`xdotool`, генерирующего события клавиатуры в среде без
физического экрана, а не в коде языка. Честно называю это ограничением
тестового окружения, а не тихо выдаю частичный результат за полный успех.

## Отрисовка прямоугольников и первый виджет UI — Кнопка

**Первые кирпичики визуального интерфейса**, часть более крупной цели —
построить всё, что понадобится для будущей визуальной среды разработки.

### Прямоугольники — без новой большой языковой фичи

`SDL_RenderFillRect` принимает не структуру по значению, а **указатель**
на `SDL_Rect` — значит вместо полноценной поддержки "C-совместимых
структур" в языке (большая, отдельная фича) хватило собрать структуру
**вручную в памяти**: добавлен симметричный `прочитать_целое32` примитив
— `записать_целое32(указатель, смещение, значение)`. `SDL_Rect` — это
просто четыре 32-битных целых подряд (16 байт), которые можно записать
через `выделить_память(16)` + четыре вызова `записать_целое32`.

`нарисовать_прямоугольник`/`обвести_прямоугольник` в `графика.код` —
**обычные функции самого языка Сфера** (не `внешняя функция`), строящие
удобный API поверх этого низкоуровневого примитива.

**✅ Проверено объективно** — не просто "не упало": цвет пикселя прочитан
обратно с холста через `SDL_RenderReadPixels` и совпал байт-в-байт с
установленным цветом (`0xFF0000FF` — красный, непрозрачный — внутри
прямоугольника; `0x000000FF` — чёрный фон — снаружи).

### Кнопка — структура Сфера поверх примитивов, без новых привязок к SDL2

```
структура Кнопка {
    целое32 х;
    целое32 у;
    целое32 ширина;
    целое32 высота;
    беззнак8 цвет_к;
    беззнак8 цвет_з;
    беззнак8 цвет_с;

    функция содержит_точку(целое32 точка_х, целое32 точка_у) -> верно { ... }
    функция нарисовать(текст холст) -> целое32 { ... }
}
```

Кнопка — это прямоугольник плюс логика "попадает ли точка в его границы"
— чистая арифметика самого языка, ни одной новой FFI-привязки не
понадобилось. Именно так и должны строиться более сложные элементы
интерфейса поверх низкоуровневых примитивов библиотеки.

**✅ Реально скомпилировано и запущено** — шесть проверок (клик внутри
одной кнопки, тот же клик корректно не задевает другую, клик снаружи всех
кнопок, включительная и исключительная границы прямоугольника) — все
прошли правильно.

### ✅ Попутно найдена и исправлена важная непоследовательность типов

Работа над `Кнопка` (поля `целое32`/`беззнак8` для совместимости с ABI
SDL2) сразу вскрыла: конструктор структуры и вызов метода **требовали
точного совпадения** числового типа — `Кнопка(50, 50, ...)` не
принимала обычный целочисленный литерал (типизируется как `целое`,
64-битное) для поля `целое32`. Отдельная функция
`проверить_совместимость_с_приведением` теперь разрешает неявное
приведение **между числовыми типами** (не убирая проверку вообще — текст
или структура по-прежнему не пройдут не глядя) в этих двух конкретных
местах, а кодогенерация (`сгенерировать_вызов_конструктора`,
`сгенерировать_вызов_метода`) генерирует настоящее LLVM-приведение перед
записью/передачей значения — иначе была бы паника при попытке записать
несовместимый по размеру тип в память.

⚠️ Сознательно узкий объём: это не глобальное изменение общей функции
проверки типов (используется ещё в 10 других местах языка — присваивание,
поля массива, `результат<T>`, `Список`/`Словарь` и так далее), каждое из
которых потребовало бы своей кодогенерационной правки. Пока — только
конструкторы структур и вызовы их методов.

## ✅ Закрыто: полностью кириллические имена внешних функций

**Идея пользователя, важная для самой сути проекта.** Раньше вызовы
выглядели как `SDL_Init(32)`, `malloc(64)` — латинские имена, зашитые в
уже скомпилированную библиотеку SDL2, значит просто переименовать их
физически невозможно (линковщик ищет символ **точно** с таким именем в
байтах библиотеки). Но появилась возможность **спрятать** эти имена:

```
внешняя функция инициализировать(беззнак32 флаги) -> целое32 как "SDL_Init";
```

Программист вызывает `инициализировать(32)` — полностью по-русски.
Латинское имя `"SDL_Init"` существует только в этой одной строке
объявления, которую пишет автор привязки (`графика.код`), а не тот, кто
её использует в своей игре.

**`графика.код` полностью переписан** — все функции (`инициализировать`,
`создать_окно`, `создать_холст`, `задать_цвет`, `опросить_событие`,
`выделить_память` и так далее) теперь имеют кириллические имена. Ни
одной латинской буквы в коде, который пишет пользователь библиотеки.

**✅ Реально скомпилировано и запущено дважды** — сначала изолированный
тест (`SDL_Init`/`SDL_Quit`/`sqrt` через русские имена), затем **полная
перезапись** `тест_клики.код` на новые имена с **повторной** проверкой
через симуляцию реального клика мыши (`xdotool`) — координаты снова
совпали точно с тем, что было послано.

### Архитектура

Потребовалось новое ключевое слово `как` и новое поле в AST
(`ОбъявлениеВнешнейФункции.реальное_имя`). Кодогенерация объявляет
LLVM-функцию под РЕАЛЬНЫМ именем (обязательное требование линковщика), но
при ОБЫЧНОМ вызове функции по русскому имени ищет её через новую таблицу
алиасов — тот же принцип fallback-таблицы, что уже отработан для
пространств имён v2 (манглированные имена функций из модулей).

## `кликер.код` — первая настоящая программа на языке, не изолированный тест

**Идея пользователя, оказавшаяся исключительно ценной.** До этого момента
язык проверялся только заранее продуманными тестовыми файлами — каждый
целенаправленно проверял одну конкретную возможность. Реальная программа
— текстовый кликер с магазином улучшений и сохранением прогресса между
запусками — заставила несколько возможностей работать **вместе**, в
комбинациях, которые изолированные тесты никогда не создавали, и почти
сразу вскрыла то, что оставалось незамеченным.

**Что делает игра:** очки, начисление за клик, магазин с тремя
улучшениями (структуры), покупка за очки с реальным эффектом на экономику
игры, интерактивный цикл через `прочитать_строку()`, сохранение и загрузка
прогресса в файл между разными запусками программы.

**✅ Реально протестировано полным циклом** — не только компиляция:
сыграна партия, куплено улучшение, программа завершена (с автосохранением),
**запущена заново как отдельный процесс**, прогресс корректно загружен и
подтверждён статистикой.

### Три реальных находки, которые дала именно эта программа

**1. `прочитать_строку()` никогда не обрезала завершающий перевод строки.**
`fgets` (стандартное, документированное поведение самой функции в C) не
убирает `\n` из буфера — значит любое сравнение введённого текста с
ожидаемым значением (`если (команда == "к")`) было заведомо неверным.
Раньше существовавший тест (`тест_ввода.код`) никогда не ловил проблему,
поскольку только **выводил** введённую строку обратно, не **сравнивал**
её ни с чем.

**2. `прочитать_строку()` открывала новый поток при каждом вызове.**
Внутри цикла ввода это означало, что вторая и последующие команды
никогда не читались — библиотека C буферизует чтение внутри структуры
`FILE*`, а создание нового потока каждый раз теряло уже прочитанные, но
не потреблённые байты. Исправлено через глобальную переменную-одиночку
(поток создаётся один раз, при первом вызове, и переиспользуется —
та же техника, что уже применена для `argc`/`argv`).

**3. Не было способа разбить текст на части** — критичный пробел для
любой сериализации (сохранение записи в файл требует превратить данные в
текст и распарсить обратно). Добавлена `подстрока(текст, начало, длина)
-> результат<текст>` — с этим сразу же поймали **третью, самую серьёзную**
находку:

### Настоящий сегфолт компилятора — и как он был пойман

Первая попытка использовать `подстрока()` уронила сам компилятор
(`sfera`) с segmentation fault — не ошибка в программе пользователя, а
крах инструмента. Через `gdb` (`gdb -batch -ex run -ex bt`) стек вызовов
указал на `LLVMTargetMachineEmit` — генерацию машинного кода, а не
построение IR. Причина: `build_alloca` была размещена **после** того, как
текущий блок уже завершился `build_conditional_branch` — инструкция
после терминатора в одном базовом блоке, невалидный LLVM IR, который не
ловится на этапе построения, только при попытке реально сгенерировать
код. Перемещение `alloca` перед ветвлением решило проблему полностью.

### Ценность подхода

Все три находки — то, что абстрактные, заранее написанные тесты почти
наверняка не поймали бы: они проверяют то, что автор теста уже
предполагал проверить, а реальная программа находит то, что никто не
предполагал заранее. `кликер.код` теперь служит и постоянным
регрессионным тестом (полный интерактивный цикл + сохранение/загрузка),
и примером для тех, кто впервые открывает исходники языка — готовый,
рабочий образец структуры, синтаксиса, идиом.

## Языковой сервер: "перейти к определению"

**Новое — реализовано меньшим объёмом работы, чем ожидалось.** Раньше эта
возможность откладывалась как требующая "добавить позиции в AST" —
крупная, инвазивная задача. Проверка показала: **лексер уже отслеживал
позицию каждого токена** (не только для сообщений об ошибках) — просто
парсер её не сохранял в AST. Понадобилось: добавить поле `позиция:
Option<(usize, usize)>` в объявления функций и структур, захватить уже
готовую `self.текущая_позиция()` в двух местах парсера, и реализовать
обработчик `textDocument/definition` в языковом сервере, переиспользуя ту
же логику "слово под курсором", что уже была у hover.

**✅ Реально проверено настоящими JSON-RPC запросами** — курсор на вызове
функции корректно ведёт к строке и столбцу её объявления.

**Приятная деталь:** для мономорфизированных методов обобщённых структур
(`Коробка<целое>.получить()`) переход ведёт не в "никуда" (синтетический,
машинно сгенерированный код), а к **исходному, написанному пользователем**
методу в шаблоне — передаётся позиция шаблона, а не `None`.

**Побочная находка:** LSP-сервер не обновлялся вслед за двумя более
ранними изменениями компилятора — сигнатурой `проверить_программу`
(пространства имён) и новым вариантом `ВерхнийУзел::Контракт` — оба
привели бы к ошибке компиляции при следующей же попытке собрать LSP-сервер
отдельно. Исправлено заодно.

### ⚠️ Честные ограничения этой версии

- Только функции, структуры и методы — не контракты (у `ОбъявлениеКонтракта`
  пока нет поля `позиция`) и не переменные (у них нет одного "места
  объявления" — могут быть переприсвоены много раз).
- Подсказки параметров при вызове (signature help) всё ещё не реализованы.

## Контракты (интерфейсы) — v1 (проверка), плюс настоящий полиморфизм (см. ниже)

**Новое — было в грамматике с самого начала, но не реализовано.**
`Token::Контракт` существовал в лексере с первой сессии, но парсер нигде
его не использовал — если бы пользователь написал `контракт Имя { ... }`,
компилятор упал бы с ошибкой "неожиданный токен".

```
контракт Печатаемый {
    функция напечатать() -> текст;
}

структура Животное : Печатаемый {
    текст имя;

    функция напечатать() -> текст {
        вернуть это.имя;
    }
}
```

Компилятор проверяет на этапе компиляции, что структура, заявляющая
`: Печатаемый`, реально имеет метод `напечатать` с **совпадающей**
сигнатурой (параметры и тип возврата) — не просто с таким именем.

**Понятная диагностика при несоответствии:**
```
структура 'Пользователь' заявляет реализацию контракта 'Печатаемый', но не
имеет метода 'напечатать', требуемого этим контрактом
```
```
структура 'Пользователь', метод 'напечатать': тип возврата не совпадает с
требованием контракта 'Печатаемый' (контракт ожидает Some(Текст), у
метода — Some(Целое))
```

**✅ Реально скомпилировано и запущено мной** — включая все три сценария:
правильную реализацию (работает), отсутствующий метод (понятная ошибка),
несовпадающую сигнатуру (понятная ошибка). Заодно полный регрессионный
прогон `привет.код` — никаких сюрпризов.

### Архитектурная особенность v1 — на момент этой версии кодогенерация не была тронута

Это был сознательно узкий v1: **только** проверка соответствия на этапе
компиляции, без полиморфизма — на тот момент. Нельзя было ещё написать
функцию, принимающую "любую структуру, реализующую контракт X" — это
требовало динамического диспетчинга (vtable), отдельного, более
крупного следующего шага. Ценность v1 была самодостаточна и без этого:
компилятор ловил забытые методы или неправильные сигнатуры **до**
запуска программы. **Этот шаг сделан** — см. отдельный раздел ниже,
где то же самое ограничение закрыто по-настоящему.

### ✅ Закрыто позже: настоящий полиморфизм через контракты (динамический диспетчинг)

**Прямое продолжение — реализовано в следующей сессии.** Именно тот
"отдельный, более крупный следующий шаг", о котором честно предупреждал
раздел выше. Теперь работает по-настоящему:

```
контракт Печатаемый {
    функция напечатать() -> текст;
}

структура Кот : Печатаемый {
    функция напечатать() -> текст { вернуть "Мяу"; }
}

структура Собака : Печатаемый {
    функция напечатать() -> текст { вернуть "Гав"; }
}

функция озвучить(Печатаемый существо) -> целое {
    вывести(существо.напечатать());
    вернуть 0;
}

функция главная() -> целое {
    озвучить(Кот());     // выведет "Мяу"
    озвучить(Собака());  // выведет "Гав" — та же функция, другая реализация
    вернуть 0;
}
```

**Архитектура — классический "толстый указатель"** (тот же подход, что
у `dyn Trait` в Rust или виртуальных функций в C++): переменная/параметр
типа-контракта представлена в памяти как пара указателей — на сами
данные структуры и на **vtable** (таблицу виртуальных методов, массив
указателей на функции, сгенерированный один раз для каждой пары
"структура + контракт", в порядке объявления методов в контракте).
Вызов метода через контракт — не прямой вызов конкретной функции, а
чтение нужного указателя из vtable по известному индексу и косвенный
вызов через него.

**⚠️ Четыре отдельные, реальные находки по пути — контракт и структура
синтаксически неразличимы** (оба — просто идентификатор с заглавной
буквы), различать приходится по факту регистрации в списке контрактов,
и это пришлось чинить **в каждом месте компилятора отдельно**, где
встречается имя пользовательского типа:
1. `тип_в_llvm` — LLVM-тип параметра/переменной с именем контракта
   ошибочно искал обычную структуру и падал.
2. `объявить_переменную` (путь для `Тип имя = значение;` с явным типом)
   вообще не знал про упаковку толстого указателя.
3. **Порядок инициализации**: список известных контрактов
   (`контракты_методы`) заполнялся *после* регистрации сигнатур всех
   функций — значит тип параметра-контракта первой же функции не
   распознавался. Исправлено перестановкой на самый первый шаг.
4. `дополнительная_информация_из_ast_типа` — параметр функции с типом
   контракта регистрировался как обычная структура, из-за чего вызов
   метода на нём пытался найти статическую (не через vtable) реализацию
   и падал с "метод не найден".

**⚠️ Пятая, самая серьёзная находка — настоящий segfault, не просто
ошибка компиляции**: `озвучить(Кот())` компилировался, но падал в
рантайме. `gdb` показал точное место — внутри `озвучить`. Причина:
упаковка в толстый указатель была реализована для объявления переменной,
но **не для передачи структуры аргументом функции** — вызывающий код
передавал обычный, "тонкий" указатель (8 байт) туда, где функция
ожидала толстый указатель (16 байт, данные + vtable). Внутри функции
чтение vtable из этого рассинхронизированного значения читало мусор,
косвенный вызов уходил по случайному адресу. Исправлено — заведена
отдельная карта "имя функции → типы её параметров" (нужна, поскольку
LLVM-тип толстого указателя одинаков для *любого* контракта — по нему
одному не узнать, какая именно vtable нужна), логика упаковки вынесена
в переиспользуемую функцию и применена при генерации обычного вызова.

**✅ Проверено объективно, тем же способом, что и вся остальная работа**:
два отдельных теста (одна структура; две структуры разного типа через
общую функцию) — оба выводят правильный, разный текст для разных
структур. `valgrind` на обоих — `0 errors`, полное отсутствие утечек и
ошибок памяти. Отдельно подтверждена регрессия — `привет.код`
компилируется и работает как раньше.

### ⚠️ Честные ограничения этой версии

- **`Список<Контракт>`** — коллекция из объектов разных структур,
  объединённых общим контрактом (самый "хрестоматийный" пример
  применения полиморфизма) — не проверялась, `Список<T>` пока не
  тестировался с T = тип-контракт.
- **Контракт как тип возврата функции** — не реализовано (только
  параметры и локальные переменные).
- **Контракты нельзя квалифицировать через модуль** (`модуль.Контракт`) —
  используются только по простому имени, как и структуры в v1
  пространств имён.

## ARC: исправлена утечка при досрочном выходе через `?`

**Закрыт долго задокументированный пробел.** Раньше структуры, объявленные
ДО `?` в функции, возвращающей `результат<тип>`, НЕ освобождались при
досрочном выходе через ошибку — не крах, а утечка памяти (программа
"работала" всё это время, просто копила мусор при каждом таком выходе).

```
функция что_то() -> результат<целое> {
    Пользователь юзер = Пользователь("Аня", 30, "секрет456");
    целое х = разделить(10, 0)?;   // ошибка -> досрочный выход
    вернуть успех(х + юзер.возраст);
    // "юзер" теперь корректно освобождается при этом досрочном выходе
}
```

**Исправление** — один вызов уже существующей функции `освободить_при_возврате`
(той же, что используется для обычного `вернуть`) перед досрочным
`build_return` в кодогенерации `?`.

### ✅ Проверено не просто "программа не падает" — реальным анализатором утечек

Использовал `valgrind --leak-check=full` для объективного, независимого
подтверждения — не полагаясь только на то, что программа завершилась без
ошибки:

- **С исправлением**: `0 bytes lost, 2 allocs, 2 frees` — идеальный баланс.
- **Без исправления** (временно откатил специально для контраста):
  `24 bytes definitely lost` — чётко видимая, конкретная утечка на
  функции с ARC-структурой перед `?`.

### ⚠️ Честно про то, что НЕ покрыто этим исправлением

Прогон `valgrind` на **всём** `привет.код` целиком по-прежнему показывает
утечки (порядка 750 байт) — но это **другая, отдельная, давно известная**
категория, не связанная с этим исправлением: **текст в языке не находится
под управлением ARC**. Каждый вызов текстовых функций стандартной
библиотеки (`регистр_в_верхний`, `целое_в_текст`, конкатенация текста
через `+` и так далее) создаёт `malloc`-буфер, который не отслеживается
никаким счётчиком ссылок — эти буферы никогда не освобождаются. Мы
документировали это ограничение с самого начала работы над стандартной
библиотекой строк — оно остаётся честно названным, отдельным следующим
шагом (потребовал бы либо оборачивать текст в ARC-совместимую структуру,
либо другой механизм управления временными буферами), не тем, что
чинилось сегодня.

## Смена регистра для кириллицы — `регистр_в_верхний`/`регистр_в_нижний`

**Новое, ранее сознательно отложенное из-за сложности.** Стандартные
`toupper`/`tolower` из libc корректно работают только с латиницей — для
языка с кириллическими идентификаторами и текстом это было бы почти
бесполезно. Теперь есть `регистр_в_верхний(текст) -> текст` и
`регистр_в_нижний(текст) -> текст`, корректно работающие с кириллицей.

```
вывести(регистр_в_верхний("привет"));           // ПРИВЕТ
вывести(регистр_в_нижний("ПРИВЕТ, Sfera! 123")); // привет, sfera! 123
```

### Почему это было по-настоящему сложно

Строчные кириллические буквы (U+0430–U+044F) в UTF-8 **пересекают границу**
между двумя ведущими байтами: `а`–`п` кодируются как `0xD0 [0xB0-0xBF]`, а
`р`–`я` — уже как `0xD1 [0x80-0x8F]` (**другой ведущий байт**!). Значит
смена регистра иногда меняет **оба** байта пары, не только один — это не
простая арифметика "прибавить константу ко всем байтам", как для латиницы.
Плюс отдельный, вне общего диапазона случай — `Ё` (`0xD0 0x81`) / `ё`
(`0xD1 0x91`).

**Архитектурное решение, снизившее риск:** вычисление новых байтов
реализовано **полностью через `build_select`-цепочки**, без ветвления
базовых блоков для самой арифметики (ветвление есть только для "это
кириллица (2 байта) или нет (1 байт)" на уровне цикла) — самый частый
источник ошибок в ручной генерации LLVM IR в этом проекте был именно в
контроле потока (пропущенные/перепутанные переходы между блоками), а
`select`-цепочки этот риск полностью убирают для самой сложной части.

**Безопасность для остального Unicode:** байты `0xD0`/`0xD1` физически не
могут быть "продолжающими" байтами внутри чужой многобайтовой
последовательности (те всегда имеют вид `10xxxxxx`, а `0xD0`/`0xD1` — это
`1101xxxx`, ведущий байт). Значит алгоритм "увидел `0xD0`/`0xD1` — обработай
как кириллицу, иначе — скопируй байт как есть" безопасен для **любого**
валидного UTF-8 (других алфавитов, эмодзи, чего угодно) — такие символы
просто не меняются (не их задача), но и не повреждаются.

**✅ Реально скомпилировано и запущено мной** — включая самые рискованные
случаи: переход через границу `п`/`р`, `Ё`/`ё`, полный алфавит туда и
обратно, и смешанный текст (кириллица + латиница + цифры + знаки
препинания одновременно) — каждый символ оказался на своём месте.

### ⚠️ Честные ограничения

- Символы за пределами ASCII и основной кириллицы (другие алфавиты,
  эмодзи) не меняют регистр (не их задача) — задокументированное,
  осознанное ограничение объёма, не забытый случай.
- Работает побайтово — не учитывает языковые особенности регистра для
  других кириллических языков (украинский, белорусский и т.д. используют
  дополнительные буквы вне базового диапазона А-Я/а-я) — только
  современный русский алфавит плюс Ё/ё.

## Пространства имён между модулями (v1 + v2 — теперь с разрешением коллизий)

**До этой версии** все подключённые файлы делили одно общее, плоское
пространство имён — единственной защитой от конфликтов было обнаружение
дубликатов (ошибка компиляции, если два файла объявляют функцию с
одинаковым именем). **Теперь коллизии разрешены** — два модуля могут
объявить функцию с одинаковым именем, разрешая неоднозначность через
явную квалификацию:

```
подключить модуль_а;   // тоже объявляет функцию "помощь()"
подключить модуль_б;   // тоже объявляет функцию "помощь()"

функция главная() -> целое {
    // Раньше (v1) это была бы ошибка компиляции при регистрации.
    // Теперь — коллизия разрешена, доступ строго через квалификацию.
    вывести(модуль_а.помощь());   // 1
    вывести(модуль_б.помощь());   // 2
    вернуть 0;
}
```

Для **уникальных** (не коллизирующих) имён по-прежнему работают оба
способа сразу:

```
подключить утилиты;

функция главная() -> целое {
    целое а = удвоить(21);            // обычный, неквалифицированный
    целое б = утилиты.удвоить(21);    // квалифицированный, через имя модуля
    вернуть 0;
}
```

**Имя модуля** — это имя подключённого файла без расширения `.код`
(например, `утилиты` для `утилиты.код`).

**Готовый пример коллизии в проекте** — `модуль_а.код`, `модуль_б.код`,
`тест_коллизия.код` — можно собрать и запустить напрямую, увидеть работу
этой фичи без необходимости писать свой тест.

### Архитектура — единообразное манглирование имён

**v1 находка, упростившая старт:** синтаксис `модуль.функция(...)`
синтаксически **неотличим** от вызова метода на переменной — парсер
разбирает оба случая совершенно одинаково. Парсер трогать не пришлось
вообще — вся работа в семантике и кодогенерации.

**v2 потребовала гораздо большего:** LLVM физически не позволяет двум
функциям в одном модуле иметь одинаковое имя. Значит функции из
подключённых файлов теперь **всегда** получают манглированное LLVM-имя
(`модуль__имя`) — единообразно, для ВСЕХ функций из модулей, не только
коллизирующих (тот же принцип, что уже применён для мономорфизации
обобщённых структур: проще и безопаснее, чем манглировать "только при
необходимости" через условную логику). Это потребовало правки самого
частого пути в кодогенераторе — генерации обычного вызова функции, с
осторожным тестированием на каждом шаге, чтобы не сломать уже работающий
код (включая полный регрессионный прогон `привет.код` и уже существующего
`тест_подключения.код`).

**Приоритет переменных, затем главного файла, затем однозначных модулей:**
если переменная и модуль называются одинаково, переменная имеет приоритет.
Если имя объявлено и в главном файле, и в подключённом модуле — главный
файл имеет приоритет для неквалифицированного доступа (то же правило,
что и в большинстве языков программирования: локальное важнее внешнего).

### Понятная диагностика неоднозначности

Попытка вызвать коллизирующее имя **без** квалификации не проваливается с
неинформативным "функция не объявлена" — вместо этого:

```
имя 'помощь' неоднозначно — объявлено в нескольких модулях (модуль_а, модуль_б) —
используй квалифицированный вызов: модуль_а.помощь(...) или модуль_б.помощь(...)
```

**✅ Реально скомпилировано и запущено мной** — включая специальный тест
на коллизию (две функции с одинаковым именем в разных модулях, обе
вызываются квалифицированно и дают ожидаемые, разные результаты),
проверку понятной ошибки при неквалифицированной попытке, и полный
регрессионный прогон (`привет.код` целиком + `тест_подключения.код`) —
никаких сюрпризов в уже работавшей функциональности.

### ⚠️ Честные ограничения текущей версии

- **Квалификация работает только для функций**, не для структур (типов) —
  `утилиты.Точка` как тип пока не поддержан.
- **Объявления главного (входного) файла нельзя квалифицировать** — только
  подключённые через `подключить` файлы получают имя модуля.
- **Коллизии между структурами** (не функциями) между модулями по-прежнему
  запрещены — v2 затронула только свободные функции, структуры остаются
  на модели v1 (осознанное сужение объёма, не забытый случай — структуры
  сложнее из-за методов, полей и конструкторов, требующих отдельной
  проработки манглирования).

## Настоящие пользовательские обобщённые структуры (generics)

**Реализовано с нуля — от парсера до реального выполнения.** До этой
версии пользователь мог использовать только ВСТРОЕННЫЕ обобщённые типы
(`Список<тип>`, `Словарь<Ключ, Значение>`) — написать свою обобщённую
структуру было нельзя. Теперь можно, включая методы:

```
структура Коробка<тип> {
    тип значение;

    функция получить() -> тип {
        вернуть это.значение;
    }

    функция установить(тип новое_значение) {
        это.значение = новое_значение;
    }
}

функция главная() -> целое {
    коробка = Коробка<целое>(42);
    вывести(коробка.получить());       // 42
    коробка.установить(100);
    вывести(коробка.получить());       // 100

    текстовая = Коробка<текст>("Привет!");
    вывести(текстовая.получить());     // Привет!
    вернуть 0;
}
```

**Архитектура — мономорфизация.** Для каждого реально использованного
сочетания (`Коробка<целое>`, `Коробка<текст>`) компилятор генерирует
ОТДЕЛЬНУЮ, полноценную LLVM-структуру и ОТДЕЛЬНЫЕ, полноценные LLVM-функции
для каждого метода, с манглированными именами (`Коробка__целое`,
`Коробка__текст`) — они совершенно не связаны друг с другом на уровне
машинного кода, просто происходят из одного текстового шаблона.

**Как это устроено внутри:**
- Парсер уже умел разбирать *использование* обобщённого типа (`Коробка<целое>`,
  `Коробка<целое>(5)`) для ЛЮБОГО имени, не только `Список`/`Словарь` —
  обнаружилось, что эта часть была готова с самого начала. Понадобилось
  научить его только *объявлению* — `структура Коробка<тип> { ... }`.
- Семантика хранит обобщённые структуры как ШАБЛОНЫ (AST с "тип" как
  placeholder), отдельно от обычных, уже готовых структур.
- При первой встрече конкретной инстанциации — функция `подставить_тип`
  рекурсивно заменяет placeholder на конкретный тип в полях, а функции
  `подставить_тип_в_блок/оператор/выражение` — рекурсивно во ВСЕХ телах
  методов (включая вложенные `если`/`пока`, объявления локальных
  переменных, и даже типовые параметры вложенных вызовов вроде
  `Список<тип>()` внутри метода). Результат регистрируется в ТЕХ ЖЕ
  таблицах, что и обычные структуры/методы, под манглированным именем —
  это позволило переиспользовать почти всю уже существующую
  инфраструктуру (доступ к полям, вызов методов, кодогенерацию) почти без
  изменений.

**⚠️ Найденный и исправленный архитектурный баг (порядок присваиваний).**
Семантика хранит "решения" о том, является ли `имя = значение;` новым
объявлением или присваиванием существующей переменной — список,
считываемый кодогенератором СТРОГО по порядку встречи операторов. Но
проверка методов обобщённой структуры (побочный эффект внутри вычисления
типа конструктора) могла добавлять свои решения в этот список РАНЬШЕ, чем
"внешний" оператор — хотя кодогенератор встречает внешний оператор
РАНЬШЕ (методы генерируются отдельным, последующим проходом). Решение —
изолировать решения присваиваний каждой инстанциации в отдельный список,
не смешивая с общим потоком программы.

**⚠️ Два найденных и исправленных бага, НЕ связанных с generics.** Работа
над методами обобщённых структур попутно вскрыла два самостоятельных
пробела, воспроизводившихся и для обычных, необобщённых структур —
просто мы никогда раньше не тестировали именно эти случаи:
- `это.поле = значение;` (сеттер внутри метода) никогда не поддерживался
  парсером вообще — `это` не распознавалось как возможное начало
  присваивания, только обычные идентификаторы.
- Вызов `void`-метода (без `-> тип`) КАК САМОСТОЯТЕЛЬНОГО ОПЕРАТОРА
  (ради побочного эффекта, не результата — самый обычный паттерн ООП,
  сеттеры) падал с ошибкой "не возвращает значение, но использован как
  выражение".

**✅ Реально скомпилировано и запущено мной** — не только написано.
Собрал компилятор локально, скомпилировал и ЗАПУСТИЛ тестовую программу с
обобщённой структурой, включая ДВЕ разные инстанциации одновременно и
вызовы методов (в т.ч. `void`-метод как самостоятельный оператор) —
работает корректно. Заодно перепрогнал весь `привет.код` целиком —
никаких регрессий в уже работавшей функциональности.

### ⚠️ Честные ограничения этой версии (v1)

- **Только ОДИН параметр типа на структуру.** `структура Коробка<тип>` —
  да, `структура Словарь<Ключ, Значение>` в пользовательском коде — нет
  (получишь понятную ошибку компиляции, не крах). Многопараметрические
  пользовательские generics — следующий, отдельный шаг.
- **Нет явного типа при объявлении переменной.** `коробка = Коробка<целое>(42);`
  работает (тип выводится из вызова конструктора справа), а
  `Коробка<целое> коробка = Коробка<целое>(42);` — пока нет (явное
  указание обобщённого пользовательского типа слева требует отдельного
  пути обработки, не связанного с вызовом конструктора).
- **Манглирование имён через `__`** (двойное подчёркивание) — в теории,
  если пользователь сам назовёт обычную структуру с таким же именем, как
  манглированное (например, структуру буквально назвать `Коробка__целое`),
  возможна коллизия. Крайне маловероятный случай, но честно обозначенный,
  не скрытый.
- **Нет проверки ограничений типа** (`структура Коробка<тип: Контракт>`) —
  контракты в языке вообще пока не реализованы семантическим анализатором
  (независимо от generics).

## Языковой сервер (LSP) для VS Code — диагностика, автодополнение, подсказки

**Новое, самое крупное дополнение к инструментам разработки** — после
подсветки синтаксиса (расширение `sfera-vscode`) теперь есть настоящий
языковой сервер: красные подчёркивания ошибок, автодополнение и подсказки
при наведении прямо в редакторе, использующие тот же лексер/парсер/
семантический анализатор, что и сам компилятор.

**Архитектура**: проект состоит из ДВУХ бинарных целей Cargo — основной
компилятор (`src/main.rs`) и языковой сервер (`src/bin/сфера_lsp.rs`),
плюс библиотечная цель (`src/lib.rs`), переиспользуемая языковым сервером.
Библиотека содержит фронтенд (лексер, парсер, семантику) — БЕЗ
кодогенерации, а значит без зависимости от `inkwell`/LLVM: серверу не
нужно реально компилировать код, только проверять его.

`main.rs` НЕ использует эту библиотеку — у него свои собственные `mod`
объявления на те же файлы (компилируются дважды: для библиотеки и для
`main.rs`) — намеренно, чтобы не рисковать уже работающим компилятором.

Реализовано через уже зрелые крейты `lsp-server` + `lsp-types` (та же
связка, что использует `rust-analyzer`), а не самописный JSON-RPC.

**⚠️ Техническая находка, пойманная только благодаря реальной сборке**:
имена МОДУЛЕЙ на кириллице (в отличие от обычных идентификаторов —
переменных/функций, которые работают без проблем везде в проекте) не
разрешаются Rust автоматически через стандартную конвенцию "имя модуля →
имя файла" — `mod подсказки;` не находит `подсказки.rs` сам по себе,
нужен явный `#[path = "подсказки.rs"] mod подсказки;`. Не нашёл бы это
без попытки реальной компиляции.

### Что реализовано

**Диагностика ошибок в реальном времени** — при открытии/изменении
`.код`-файла сервер прогоняет лексер → парсер → семантику, находит первую
ошибку (если есть) и отправляет её редактору. Очищает диагностики при
закрытии файла.

**Автодополнение (`textDocument/completion`)** — два источника разом:
- **Статический список** (`src/подсказки.rs`) — все ключевые слова,
  встроенные типы, все функции стандартной библиотеки, с описанием и
  сигнатурой для каждой.
- **Динамический список** — функции и структуры, объявленные В ТЕКУЩЕМ
  ОТКРЫТОМ ФАЙЛЕ, с точной сигнатурой (типы параметров, тип возврата),
  собираются заново при каждом изменении файла.

**Подсказки при наведении (`textDocument/hover`)** — наведи курсор на имя
функции, метода, структуры или ключевого слова — увидишь сигнатуру/поля/
описание. Слово под курсором ищется ТЕКСТОВЫМ способом (простой поиск
границ идентификатора в сыром тексте документа), не через AST — см.
следующий раздел про то, почему.

**"Перейти к определению" (`textDocument/definition`)** — теперь тоже
реализовано (см. отдельный, подробный раздел выше). Оказалось, что нужная
инфраструктура (позиция каждого токена) уже существовала в лексере —
просто не сохранялась в AST. Понадобилось добавить одно новое поле в
объявления функций/структур и захватить уже готовую позицию в двух местах
парсера — заметно меньше работы, чем предполагалось изначально.

### Что НЕ реализовано, и почему именно это

**Подсказки параметров при вызове (signature help)** — в отличие от
"перейти к определению" (которому хватило позиций деклараций), эта
возможность требует знать, "где именно находится курсор ВНУТРИ вызова
функции" (какой по счёту аргумент сейчас вводится) — то есть позиции
нужны не только для деклараций, а для самих ВЫЗОВОВ, вложенных в
произвольные выражения. Это более широкая, самостоятельная задача —
сознательно отложена как честно названный следующий шаг, а не тихо
пропущена.

**Автодополнение переменных из текущей функции** — тоже отложено: заявка
"что видно в этой конкретной точке курсора" требует отслеживания области
видимости, которое стоило бы делать отдельно и тщательно, не мимоходом.

### ⚠️ Известные ограничения

- **Многофайловые проекты не поддержаны корректно.** Логика разрешения
  `подключить` живёт в `main.rs`, не в переиспользуемой библиотеке —
  диагностика и автодополнение видят ТОЛЬКО открытый файл изолированно.
- **Семантические ошибки — без точной позиции.** `ОшибкаСемантики`
  содержит только текст сообщения — такие диагностики привязываются к
  первой строке файла с пометкой `[без точной позиции]`.
- **Только первая найденная ошибка** — лексер/парсер/семантика
  останавливаются на первой ошибке, не накапливают список.

### ✅ Эта версия ДЕЙСТВИТЕЛЬНО проверена — не только скомпилирована

В отличие от первой версии сервера (только диагностика, отправленная без
возможности собрать), эта версия **реально собрана и протестирована**:
Rust и LLVM 18 установлены и настроены локально (доступны через стандартные
системные репозитории Ubuntu — `rustc`/`cargo`/`llvm-18-dev`/`clang`), весь
проект собран (`cargo build`), и сам языковой сервер проверен через
настоящие JSON-RPC запросы (`initialize`, `textDocument/didOpen`,
`textDocument/hover`, `textDocument/completion`) — подтверждено, что
сервер отвечает корректно и не падает на последовательности запросов.
Заодно пересобран и заново прогнан весь `привет.код` целиком — результат
идентичен уже проверенному ранее, значит новый код не задел сам компилятор.

**Как собрать и подключить** — см. `sfera-vscode/README.md`.

## Сборка библиотек (`--библиотека`) — первый шаг к системе пакетов

Раньше компилятор ВСЕГДА требовал функцию `главная` — любой `.код`-файл
обязан был быть самостоятельной программой. Теперь можно собрать файл как
**библиотеку** — код, предназначенный для подключения в другой проект, а
не для самостоятельного запуска:

```bash
cargo run -- утилиты.код --библиотека
```

В библиотечном режиме компилятор:
- НЕ требует функцию `главная` (её отсутствие — это нормально, не ошибка)
- НЕ генерирует обёртку `main` — библиотеке не нужна точка входа
- НЕ линкует результат в исполняемый файл и не запускает его — итоговый
  артефакт останавливается на объектном файле (`.o`)

**Честно про масштаб этого шага**: это не полноценная система пакетов —
просто первая, самая необходимая предпосылка для неё (различие между "это
программа" и "это код, который встраивается в чужой проект"). Готовый
`.o`-файл пока нужно линковать в другой проект ВРУЧНУЮ (например, передав
его тем же `clang` вместе с объектным файлом основной программы) —
автоматического способа "подключить готовую библиотеку" из `.код`-кода
пока нет; `подключить` по-прежнему работает только с исходным `.код`-текстом
(см. раздел про многофайловую сборку выше), не с уже скомпилированными
артефактами.

### Установка как отдельной команды

Чтобы вызывать компилятор как обычную команду из любой папки (а не через
`cargo run --`), собери release-версию и положи бинарник в PATH:

```bash
cargo build --release
sudo cp target/release/sfera /usr/local/bin/запустить
```

После этого из любой директории:
```bash
запустить мой_файл.код
```

**Важно понимать:** `запустить` после этого — НЕ обёртка над `cargo`, а
настоящий, самостоятельный нативный бинарник. `cargo` нужен только для
ПЕРЕСБОРКИ компилятора после изменения его исходников (`.rs`-файлов) — то
есть только пока сам компилятор активно дорабатывается. Обычной программе
на "Сфере" `cargo` вообще не нужен ни для компиляции, ни для запуска.

**Удобство на время активной разработки компилятора**: в проекте есть
скрипт `собрать.sh`, объединяющий оба шага выше в один:
```bash
./собрать.sh
```
Это не отдельная возможность языка, просто маленькое удобство, пока мы
продолжаем менять исходники самого компилятора каждую сессию.

## Архитектура сборки: теперь через настоящий LLVM API, не через clang-компиляцию

**Изменилось:** раньше `clang` делал две вещи — компилировал текстовый `.ll`
в машинный код И линковал результат в исполняемый файл. Теперь **компиляция
идёт напрямую через LLVM API** (`TargetMachine`, вызывается из
`codegen.rs::записать_объектный_файл`) — это уже НАСТОЯЩАЯ часть нашего
компилятора, не внешний инструмент. `clang` остался только для
**финальной линковки** уже готового объектного (`.o`) файла с системными
библиотеками (`libc`, откуда `printf`/`malloc`/`free`).

**Почему полностью убрать clang пока не вышло:** линковка — платформенно-
специфичная задача (нужно точно знать, как связать объектный код с системными
библиотеками именно на macOS/Linux). У LLVM есть свой линковщик (`lld`), но
подключить его напрямую из нашего кода потребовало бы сырых FFI-биндингов —
`inkwell` не даёт готовой обёртки для этого. Это отдельный, больший будущий
шаг; пока `clang` — самый практичный способ получить готовый линковщик.

**Что это даёт практически:** теперь можно проверить, каждый ли этап
компиляции — наш, а не "спрятан" во внешнем `clang`. Если что-то не так
именно с генерацией машинного кода (не с линковкой) — ошибка будет видна
уже на этапе `записать_объектный_файл`, а не где-то внутри чёрного ящика
`clang -O2 file.ll`.

## ⚠️ Новый непроверенный код: компиляция через TargetMachine

Использованная схема (`Target::initialize_native` → `TargetMachine::get_default_triple`
→ `create_target_machine` → `write_to_file`) — это широко задокументированный,
стандартный паттерн `inkwell` (встречается почти в любом туториале по
написанию компилятора на его основе), поэтому риск здесь **ниже**, чем у
многих других частей этого компилятора. Тем не менее, не проверено
локальной сборкой. Если возникнет ошибка именно здесь — скорее всего,
в точной сигнатуре `create_target_machine` (порядок/типы параметров могут
чуть отличаться между версиями `inkwell`).

## Требование: clang должен быть в PATH (теперь только для линковки)

Финальный шаг конвейера — линковка уже готового `.o` файла в исполняемый —
делается через вызов внешней команды `clang`, она обычно устанавливается
вместе с LLVM (см. шаги установки выше). Проверить:

```bash
clang --version
```

Если команда не найдена, но LLVM установлен — возможно, нужно явно
добавить путь к `clang` в PATH (например, `$(brew --prefix llvm@18)/bin`
на macOS).

## Частые проблемы при первой сборке

**`error: unable to find libclang` / `LLVM_SYS_180_PREFIX not set`**
Переменная окружения не прописана или указывает не туда. Перепроверь путь
командой `brew --prefix llvm@18` (macOS) и убедись, что переменная
экспортирована именно в той сессии терминала, где запускаешь `cargo`.

**Долгая первая сборка (5-15 минут)**
Нормально — `inkwell`/`llvm-sys` при первой сборке генерируют Rust-обвязки
поверх C++ API LLVM, это тяжёлый процесс. Последующие сборки быстрее
благодаря кэшу `cargo`.

**Ошибка компиляции с сообщением про несовместимую версию LLVM**
Убедись, что `features = ["llvm18-0"]` в `Cargo.toml` совпадает с
установленной версией LLVM. Если у тебя стоит другая версия (например 17) —
поменяй и фичу в `Cargo.toml`, и цифры в переменной окружения
(`LLVM_SYS_170_PREFIX` вместо 180).

## Что уже умеет компилятор (на эту версию)

- Функции с параметрами и возвращаемым значением
- Целочисленная арифметика (`+ - * / %`), сравнения, `&&`/`||`
- `если` / `иначе`, `пока`
- `целое` (и варианты размера), `текст` (как C-style строка), `верно`
- `неизменно` — проверка при семантическом анализе, что переменная не переприсваивается
- Вывод типа (`имя = значение;` без явного типа)
- Базовая проверка типов
- `вывести(...)` — временно реализовано как обёртка над `printf` (C-библиотека)
- Текстовые литералы БЕЗ интерполяции
- **Массивы фиксированного размера** (`целое[] числа = [1, 2, 3];`):
  литерал, чтение по индексу (`числа[0]`), запись по индексу
  (`числа[0] = 10;`). Размер выводится из литерала при объявлении, или
  указывается явно (`целое[5]`).
- **`для каждого`** (`для каждого элемент в числа { ... }`) — цикл по
  массиву, реализован через скрытый индекс-счётчик под капотом (для
  пользователя языка это не видно и не важно).
- **Структуры**: объявление полей, автоконструктор
  (`Пользователь("Аня", 30)`), доступ к полю на чтение и запись,
  **методы** (`функция именинник() -> целое { вернуть это.возраст + 1; }`,
  вызов через `юзер.именинник()`). Объекты выделяются в куче через
  `malloc` — это сознательная подготовка к будущему ARC, а не финальная
  модель памяти.
- **`публично`/`приватно`** для полей и методов структур. Приватное поле/метод
  доступны ТОЛЬКО изнутри методов той же самой структуры (через `это` или
  любой другой способ обращения) — обычная инкапсуляция в духе большинства
  ООП-языков. Без явного модификатора поле/метод публичны по умолчанию.
  **Важное ограничение**: у нас пока нет настоящей многофайловой модульной
  системы — значит "видимость между модулями" не применима, речь идёт
  только о границе "внутри структуры / снаружи структуры", а не о полноценной
  приватности на уровне файла или пакета, как в языках с модулями. Эта
  фича — только семантический анализ, кодогенерация вообще не затронута
  (у видимости нет представления в машинном коде).
- **Многофайловая сборка** (`подключить имя;`, `подключить "путь";`) —
  рекурсивно находит и сливает подключённые файлы в одну программу перед
  анализом. НЕ настоящая изоляция пространств имён (все файлы делят одно
  общее пространство), но теперь хотя бы дублирующиеся имена (функции,
  структуры, методы, поля) обнаруживаются с понятной ошибкой, а не молча
  подменяются последним объявлением. См. отдельный раздел выше про сборку и запуск.
- **Контракты (интерфейсы)** — `контракт Печатаемый { функция напечатать() -> текст; }`
  плюс `структура X : Печатаемый`. Компилятор проверяет на этапе
  компиляции, что структура реально имеет требуемые методы с совпадающими
  сигнатурами. v1 — только проверка соответствия, без настоящего
  полиморфизма (кодогенерация не тронута вообще). Реально скомпилировано
  и запущено на всех трёх сценариях (успех, отсутствующий метод,
  несовпадающая сигнатура). См. отдельный раздел ниже.
- **ARC: исправлена утечка при досрочном выходе через `?`** — структуры,
  объявленные до `?`, теперь корректно освобождаются при досрочном выходе
  через ошибку (раньше — утечка, не крах). Проверено объективно, через
  `valgrind --leak-check=full` (0 байт с исправлением против 24 байт без
  него на том же тесте), не просто "программа не падает". Честно
  задокументировано, что делает НЕ решает: утечки текстовых буферов (текст
  не под ARC) — отдельная, известная категория. См. отдельный раздел ниже.
- **Смена регистра для кириллицы** (`регистр_в_верхний`/`регистр_в_нижний`) —
  корректно работает с кириллицей, не только латиницей (в отличие от
  стандартных `toupper`/`tolower`). Ранее сознательно отложено из-за
  сложности (граница между ведущими UTF-8-байтами внутри кириллического
  диапазона, особый случай Ё/ё) — реализовано через `build_select`-цепочки
  вместо ветвления, чтобы снизить риск. Реально скомпилировано и запущено
  на самых рискованных случаях. См. отдельный раздел ниже.
- **Пространства имён между модулями (v1 + v2 — теперь с разрешением
  коллизий)** — `модуль.функция(...)` наряду с обычным, неквалифицированным
  доступом. Два модуля теперь МОГУТ объявить функцию с одинаковым именем
  (раньше — ошибка компиляции) — разрешается через квалификацию, с понятной
  диагностикой при попытке неквалифицированного доступа к неоднозначному
  имени. Реализовано через единообразное манглирование LLVM-имён функций
  из модулей. Реально скомпилировано и запущено, включая специальный тест
  на коллизию и полный регрессионный прогон. Пока только для функций, не
  структур. См. отдельный раздел ниже.
- **Настоящие пользовательские обобщённые структуры (generics)** —
  `структура Коробка<тип> { тип значение; функция получить() -> тип {...} }`,
  не только встроенные `Список`/`Словарь`. Через мономорфизацию (отдельная
  LLVM-структура и отдельные LLVM-функции методов на каждую использованную
  конкретную инстанциацию). Реально скомпилировано и запущено, включая
  несколько инстанциаций одновременно и вызовы методов. Пока без
  нескольких параметров типа, без явного типа в объявлении переменной —
  честно названные следующие шаги. См. отдельный раздел ниже.
- **Настоящая загрузка "на голом железе", включая настоящий код на Сфере,
  структуры под ARC и `вывести(...)`** — Multiboot-совместимое "ядро"
  загружено напрямую через `qemu-system-x86_64 -kernel`, без
  BIOS-загрузчика, без диска, без единой операционной системы. Полный
  переход из 32-битного режима (в котором Multiboot передаёт управление)
  в 64-битный (таблицы страниц, `PAE`, `EFER`, `GDT`), вызов
  скомпилированной нашим языком `main`, собственный распределитель
  памяти (тот же, что в автономном режиме) и собственная, написанная с
  нуля на ассемблере реализация `printf` (`%s`, `%lld`) — вариативные
  аргументы по System V ABI, отслеживание курсора экрана. Проверено
  объективно, шаг за шагом: "Sfera: 30", затем "Sfera: 42" (структура),
  затем "Hello from bare metal!" + "777" + "Result: 0" (полноценный
  вывод). По пути найдены и решены реальные проблемы: Multiboot 1
  требует 32-битный ELF-контейнер даже для 64-битного кода
  (`OUTPUT_FORMAT(elf32-i386)`), а два независимых способа записи на
  экран конфликтовали, пока не были объединены в один. Честное
  ограничение: нет `%f`, кириллица всё ещё не отображается (VGA не
  понимает многобайтовый UTF-8), нет прокрутки экрана. См. отдельный
  раздел ниже.
- **Автономный режим (`--автономно РАНТАЙМ.o`, v1)** — программы на
  Сфере теперь могут работать **полностью без операционной системы под
  собой**, без единого байта libc — первый шаг к тому, чтобы на языке
  можно было писать ядро ОС, загрузчик, прошивку встраиваемого
  устройства. Реализовано без единого изменения в самой генерации кода
  — написан отдельный, настоящий x86-64 ассемблерный файл
  (`минимальный_рантайм.s`, точка входа `_start` + системные вызовы
  напрямую), компилятор лишь научился его подключать. Проверено
  объективно: `file`/`ldd` подтверждают полную независимость от `libc`,
  программа реально запущена и дала верный результат. Честные
  ограничения: структуры/текст под ARC не работают без своего
  распределителя памяти (нет `malloc` без `libc`), поддержана только
  Linux x86-64. См. отдельный раздел ниже.
- **Многопоточность (`параллельно { тело }` + `канал<T>`, v1)** —
  ключевые слова были в грамматике с первой сессии, кодогенерация жёстко
  отклоняла — теперь реально работает через `pthread_create`. Проверено
  объективно: `helgrind` — 0 ошибок гонок данных; тест с двумя потоками
  разной длительности доказал реальную параллельность (порядок
  завершения не совпадает с порядком запуска в коде). Честное
  ограничение: тело блока не может использовать переменные из
  окружающей области видимости (защита от use-after-return) — кроме
  единственного, осознанного исключения — `канал<T>`, реализованного
  позже: безопасный "почтовый ящик" для передачи одного значения из
  потока обратно. По пути найдена и исправлена реальная, поучительная
  ошибка (segfault) — LLVM-значения не могут пересекать границы функций,
  решено передачей через `malloc`-буфер как штатный аргумент
  `pthread_create`. Реальный тест (`параллельно` вычисляет `2+2`,
  отправляет через канал) вывел точное значение, `helgrind` подтвердил
  0 ошибок. Нет `join`. См. отдельный раздел ниже.
- **Пакетный менеджер (`сфера_пакеты`, v1)** — отдельный инструмент, git
  как реестр (без своей центральной инфраструктуры). Простой манифест
  (`сфера.зависимости`), команда `установить` клонирует репозитории и
  копирует `.код` файлы в `пакеты/` — тот же, уже существующий механизм
  `подключить` работает без изменений. Реально протестировано: настоящий
  `git clone`, компиляция и запуск программы, использующей установленный
  пакет, плюс проверка обработки ошибок. См. отдельный раздел ниже.
- **Текст под ARC (v1, частично, плюс найденные и исправленные
  double-free и use-after-free)** — конкатенация и текстовые функции
  стандартной библиотеки (`регистр_в_верхний`, `целое_в_текст` и т.д.)
  создавали утечку памяти (текст не был под управлением ARC, в отличие
  от структур). Простые локальные переменные, промежуточные значения в
  цепочках `+`/`==`/`!=` (например, средний результат в `а + б + в`),
  текст внутри `результат<текст>` (`подстрока`, `прочитать_строку`,
  `прочитать_файл` — освобождается условно, только если `успешно`), и
  переменные, впервые становящиеся владеющими через переприсваивание
  (полностью — вне циклов, частично — внутри циклов, честно объяснено
  в отдельном разделе) теперь отслеживаются и освобождаются. Проверено
  через `valgrind` — несколько отдельных тестов, включая специально
  неуспешный случай `подстрока`, все дают `0 errors`. При попытке
  безопасно расширить покрытие дважды находились настоящие, серьёзные
  ошибки памяти (не просто утечки): **double-free** (`pop()` текстового
  фрейма отсутствовал в четырёх местах) и **use-after-free** (старое
  значение переменной освобождалось до вычисления нового, которое само
  читало старое) — обе найдены реальным тестом через `valgrind`,
  исправлены, подтверждены. Честно названные границы v1 (поля структур,
  неполное покрытие внутри циклов — требует настоящего рантайм-флага
  владения) не покрыты. См. отдельный раздел ниже.
- **Слабые ссылки (`слабая`)** — разрывают циклы ARC (сильная ссылка А→Б
  не блокируется тем, что Б "как бы" ссылается на А через слабое поле).
  Ключевое слово существовало в грамматике с первой сессии, семантика
  жёстко его отклоняла — теперь реализовано: слабое поле исключается из
  учёта retain/release. Проверено через `valgrind` — идеальный баланс
  аллокаций, без double-free. Не "настоящая" слабая ссылка с проверкой
  живости цели (может стать висячей) — честно названное ограничение v1.
  См. отдельный раздел ниже.
- **UI-кирпичики: прямоугольники, кнопки, ввод текста с клавиатуры,
  шрифты** — весь список, поставленный пользователем, теперь готов.
  Построено поверх FFI-примитивов, без новых больших языковых фич. Кнопка
  — обычная структура Сфера (прямоугольник + проверка попадания клика).
  Ввод текста — через `SDL_TEXTINPUT` (готовый UTF-8, не сырые коды
  клавиш). Шрифты — через `SDL_ttf`, включая настоящий кириллический
  текст на экране, объективно проверенный чтением пикселя. По пути
  найдена и исправлена непоследовательность типов (конструкторы/методы
  структур не разрешали числа разных размеров) и найдена ABI-хитрость
  (передача маленькой C-структуры по значению работает как `беззнак32`).
  Латиница при вводе с клавиатуры проверена побуквенно точно; кириллица
  архитектурно работает (каждая пойманная буква верна), но тестовый
  инструмент (`xdotool`/`Xvfb`) честно ограничен в надёжной симуляции
  нелатинского набора. См. отдельные разделы ниже.
- **FFI (`внешняя функция`) и графика через SDL2, включая обработку
  кликов мыши** — общая возможность привязки к любой C-библиотеке
  (`внешняя функция имя(...) -> тип;` + флаг `--линковать ИМЯ`), не только
  для графики. Привязки к SDL2 написаны как обычный подключаемый
  `.код`-файл (`графика.код`), не встроены в компилятор. Реально
  скомпилировано и запущено — окно SDL2, и **обработка настоящих кликов
  мыши** (проверено симуляцией внешнего ввода через `xdotool`, координаты
  совпали байт-в-байт). Плюс новая, общая возможность явного приведения
  типов (`целое32(значение)`). Пока без C-совместимых структур по
  значению (нет отрисовки фигур) — честно названный следующий шаг.
  См. отдельный раздел ниже.
- **`кликер.код`** — первая настоящая программа на языке (не изолированный
  тест): текстовая игра с магазином улучшений и сохранением прогресса
  между запусками. Нашла три реальных пробела за один заход, включая
  настоящий сегфолт компилятора (невалидный LLVM IR — инструкция после
  терминатора блока), пойманный через `gdb`. Добавлена новая функция
  стандартной библиотеки `подстрока(текст, начало, длина)`. Реально
  протестировано полным циклом (сохранить → перезапустить процесс →
  загрузить). См. отдельный раздел ниже.
- **Языковой сервер (LSP)** — диагностика ошибок в реальном времени,
  автодополнение (ключевые слова, типы, стандартная библиотека, функции/
  структуры текущего файла), подсказки при наведении (hover) и "перейти к
  определению" для VS Code. Переиспользует настоящий лексер/парсер/семантику
  компилятора (библиотечная цель `src/lib.rs`, без зависимости от LLVM).
  Подсказки параметров при вызове (signature help) — пока не реализованы.
  **Реально собрано и проверено** локальной установкой Rust/LLVM 18 —
  не только написано. См. отдельный, подробный раздел ниже.
- **Сборка библиотек** (`--библиотека`/`-b`) — файл без функции `главная`
  теперь можно собрать как объектный файл для подключения в другой проект,
  а не только как самостоятельную программу. Первый шаг к системе пакетов,
  не полноценная система сама по себе. См. отдельный раздел выше.
- **Начало стандартной библиотеки** — пятнадцать встроенных функций
  (тот же принцип, что и `вывести` — специальный случай компилятора, не
  обычные функции языка): `длина`, `целое_в_текст`, `дробное_в_текст`,
  `текст_в_целое`, `абс`, `мин`, `макс`, `верно_в_текст`, `содержит`,
  `найти`, `прочитать_строку`, `аргументы_командной_строки`,
  `прочитать_файл`, `записать_файл`, `выполнить_команду`. Закрывают самые
  критичные дыры — раньше не было НИКАКОГО способа превратить число в
  текст (кроме как внутри интерполяции), разобрать текст обратно в число,
  найти подстроку, прочитать хоть что-нибудь извне программы, узнать, с
  какими аргументами программу запустили, сохранить данные между
  запусками, или запустить команду операционной системы. См. отдельный
  раздел ниже.
- **Сравнение и конкатенация текста** (`текст == текст`, `текст != текст`,
  `текст + текст`) — через `strcmp`/`strlen`/`malloc`/`memcpy`. Определяется
  по реальному LLVM-типу значения, не по виду AST. См. отдельный раздел
  ниже про известное следствие (утечка при каждой конкатенации).
- **Интерполяция строк** (`"Рост: $рост"`) — поддерживается только простая
  форма `$имя` (одно имя переменной), НЕ `${выражение}`. Работает ТОЛЬКО как
  прямой единственный аргумент `вывести(...)` — реализовано напрямую через
  printf с format-строкой и variadic-аргументами, без настоящей runtime
  конкатенации текста. Сохранить интерполированную строку в переменную или
  передать в другую функцию нельзя — компилятор выдаст понятную ошибку.
  Подставлять можно только простые переменные — не поля структур
  (`$юзер.имя` не сработает) и не элементы массивов. Символ `%` в тексте
  автоматически экранируется — защита от case, когда пользовательский текст
  случайно совпал бы со спецификатором формата printf.
- **`Список<тип>`** — растущая динамическая коллекция. **НЕ пример общих
  generics** (см. пояснение ниже) — встроенный в компилятор тип, по той же
  архитектурной модели, что и `результат<тип>` и фиксированные массивы.
  `Список<целое>()` — создать пустой список; `.добавить(x)`, `.получить(i)`,
  `.размер()` — три поддержанных метода. Живёт в куче, управляется ARC
  (растёт счётчик ссылок при копировании, как у обычных структур). Буфер
  данных растёт автоматически (удвоением) при нехватке места — настоящая
  реализация с `malloc`/`memcpy`/`free`, не заглушка. Подробности и известные
  риски — в отдельном разделе ниже.
- **`Словарь<Ключ, Значение>`** — реализован как список пар ключ-значение с ЛИНЕЙНЫМ
  поиском (не настоящая хеш-таблица) — переиспользует архитектуру `Список<тип>`.
  **Ключи теперь любого поддержанного типа** (целочисленные и текстовые) —
  сравнение ключей внутри `сгенерировать_метод_словаря` само определяет
  способ по РЕАЛЬНОМУ типу значений (текст — через `strcmp`, целые числа —
  через `build_int_compare`), тем же принципом, что уже применён в
  `сгенерировать_бинарное` для операторов над текстом. `.положить(ключ, значение)`,
  `.получить(ключ) -> результат<значение>`
  (в отличие от `Список.получить`, здесь явно обрабатывается случай
  "ключа нет" через уже знакомую модель `результат<тип>`, а не падает
  молча), `.размер()`. Подробности и известные риски — в отдельном
  разделе ниже.
- **ARC**: счётчик ссылок в каждой структуре, растёт корректно при
  копировании переменных (`Пользователь другой = юзер;`) И при добавлении
  структуры в `Список`/`Словарь` (тот же класс use-after-free, что был найден
  и исправлен в конструкторе структур, теперь закрыт и здесь). Автоматическое
  освобождение памяти теперь работает и на верхнем уровне функции, И внутри
  вложенных блоков (`если`/`пока`/`для каждого`, на любой глубине), И
  РЕКУРСИВНО для полей-структур (структура А хранит поле-структуру Б — Б
  тоже освобождается при освобождении А). Ранний возврат через `?`
  всё ещё не покрыт (не регресс — просто ещё не сделано). См. отдельный,
  подробный раздел ниже — это самая свежая, ещё не проверенная сборкой
  часть кода.
- **`результат<тип>` + `?`** (модель ошибок в духе Rust): `успех(x)`,
  `ошибка("сообщение")`, оператор `?` для проброса ошибки вверх по стеку
  вызовов. **Развернуть `результат<тип>` можно и без `?`** — через
  псевдополя `.успешно` (`верно`), `.значение` (`тип`), `.сообщение` (`текст`),
  доступные из ЛЮБОЙ функции, не только объявленной как `результат<тип>`
  (пример — использование в `главная()` в `привет.код`). Проверяется
  семантическим анализом (тип успешного значения, что `?` используется
  только внутри функций, объявленных как `результат<тип>`). Также при
  `вернуть` теперь по-настоящему проверяется совпадение типа с объявленным
  `-> тип` функции — раньше эта проверка отсутствовала вообще.

Конвейер: лексер → парсер → семантический анализ → LLVM IR → `clang` → исполняемый файл.

## ⚠️ Новый непроверенный код: `для каждого`

Реализация переиспользует уже проверенную (хотя тоже непроверенную сборкой)
GEP-механику индексации массива — риск ниже, чем у массивов/результата
изначально, но всё же не проверено локальной сборкой. Единственная новая
деталь — `build_int_compare` со сравнением индекса и размера массива и явный
скрытый счётчик `alloca`; оба паттерна уже использовались раньше в
`сгенерировать_цикл_пока`/индексации, так что риск умеренный.

Известное ограничение: переменная цикла (`элемент` в `для каждого элемент в X`)
пока не может сама быть структурой — если элементы массива когда-нибудь
станут структурами, доступ к их полям внутри тела цикла потребует
дополнительной работы (аналогично тому, как это уже сделано для обычных
переменных-структур через `ДополнительнаяИнформация::Структура`).

## ⚠️ Найден и исправлен реальный баг: `вывести(...)` печатал текст как число

При добавлении псевдополей `результат<тип>` обнаружился настоящий, а не
гипотетический баг: `вывести(...)` раньше различал только "текстовый
литерал напрямую" (`вывести("привет")`) и "всё остальное" (всегда
печаталось через числовой формат `%lld`). Значит `вывести(переменная_текст)`
или `вывести(объект.текстовое_поле)` печатали бы указатель на текст, как
если бы это было число — то есть мусор или крэш. Исправлено: формат печати
теперь выбирается по РЕАЛЬНОМУ типу вычисленного значения (`PointerType` →
текст, `IntType` → число), а не по виду исходного кода. Это привело
`привет.код` к рабочему состоянию для вывода `результат<тип>.сообщение`.

Оставшийся, не исправленный сейчас нюанс: тип `верно` (i1) идёт через тот
же числовой путь `%lld` — из-за особенностей variadic-функций в C (каким
образом маленькие типы вроде i1/i8/i16 продвигаются при передаче в `printf`)
это МОЖЕТ работать некорректно на некоторых платформах. Не проверено;
если увидишь мусор при `вывести(значение_типа_верно)` — дай знать.

## ⚠️ Новый непроверенный код: доступ к псевдополям результат<тип>

Доступ через `.успешно`/`.значение`/`.сообщение` (в `сгенерировать_доступ_к_полю`)
написан тем же способом, без проверки компиляцией — использует
`build_extract_value` на значении, загруженном напрямую из переменной
(не из указателя, в отличие от пользовательских структур). Если здесь
ошибка — скорее всего, в порядке `load` → `into_struct_value()` →
`build_extract_value`.

## ⚠️ Новый непроверенный код: результат<тип> и оператор ?

Эта часть — самая экспериментальная в компиляторе на сегодняшний день,
написана без единой проверки компиляцией, и использует несколько LLVM-техник
впервые (сверх уже рискованных техник из раздела про массивы):

- **`результат<тип>` представлен как анонимная (безымянная) LLVM-структура**
  `{ i1 успешно, тип значение, i8* сообщение }`, а не именованная, как
  пользовательские структуры языка. Это должно работать без отдельного
  реестра типов (анонимные структуры с одинаковым набором полей LLVM
  считает одним типом автоматически) — но сама идея использована впервые.
- **`StructType::get_undef()`** — используется для структур впервые (для
  массивов мы уже использовали `ArrayType::get_undef()` успешно по логике,
  но для структур это новый вызов).
- **`BasicTypeEnum::VectorType`** — добавлен в функцию `undef_значение` для
  полноты match, но векторные типы в компиляторе никогда не используются
  и не тестировались; если такого варианта в этой версии `inkwell` не
  существует — компилятор укажет на это точно и однозначно, легко исправить
  (просто убрать эту одну строку).
- **`?` — единственное место в кодогенераторе, где вычисление ВЫРАЖЕНИЯ
  создаёт ветвление** (условный переход + возможный ранний `вернуть`).
  Все остальные выражения в компиляторе — линейные, без базовых блоков.
  Если здесь есть логическая ошибка — скорее всего, в порядке
  `position_at_end`/`build_conditional_branch`/`build_return` внутри
  `сгенерировать_проброс`.
- **Арифметика над `результат<тип>` не имеет смысла и всё ещё не поддержана,
  и это по-прежнему риск паники, а не аккуратной ошибки** — семантика
  формально может пропустить `результат<целое> + результат<целое>` (типы
  совпадают структурно), а `результат<тип>` представлен как СТРУКТУРА
  (агрегат из трёх полей), не указатель — значит новая проверка "текст ли
  это" (по признаку "указатель") здесь не срабатывает, и код попадает в
  старый числовой путь (`.into_int_value()`), что для агрегата — паника
  Rust внутри `inkwell`, а не понятная ошибка компиляции. Не используй
  `результат<тип>` в арифметических выражениях.

## ⚠️ Известные риски именно в реализации структур (эта версия)

Часть кода для структур писалась без возможности локально прогнать `cargo build`
(в среде разработки не было доступа к тулчейну Rust) — то есть эта часть
**не проверена компиляцией**, в отличие от более ранних этапов, которые
прогонялись раньше по ходу разработки. Наиболее вероятные места, где может
понадобиться правка при первой сборке:

- `найти_имя_структуры_по_llvм_типу` — использует `print_to_string()` на
  LLVM-типах и сравнение полученных строк для определения, к какой структуре
  относится указатель. Это рабочий, но "грубый" приём — если формат вывода
  `print_to_string()` в твоей версии `inkwell`/LLVM отличается от ожидаемого
  (например, другой синтаксис указателей в новых версиях LLVM), сравнение
  может не сработать. Если увидишь ошибку здесь — пришли текст ошибки,
  поправим на более надёжный способ (хранить тип структуры явно в таблице
  переменных, а не выводить его из LLVM-типа постфактум).
- `build_struct_gep`, `get_field_type_at_index`, `opaque_struct_type`,
  `build_pointer_cast` — это реальные методы `inkwell`, но их точная
  сигнатура может немного отличаться между версиями крейта; если `cargo`
  укажет на несовпадение типов в этих местах — обычно это вопрос мелкой
  правки вызова, не переписывания логики.
- ~~Определение структуры по LLVM-типу указателя~~ — это было реальной
  проблемой (не просто риском): начиная с LLVM 15 указатели стали
  "непрозрачными" (opaque pointers), и угадать по виду типа, к какой
  структуре он относится, физически невозможно. Исправлено: теперь
  кодогенератор хранит имя структуры явно, в момент объявления переменной,
  а не пытается вывести его постфактум из LLVM-значения.

Присылай текст ошибок компиляции как есть — по конкретному сообщению будет
быстро понятно, что именно поправить.

## ⚠️ `Словарь<Ключ, Значение>`: архитектура и риски (важно прочитать перед тестами)

**Тоже НЕ настоящая хеш-таблица.** Реализован как список ПАР ключ-значение
с линейным поиском — переиспользует архитектуру `Список<тип>` (та же модель
роста буфера через `malloc`/`memcpy`/`free`), но с ДВУМЯ параллельными
массивами (ключи, значения) вместо одного.

**Как это устроено внутри:**
- LLVM-структура: `{ i64 счётчик_ссылок, i64 размер, i64 вместимость, ключ* ключи, значение* значения }`
- `.положить(ключ, значение)` — линейный поиск существующего ключа (цикл
  через скрытый alloca-счётчик, тот же приём, что и в `для каждого`); если
  найден — перезаписывает значение на месте (размер не растёт); если не
  найден — растит ОБА буфера синхронно (если нужно) и добавляет пару в конец.
- `.получить(ключ)` — тот же линейный поиск; возвращает `результат<значение>`:
  `успех(значение)` если ключ найден, `ошибка("ключ не найден")` если нет.
  Это честнее, чем `Список<тип>.получить(i)`, которое не проверяет границы
  вообще — здесь "ключа нет" обрабатывается явно через уже знакомую модель
  ошибок, а не тихо.

**⚠️ Новая техника, использованная здесь впервые:** alloca-ячейка для
"результата" метода, заполняемая в РАЗНЫХ базовых блоках (найден/не найден)
и читаемая в одной общей точке после — способ объединить два возможных
исхода без ручного построения PHI-узлов (тот же принцип, что уже
использовался для индекса цикла в `для каждого`, просто применённый к
возвращаемому значению).

**Известные ограничения этой версии:**
- ~~Только целочисленные ключи~~ — СНЯТО в этой версии: `сравнить_ключи_словаря`
  теперь определяет способ сравнения по реальному типу значения (текст —
  `strcmp`, целые числа — `build_int_compare`). Проверено на `Словарь<текст, целое>`
  в `привет.код`. Другие типы ключей (например, `верно`, структуры) пока не
  проверялись и могут потребовать дополнительной работы.
- Нет `.удалить(ключ)` — только положить, получить, размер
- Нет `.содержит(ключ)` — можно проверить через `.получить(ключ).успешно`
- Линейный поиск — O(n) на каждую операцию, не O(1), как у настоящей
  хеш-таблицы. Для маленьких словарей (десятки записей) разница не имеет
  практического значения; для тысяч записей это будет заметно медленнее
- Присваивание `код построить_результат_успех/ошибка` **намеренно дублирует**
  логику уже существующих `сгенерировать_успех`/`сгенерировать_ошибку`,
  а не переиспользует их напрямую — они принимают AST-выражение и вычисляют
  его, а здесь значение уже вычислено заранее (из чтения буфера). Небольшое
  дублирование кода ради того, чтобы не рисковать регрессией уже
  проверенного (тестами) пути для обычного `результат<тип>`.

## ⚠️ `Список<тип>`: архитектура и риски (важно прочитать перед тестами)

**Это не то же самое, что настоящие пользовательские generics** (см.
отдельный, подробный раздел ниже — они теперь реализованы). `Список<тип>`
остаётся **встроенным в компилятор типом**, распознаваемым по
зарезервированному имени "Список" (нельзя объявить свою структуру с таким
именем), с фиксированной, вручную написанной в `codegen.rs` логикой — та
же архитектурная модель, что у `результат<тип>` и фиксированных массивов.
Настоящие пользовательские обобщённые структуры (`структура Коробка<тип>
{ ... }`) реализованы ОТДЕЛЬНО, через мономорфизацию — не переиспользуют
этот механизм напрямую, хотя идея (генерировать отдельную копию под каждый
использованный конкретный тип) в основе та же.

**Как это устроено внутри:**
- LLVM-структура: `{ i64 счётчик_ссылок, i64 размер, i64 вместимость, тип* данные }`
- **Предварительная регистрация**: перед генерацией тел функций семантический
  анализатор собирает МНОЖЕСТВО всех конкретных типов, для которых где-либо в
  программе создавался `Список<тип>`, и кодогенератор заранее синтезирует LLVM-тип
  для каждого — по той же схеме, что и для обычных пользовательских структур.
  Это позволяет `тип_в_llvm` оставаться простым read-only методом, не требующим
  мутации на лету во время генерации тел функций.
- **Ключ инстанциации строится из НАШЕГО типа** (`РешённыйТип`), а не выведен
  из LLVM-типа постфактум — та же защита от проблемы opaque pointers (LLVM 15+),
  которую мы уже проходили и исправляли для структур.
- **Рост буфера** — настоящая реализация: при нехватке места выделяется новый
  буфер (удвоение вместимости, начиная с 4), старые данные копируются через
  `memcpy`, старый буфер освобождается через `free`.

**⚠️ Использованные новые техники, не встречавшиеся раньше в этом компиляторе:**
- `build_select` — для тернарного выбора "новая вместимость = если было 0,
  то 4, иначе ×2"
- `build_is_null` — проверка "уже был выделен буфер данных, или список ещё
  совсем пустой"
- Одно-индексный `build_gep` (адресная арифметика "данные + индекс") — это
  ОТЛИЧАЕТСЯ от двух-индексного GEP, который используется для чтения из
  фиксированных массивов (`целое[5]`): там указатель ведёт на весь `ArrayType`
  целиком, здесь — просто на первый элемент буфера в куче.

Если при сборке возникнет ошибка именно в `сгенерировать_метод_списка` —
вероятнее всего, в точной сигнатуре одного из этих трёх вызовов.

**Известные ограничения этой версии:**
- Нет `.удалить(i)` — только добавление, чтение, размер
- Нет `список[i]` как синтаксического сахара — только явное `.получить(i)`
  (осознанное решение: индексация массивов и списков технически устроена
  по-разному, разрешить один синтаксис для обоих раньше времени означало бы
  риск, а не экономию)
- Нет вывода типа для `Список<тип>` через простое присваивание (`числа = Список<целое>();`
  без явного `Список<целое>` слева) — только через явное объявление типа
- `Список` элементов-структур не проверен и может потребовать доработки
- Парсер разбора `Список<целое>(...)` использует откат позиции при
  неоднозначности с оператором `<` (та же классическая проблема, что и в
  `a<b>(c)` в C++) — в очень редких случаях (`a < b > (c)` как часть более
  сложного выражения) может неверно распознать код как генерик-вызов

## ⚠️ ARC: что реально сделано, а что — нет (важно прочитать перед тестами)

**Эта версия НЕ ПРОВЕРЕНА сборкой** — она написана и отправлена, пока у автора
не было доступа к компьютеру для тестирования. Раздел ниже — самая важная
документация в этом README на сегодня, читай внимательно перед тем, как
пробовать что-либо, где задействованы структуры.

**Сделано и должно работать:**
- Каждая структура имеет скрытое поле-счётчик ссылок (i64, индекс 0 в
  LLVM-представлении, до всех пользовательских полей). Конструктор
  инициализирует счётчик значением `1`.
- `захватить(...)` — увеличивает счётчик на 1. `отпустить(...)` — уменьшает
  на 1, и если дошёл до нуля — вызывает `free`.
- `захватить` автоматически вызывается при копировании существующей
  переменной-структуры в новую (`Пользователь другой = юзер;`).
- **НОВОЕ в этой версии — автоматическое `отпустить` теперь покрывает
  ВЛОЖЕННЫЕ блоки** (`если`/`иначе`/`пока`/`для каждого`), не только
  верхний уровень функции, как было раньше.

### Как это устроено — стек областей видимости

Раньше был один плоский список "структуры верхнего уровня функции" и флаг
"мы сейчас на верхнем уровне или нет" — специально узкая, но безопасная
версия, потому что таблица переменных в кодогенераторе плоская (не по
областям видимости), и расширение на вложенные блоки без дополнительной
защиты рисковало обращением к неинициализированной памяти (если бы
структура объявлялась внутри `если`, а её пытались освободить ПОСЛЕ этого
блока, не зная, выполнилась ли вообще эта ветка в рантайме).

**Теперь вместо плоского списка — настоящий СТЕК**: каждый вложенный блок
(тело функции целиком, затем каждый `если`/`иначе`/`пока`/`для каждого`)
добавляет свой уровень поверх при входе, и убирает его при выходе. Правила:

- **При объявлении структурной переменной** — добавляем её в САМЫЙ ВЕРХНИЙ
  (самый вложенный, "текущий") уровень стека.
- **При `вернуть` на ЛЮБОЙ глубине вложенности** — освобождаем структуры
  ИЗ ВСЕХ уровней стека сразу (вся функция целиком, вниз до текущей точки),
  кроме той, что совпадает с самим возвращаемым значением (владение
  "перемещается" наружу, без изменения счётчика — как перемещение (move)
  в Rust).
- **При естественном выходе из блока** (условие цикла стало ложным, конец
  ветки `если`/`иначе` без `вернуть` внутри) — освобождаем структуры ТОЛЬКО
  текущего (только что законченного) уровня, затем убираем этот уровень со
  стека. Родительские уровни не трогаем — они всё ещё "живы".

**Почему это безопасно** (в отличие от наивного расширения без стека):
освобождение теперь ВСЕГДА генерируется ВНУТРИ ТОГО ЖЕ блока, где были
объявлены структуры — если LLVM в рантайме вообще дошёл до этой точки,
значит объявление структуры (более раннее в том же блоке) уже точно
выполнилось. Опасность была именно в попытке освободить структуру СНАРУЖИ
блока — а мы теперь этого не делаем: каждый блок убирает за собой сам.

**Циклы — особый случай, тоже учтён**: для `пока`/`для каждого` освобождение
текущего уровня происходит НА КАЖДОЙ итерации (перед переходом обратно к
условию), а не один раз в конце всего цикла — иначе при повторном входе в
тело цикла alloca-ячейка перезаписывалась бы новым объектом, а объект
предыдущей итерации "утекал" бы, так и не будучи отпущенным.

**Что покрыто:**
- Структуры на верхнем уровне функции (как и раньше)
- Структуры внутри `если`/`иначе`/`пока`/`для каждого`, на любом уровне
  вложенности (вложенные если-внутри-если тоже должны работать — стек
  общий, глубина не ограничена искусственно)
- `вернуть` на любом уровне вложенности — верно освобождает все объемлющие
  уровни, не только свой собственный
- Естественный выход из цикла/ветки без явного `вернуть`
- И явный, и неявный (void-функции) возврат

**Что НЕ покрыто (по-прежнему "течёт", как и раньше — это НЕ регресс,
просто ещё не реализованная часть):**
- Ранний возврат через оператор `?` (внутри `сгенерировать_проброс`) —
  сознательно не тронут, чтобы не рисковать регрессией уже проверенного
  тестами пути `результат<тип>`. Если внутри тела функции используется `?`,
  структуры, объявленные ДО этой точки, не освободятся при досрочном выходе
  через `?` — освободятся только при обычном `вернуть`.
- `параллельно` — не поддержан в кодогенерации вообще (отдельная ошибка),
  поэтому вопрос вложенных структур там пока не актуален.
- Параметры функций/методов (включая `это`) — они и не ретейнятся при
  получении, поэтому симметрично и не отпускаются.
- Присваивание существующей переменной новым значением (`юзер = другой;`) —
  старая ссылка просто "теряется" без освобождения.
- **✅ ЗАКРЫТО в этой версии: тот же риск в `Список<Структура>`/`Словарь<...,Структура>`.**
  Ранее здесь было предупреждение "похожий риск НЕ исправлен" — теперь
  исправлено: `Список.добавить(...)` и `Словарь.положить(ключ, значение)`
  теперь тоже делают `захватить`, если элемент/значение — структура И
  аргумент передан как простая переменная (не свежий вызов конструктора).
  Реализация переиспользует ту же проверку, что и в конструкторе структур:
  `ДополнительнаяИнформация::Список`/`::Словарь` теперь дополнительно несут
  `имя_структуры_элемента`/`имя_структуры_значения` (вычисляются из
  `РешённыйТип` при регистрации типа переменной). Тест `arc_в_коллекциях()`
  в `привет.код` — специально для проверки: одна и та же переменная-структура
  одновременно используется напрямую, через `Список`, и через `Словарь`.
  Ожидаемый результат — `84`.

**⚠️ Новая, непроверенная область кода в этой версии** — весь механизм
push/pop стека вокруг `если`/`пока`/`для каждого`, и особенно порядок
операций на границах блоков (когда именно освобождать текущий уровень
относительно перехода к следующему базовому блоку). Логика продумана и
несколько раз перепроверена вручную (раз нет возможности скомпилировать),
но это самая архитектурно рискованная правка после первоначальной версии ARC.
В `привет.код` добавлены ДВЕ тестовые функции:
- `посчитать_возраст_временного()` — старый тест, верхний уровень
  (ожидается `99`)
- `arc_во_вложенном_блоке(5)` — НОВЫЙ тест специально для вложенных
  блоков: структура внутри `если` (условие истинно) и структуры внутри
  цикла `пока` (3 итерации, каждая создаёт свою структуру). Ожидаемый
  результат — `8` (5 из ветки `если`, плюс 0+1+2 из трёх итераций цикла).

При первой возможности собери и проверь именно эти два результата.

### Рекурсивное освобождение ARC (новое в этой версии) + найденный и исправленный use-after-free

Когда структура А хранит поле-структуру Б, теперь при освобождении А
компилятор автоматически рекурсивно вызывает `отпустить` и для Б — раньше
это было явно задокументированным упрощением ("Б не получает свой отпустить
автоматически"), теперь исправлено. Реализовано через `структурные_поля`
(карта "структура → её поля-структуры", заполняется один раз при регистрации
структур) плюс защита от бесконечной рекурсии в самом КОМПИЛЯТОРЕ (не в
программе пользователя!) на случай циклических ссылок типов (структура А
хранит поле типа Б, Б хранит поле типа А) — без этой защиты кодогенератор
попытался бы генерировать `отпустить(А) → отпустить(Б) → отпустить(А) → ...`
до переполнения собственного стека прямо во время сборки.

**При проектировании этой фичи обнаружился и был исправлен настоящий
use-after-free**, не гипотетический: конструктор структуры (`Компания("Р", основатель)`)
не делал `захватить` (retain) для поля-структуры, если ему передавали УЖЕ
СУЩЕСТВУЮЩУЮ переменную (`основатель`, объявленную отдельно) — счётчик
ссылок оставался 1, хотя реально на объект теперь ссылались ДВА места
(сама переменная и новое поле). При освобождении сначала переменной, потом
структуры (которая рекурсивно попыталась бы отпустить то же самое, уже
освобождённое поле) — это было бы обращением к уже освобождённой памяти.
Исправлено: конструктор теперь делает `захватить` для полей-структур,
ЕСЛИ аргумент — простая переменная (не свежий вложенный вызов конструктора,
у которого и так уже счётчик 1 — повторный retain создал бы обратную
проблему, утечку).

Тест `arc_рекурсивное_освобождение()` в `привет.код` — специально написан
для проверки именно этого: структура `Компания` с полем-структурой
`Пользователь`, обе создаются на верхнем уровне, ни одна не возвращается
сама (возвращается только число из вложенного поля) — обе должны корректно
освободиться, включая рекурсивно, без обращения к уже освобождённой памяти.
Ожидаемый результат — `45`.

**⚠️ Похожий, но НЕ исправленный риск** — см. пункт в списке "что НЕ покрыто"
выше про `Список<Структура>`/`Словарь<...,Структура>`.

## ⚠️ Новый непроверенный код: массивы

Реализация массивов (эта версия) написана тем же способом, что и структуры/
методы — без возможности локально прогнать `cargo build` по ходу написания.
Конкретные места с наибольшим риском:

- **`build_insert_value` + `get_undef()` для построения литерала массива**
  (`сгенерировать_массив_литерал`) — эта техника используется в компиляторе
  впервые, ни разу не проверялась на других участках кода. Если здесь
  ошибка — скорее всего, в порядке аргументов `build_insert_value` или в
  доступности метода `.get_undef()` на `ArrayType`.
- **`build_gep` (без "_struct_", "сырой" общий GEP) с двумя индексами** —
  используется для индексации массива (`сгенерировать_доступ_по_индексу`,
  `найти_адрес_места_записи`). Обёрнут в `unsafe {}`, в отличие от
  `build_struct_gep` (который в итоге не потребовал `unsafe` — см. более
  раннее исправление). Возможно, `build_gep` в этой версии `inkwell` тоже
  не требует `unsafe`, и компилятор выдаст warning "unnecessary unsafe" —
  это не ошибка, просто убери `unsafe { }` в этом случае.
- Массивы **структур** и массивы, выведенные через присваивание без явного
  типа (`числа = [1, 2, 3];` вместо `целое[] числа = [1, 2, 3];`) —
  поддержаны только для простых числовых/текстовых элементов; для массивов
  структур потребуется отдельная проверка.

## ⚠️ Новое: сравнение и конкатенация текста (реализовано, но не проверено сборкой)

Раньше здесь было предупреждение "не используй `текст + текст`" — теперь это
исправлено. `текст == текст`, `текст != текст` и `текст + текст` теперь
реализованы по-настоящему:
- **Сравнение** — через `strcmp` (сравнивает СОДЕРЖИМОЕ строк побайтово, а
  не адреса указателей — раньше, до этой правки, простое сравнение
  указателей было бы неверным: два одинаковых по содержимому, но разных
  объекта строки считались бы разными).
- **Конкатенация** — через `malloc` нового буфера размером с сумму длин
  (`strlen` для каждой строки) плюс один байт под завершающий ноль, и два
  `memcpy` (левая часть, затем правая часть вместе с её нулевым байтом).

И то, и другое определяется не по виду AST-узла, а по РЕАЛЬНОМУ LLVM-типу
вычисленного значения (указатель — значит текст) — тот же принцип, которым
раньше был исправлен похожий баг в `вывести(...)`.

**⚠️ Известное следствие:** результат конкатенации — новый `malloc`-буфер,
который никогда не освобождается (текст пока вообще не участвует в ARC —
ни литералы, ни результаты конкатенации не имеют счётчика ссылок). Каждая
конкатенация — небольшая утечка. Это не хуже, чем было раньше (текст и
так никогда не управлялся по памяти), но раньше просто не было способа
создать НОВУЮ строку в принципе — теперь есть, и вместе с этим появилась
эта конкретная утечка. Задокументировано честно, не скрыто.

**Операторы, для которых текст НЕ поддержан** (`-`, `*`, `/`, `%`, `<`, `>`,
`<=`, `>=`) — семантика формально их не запрещает (проверяет только
совпадение типов), но кодогенератор для них выдаст понятную ошибку
"оператор X не применим к тексту", а не упадёт непонятно.

## Строгий, табличный стиль UI панели разработчика (Excel/1C-стиль)

**Мотивация** — прежний вид панели (яркие скруглённые кнопки на тёмном
фоне) не устраивал: хотелось порядка, структурированности, настоящей
таблицы данных — как в Excel или 1C, а не ярких кнопок. Реализовано в
`графика.код`, применено к вкладке "Пакеты" панели.

### Новый примитив и структура `Таблица`

Добавлен `нарисовать_линию` (прямая привязка к `SDL_RenderDrawLine`) —
до этого в библиотеке вообще не было способа нарисовать одну линию,
только целиком закрашенный или очерченный прямоугольник.

`Таблица` — переиспользуемый компонент с произвольным числом колонок
(ширины задаются через `Список<целое>`, а не жёстко зашитым числом):
`нарисовать_заголовок(холст, шрифт, Список<текст> заголовки)` и
`нарисовать_строку(холст, шрифт, номер, Список<текст> значения, чётная)`
— тёмный фон заголовка, чередующийся (полосатый) фон строк, тонкие
серые разделители между колонками и строками.

### ⚠️ Две реальные находки в самом компиляторе, обнаруженные по пути

1. **`Список<T>` как ПОЛЕ структуры не работал вообще** — раньше
   `Список<T>` использовался только как локальная переменная или
   аргумент функции. Поле `ширины_колонок: Список<целое>` у `Таблица`
   провалилось с ошибкой "Список<тип> нельзя объявить через вывод
   типа" — оказалось, что регистрация полей структур
   (`зарегистрировать_структуры` в `codegen.rs`) использовала свободную
   функцию `решённый_тип_в_llvm`, которая сознательно отказывается
   обрабатывать `Список`/`Словарь` (для них нужен доступ к `&mut self`
   через `получить_или_создать_тип_списка`, которого у свободной
   функции нет). Исправлено — явный цикл по полям структуры вместо
   единого `.map().collect()`, с отдельной веткой для `Список`/`Словарь`.

2. **`это.поле_список.метод()` не работает** — цепочка доступа к
   полю-списку с немедленным вызовом метода на нём проваливается с
   "поле само не является структурой". Обходной путь без изменений
   компилятора — сначала прочитать поле в локальную переменную, вызывать
   методы уже у неё. Настоящее исправление (научить кодогенерацию цепочек
   доступа к полю работать со списком/словарём напрямую) — честно
   названный, следующий шаг.

### ✅ Применено к вкладке "Пакеты" — с найденным и исправленным багом парсинга

Вкладка "Пакеты" теперь показывает настоящую таблицу (Имя | Источник |
Описание), а не голый текстовый вывод. Написан парсер
(`разобрать_пакеты` в `панель.код`), разбирающий текстовый вывод
`сфера_пакеты список` в три параллельных списка.

**⚠️ Реальный баг, найденный тестом (не просто "выглядело неправильно",
а видимый мусор на экране)**: первая версия использовала жёстко
закодированное число `15` для обрезки префиксов `"    источник: "` и
`"    описание: "` — неверное, поскольку сами слова "источник"/
"описание" — кириллица, 2 байта на букву в UTF-8, реальная длина
префикса 22 байта, не 15. Итог — искажённый, съехавший текст на экране.
Исправлено на **динамический** расчёт через `длина(...)` от самого
текста префикса, а не магическое число — устраняет саму возможность
этой ошибки навсегда, а не просто чинит один конкретный случай (та же
самая ошибка уже случалась раньше в этой сессии, с другим текстом).

**Проверено объективно**, тем же способом, что и всё остальное —
реальный `git`-репозиторий, реальная установка через `сфера_пакеты`,
скриншот панели до и после исправления явно показывает разницу.

### ⚠️ Честные, отдельно найденные ограничения

- **Длинный текст не переносится и не обрезается по ширине колонки** —
  если значение шире отведённого места, оно просто наезжает на
  соседнюю колонку. Нужна логика обрезки (например, "..." в конце) —
  честно названный, следующий шаг.
- **Метаданные пакета привязаны к имени ЗАВИСИМОСТИ, не к имени
  каждого установленного файла** — если один репозиторий содержит
  несколько `.код` файлов, метаданные (источник/описание) записываются
  только один раз, под именем самой зависимости. Остальные файлы
  честно показывают "—" в этих колонках (не падают, просто нет данных)
  — реальное, отдельное архитектурное ограничение `сфера_пакеты`,
  обнаруженное этим же тестом, не входит в объём текущего исправления.
- **Тёмно-серый текст статуса на тёмном фоне почти не виден** — замечено
  при тестировании (сообщение "Нажми «Обновить список»..." использует
  тот же тёмно-серый цвет, что и текст внутри светлой таблицы, но
  рисуется поверх тёмного фона основной области) — мелкая, но реальная
  находка, ещё не исправлена.
