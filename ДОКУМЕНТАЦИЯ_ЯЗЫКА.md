## Первая программа

```
функция главная() -> целое {
    вывести("Привет, мир!");
    вернуть 0;
}
```

Каждая программа обязана иметь функцию `главная`, возвращающую `целое`
(код завершения — `0` означает успех). Компилируется командой:

```bash
запустить привет.код -c
```

⚠️ **Без `-c` программа не только соберётся, но и сразу запустится** —
удобно для быстрой проверки. Флаг `-c` можно писать и кириллицей, как
`-с` (по первой букве слова "собрать") — оба варианта равнозначны и
работают одинаково. Внешне кириллическая "с" и латинская "c" выглядят
неотличимо на экране, но для компьютера это разные символы — поэтому
поддержаны **оба**, а не только один, чтобы привычная латинская `-c`
(как почти везде в мире разработки) продолжала работать без сюрпризов.
То же самое верно для `-b`/`-б` (`--библиотека`).

## Основы синтаксиса

- **Комментарии**: `//` до конца строки, `/* ... */` — многострочные
- **Каждый оператор заканчивается точкой с запятой** (`;`)
- **Блоки кода** — в фигурных скобках `{ }`
- Язык **полностью кириллический** — все ключевые слова, имена
  встроенных функций и типов пишутся кириллицей

## Типы данных

### Целые числа

| Тип | Размер | Знаковый |
|---|---|---|
| `целое` | 64 бита | да |
| `целое8` | 8 бит | да |
| `целое16` | 16 бит | да |
| `целое32` | 32 бита | да |
| `целое64` | 64 бита | да (то же, что `целое`) |
| `беззнак8` | 8 бит | нет |
| `беззнак16` | 16 бит | нет |
| `беззнак32` | 32 бита | нет |
| `беззнак64` | 64 бита | нет |

⚠️ **Важно**: типы разной разрядности **не смешиваются неявно** —
`целое32` и `целое` в одном выражении требуют явного приведения:

```
целое32 а = 5;
целое б = 10;
целое итог = целое(а) + б;   // явное приведение обязательно
```

### Дробные числа

`дробное` (по умолчанию, 64 бита), `дробное32`, `дробное64`.

### Текст

`текст` — строка. Литералы в двойных кавычках: `"привет"`.
Конкатенация — оператором `+`:

```
текст имя = "Аня";
текст приветствие = "Привет, " + имя + "!";
```

Экранированные последовательности внутри строк: `\n` (новая строка),
`\r` (возврат каретки — важно для сетевых протоколов вроде HTTP, где
строки заголовков разделяются именно парой `\r\n`), `\t` (табуляция),
`\"` (кавычка), `\\` (обратный слеш).

### Логический тип

`верно` — булев тип. Литералы: `да` (истина) и `нет` (ложь) —
**не** `true`/`false`.

```
верно готово = да;
если (готово) {
    вывести("Готово!");
}
```

## Переменные

Объявление с явным типом — `тип имя = значение;`:

```
целое возраст = 25;
текст имя = "Иван";
верно активен = да;
```

### Вывод типа (`имя = значение;`)

Тип слева можно опустить целиком — если `имя` ещё не объявлено в этой
области видимости, `имя = значение;` — это ОБЪЯВЛЕНИЕ, а не присваивание,
и тип выводится из выражения справа:

```
возраст = 25;              // выведено: целое
имя = "Иван";               // выведено: текст
итог = удвоить(21);          // выведено из типа возврата функции
точка = Точка(3, 4);         // выведено: Точка (вызов конструктора структуры)
```

Работает для любого выражения, тип которого семантический анализ может
определить напрямую (числовые и строковые литералы, `да`/`нет`, вызовы
функций и методов, конструкторы структур, арифметика и т. д.) — то есть
для подавляющего большинства реальных объявлений. Никакого отдельного
синтаксиса (вроде `:=`) не требуется — используется тот же оператор `=`,
что и у присваивания; различает их семантический анализ по тому, было ли
имя уже объявлено в текущей области видимости (см. `grammar.md`, раздел
4, и `ast::Оператор::Присваивание` — узел с этим именем на самом деле
неоднозначен и разрешается именно так).

⚠️ **Ограничения**:
- `Список<T>`/`Словарь<Ключ, Значение>` через вывод типа объявить нельзя
  — у них всегда только один типовый параметр в грамматике, конкретный
  `Т` для пустого литерала-контейнера вывести неоткуда; указывай тип
  явно (`Список<целое> числа = Список<целое>();`).
- `неизменно` требует явного типа (`неизменно целое максимум = 100;`) —
  вывод типа с `неизменно` не комбинируется в этой версии.
- Если выражение справа настолько сложное, что тип не определяется
  напрямую — честная ошибка компиляции ("не удалось вывести тип для
  '...' — выражение справа слишком сложное для текущей версии
  анализатора"), а не молчаливое падение к какому-то типу по умолчанию.

### Неизменяемые переменные

Ключевое слово `неизменно` перед типом запрещает переприсваивание:

```
неизменно целое максимум = 100;
```

### Явные приведения типов

Синтаксис — имя типа как функция: `целое32(значение)`, `дробное(значение)`.

⚠️ **Важно**: приведение нужно даже при инициализации **числовым
литералом** — типы разной разрядности не смешиваются неявно нигде:

```
целое32 а = целое32(5);    // так, не "целое32 а = 5;"
целое итог = целое(а) + б;  // и здесь тоже явно
```

## Операторы

### Арифметические

`+` `-` `*` `/` `%` (остаток от деления)

### Сравнение

`==` `!=` `<` `>` `<=` `>=`

### Логические

`&&` (И) `||` (ИЛИ) `!` (НЕ)

### Побитовые

`&` (побитовое И) `|` (побитовое ИЛИ) `^` (побитовое исключающее ИЛИ) `~`
(побитовое отрицание, унарный) — только для целых чисел, оба операнда
должны быть одного типа:

```
целое а = 12;
целое б = 10;
целое и_результат = а & б;    // 8
целое или_результат = а | б;  // 14
целое искл_результат = а ^ б; // 6
целое не_результат = ~5;      // -6
```

⚠️ **Приоритет ниже, чем у сравнения** (та же схема, что в C/Rust,
намеренно, не случайно) — `а & б == 8` разберётся как `а & (б == 8)`,
не как `(а & б) == 8`. При смешивании с сравнением используй явные
скобки.

### Сдвиги (`<<`, `>>`)

`<<` (сдвиг влево) и `>>` (сдвиг вправо, арифметический/знаковый) — та
же строгость, что у остальных побитовых операторов: только целые числа,
оба операнда (значение и количество сдвигов) — **одного и того же
типа**:

```
целое а = 1;
целое б = 3;
вывести(целое_в_текст(а << б));  // 8

целое число = 64;
целое степень = 2;
вывести(целое_в_текст(число >> степень));  // 16
```

Смешивание разных целочисленных типов запрещено явно (не по ошибке,
а намеренно, ради единообразия с `&`/`|`/`^`) — количество сдвигов
нужно привести к типу значения:

```
целое32 узкий = целое32(1);
узкий << целое32(3);  // ок — оба целое32
узкий << 3;           // ошибка: 3 по умолчанию — целое (64-бит), а не целое32
```

⚠️ **Честные ограничения**:
- Сдвиг числом бит, равным или большим разрядности типа (например,
  `целое32(1) << целое32(35)`), — поведение LLVM/аппаратуры, не
  гарантированное языком (обычно берётся по модулю разрядности, но
  на это не стоит полагаться).
- `>>` всегда арифметический (знаковый) — то же самое решение,
  что уже негласно принято для остальных операций над целыми
  (`/`, `%`, `<`, `>` и т. д.): беззнаковые типы (`беззнак8/16/32/64`)
  тоже получают знаковую семантику сдвига вправо. Это унаследованное
  ограничение, не новое именно для сдвигов.

**Почему это не конфликтует с `Список<Список<целое>>`.** Лексер
специально НЕ трогали — он по-прежнему выдаёт `<` и `>` как отдельные,
не склеенные токены, ровно как раньше. Распознавание `<<`/`>>`
происходит только в ОДНОМ месте — при разборе ВЫРАЖЕНИЙ (два токена
`<`/`>` подряд без пробела не могут означать ничего, кроме сдвига),
а закрытие вложенных обобщённых типов (`Список<Список<целое>>`)
целиком происходит в отдельном, никогда не пересекающемся с разбором
выражений коде разбора ТИПОВ — конфликта нет, проверено вживую (см.
ИСТОРИЯ_РАЗРАБОТКИ.md).

### Текст

`+` — конкатенация. `==`/`!=` — сравнение по содержимому (не по адресу).

#### Интерполяция строк

Внутри текстового литерала `$имя` подставляет значение переменной,
а `${выражение}` — значение ЛЮБОГО выражения (форматируемого типа —
см. ниже):

```
целое возраст = 25;
текст имя = "Никита";

вывести("Привет, $имя! Тебе $возраст лет.");
вывести("Через год будет ${возраст + 1} лет.");

// Результат интерполяции — обычное текстовое значение: его можно
// сохранить в переменную, вернуть из функции, передать куда угодно,
// склеить через "+" — не только напечатать напрямую.
текст сообщение = "Итог: ${площадь(3, 4)} м²";
```

Поддерживаются только форматируемые типы: `текст`, любые целые
(`целое`, `целое8`/`16`/`32`/`64`, `беззнак8`/`16`/`32`/`64`), `дробное`
(и `дробное32`/`64`), `верно` (печатается как `да`/`нет`). Попытка
вставить структуру, контракт или другой неформатируемый тип —
ошибка семантического анализа, а не крах или тихая порча вывода.

Экранирование: `\$` вставляет буквальный символ `$` без интерполяции
(`"цена: 5\$"` → `цена: 5$`).

⚠️ **Честное ограничение**: строковые литералы ВНУТРИ `${...}` не
поддерживаются (`"${если а { "да" } иначе { "нет" }}"` не разберётся
корректно) — лексер разбирает внешний текстовый литерал целиком ДО
того, как парсер узнаёт о вложенном `${...}`, поэтому неэкранированная
кавычка внутри `${...}` преждевременно закрыла бы внешний литерал.
Обычные выражения без вложенных строк (арифметика, вызовы функций и
методов, доступ к полям, индексация) работают без ограничений.

## Управляющие конструкции

### Условие

```
если (х > 10) {
    вывести("Больше десяти");
} иначе если (х > 0) {
    вывести("Положительное");
} иначе {
    вывести("Ноль или отрицательное");
}
```

### Цикл с условием

```
целое счётчик = 0;
пока (счётчик < 5) {
    вывести(целое_в_текст(счётчик));
    счётчик = счётчик + 1;
}
```

### Цикл по коллекции

```
целое[3] числа = [1, 2, 3];
для каждого элемент в числа {
    вывести(целое_в_текст(элемент));
}
```

Работает и с `Список<T>` — тип переменной цикла выводится автоматически
из типа элемента списка:

```
Список<целое> числа = Список<целое>();
числа.добавить(1);
числа.добавить(2);
для каждого элемент в числа {
    вывести(целое_в_текст(элемент));
}
```

### Досрочный выход и переход к следующей итерации

`прервать;` — немедленно выходит из ближайшего охватывающего цикла
(`пока` или `для каждого`). `продолжить;` — пропускает остаток тела
текущей итерации и переходит к следующей (для `для каждого` — к
следующему элементу).

```
целое i = 0;
пока (i < 100) {
    i = i + 1;
    если (i % 2 == 0) {
        продолжить; // пропустить чётные
    }
    если (i > 10) {
        прервать; // остановиться после 10
    }
    вывести(целое_в_текст(i));
}
```

Оба ключевых слова действуют только на САМЫЙ БЛИЖНИЙ охватывающий
цикл — во вложенных циклах `прервать` не выходит из внешнего, только
из внутреннего. Использование вне цикла — ошибка компиляции.

⚠️ **Честное ограничение**: тело `параллельно { }` компилируется в
отдельную функцию (см. раздел «Многопоточность») — `прервать`/
`продолжить` внутри него могут относиться только к циклу, объявленному
НЕПОСРЕДСТВЕННО внутри того же блока `параллельно`, не к циклу снаружи
него.

## Функции

```
функция сложить(целое а, целое б) -> целое {
    вернуть а + б;
}
```

- Тип возврата указывается через `->` после списка параметров
- `вернуть` — оператор возврата значения
- Функция без возвращаемого значения просто не пишет `-> тип`:

```
функция напечатать_дважды(текст сообщение) -> целое {
    вывести(сообщение);
    вывести(сообщение);
    вернуть 0;
}
```

### Проверка аргументов при вызове

Компилятор проверяет и количество, и типы аргументов при каждом вызове
— как обычной функции, так и функции из подключённого модуля:

```
функция сложить(целое а, целое б) -> целое { вернуть а + б; }

сложить(5);        // ошибка: функция 'сложить' ожидает 2 аргумент(ов), передано 1
сложить(5, "три"); // ошибка: несовпадение типов для аргумента 2
сложить(5, 3);     // верно
```

Параметр, объявленный как контракт, принимает любую структуру, реально
его реализующую (`структура X : ИмяКонтракта`) — не только буквально
значение самого контракта.

### Обобщённые функции

Поддержаны, с честными ограничениями — см. раздел
[Обобщённые типы](#обобщённые-типы) (там же обобщённые структуры).

## Массивы

Фиксированного размера, размер — часть типа. **Требуют явной
инициализации** литералом при объявлении:

```
целое[5] числа = [10, 20, 30, 40, 50];
числа[0] = 99;              // обращение и запись по индексу
вывести(целое_в_текст(числа[0]));
```

### Массив массивов — `тип[N][M]`

Вложенные фиксированные массивы — та же семантика, что и в C:
`тип[N][M]` — это N элементов типа `тип[M]` (первый индекс выбирает
"строку"). Глубина вложенности не ограничена (`тип[N][M][K]` тоже
работает):

```
целое[2][3] м = [[1, 2, 3], [4, 5, 6]];
вывести(целое_в_текст(м[0][2]));   // 3
м[1][0] = 99;
вывести(целое_в_текст(м[1][0]));   // 99
```

⚠️ Честное ограничение: элементы вложенного массива ограничены
скалярными типами — массив массивов **структур** (`Точка[2][2]`) не
поддержан в этой версии.

## Структуры

```
структура Точка {
    целое х;
    целое у;

    функция сумма_координат() -> целое {
        вернуть это.х + это.у;
    }
}
```

- Поля объявляются как обычные переменные, без значений по умолчанию
- Методы — обычные функции внутри тела структуры
- **`это`** — ссылка на текущий экземпляр внутри метода (аналог
  `self`/`this` в других языках)
- **Конструктор генерируется автоматически**, по всем полям в порядке
  объявления:

```
Точка точка = Точка(3, 4);
вывести(точка.сумма_координат());   // выведет 7
```

Структуры — всегда объекты в куче (передаются по ссылке), с
автоматическим подсчётом ссылок — см. [ARC](#управление-памятью-arc).

### Слабые ссылки

Поле, объявленное как `слабая Тип`, не увеличивает счётчик ссылок —
нужно для разрыва циклических ссылок (например, родитель ↔ потомок):

```
структура Цель {
    текст имя;
}

структура Держатель {
    текст имя;
    слабая Цель цель;    // не увеличивает счётчик ссылок "Цель"
}

функция главная() -> целое {
    Цель цель = Цель("моя цель");
    Держатель держатель = Держатель("держатель", цель);
    вывести(держатель.цель.имя);
    вернуть 0;
}
```

### Проверка живости — `.жива()`

Перед обращением к цели через слабую ссылку можно (и нужно) проверить,
не была ли она уже освобождена — метод `жива()` доступен на любом
доступе к полю, объявленному как `слабая`:

```
если (держатель.цель.жива()) {
    вывести(держатель.цель.имя);
} иначе {
    вывести("цель уже освобождена");
}
```

Работает безопасно даже после того, как цель "логически" умерла (её
счётчик сильных ссылок дошёл до нуля) — пока жива хотя бы одна слабая
ссылка на неё, компилятор откладывает реальное освобождение памяти
именно для того, чтобы `жива()` могла её безопасно проверить, не
рискуя обращением к уже переиспользованной памяти. Как только
последняя слабая ссылка тоже перестаёт существовать — отложенное
освобождение происходит немедленно.

## Обработка ошибок — результат\<Т\>

Вместо исключений — обёртка `результат<Т>`, содержащая три поля:
`.успешно` (`верно`), `.значение` (тип `Т`, валиден только при успехе),
`.сообщение` (текст ошибки, валиден только при неудаче).

```
функция разделить(целое а, целое б) -> результат<целое> {
    если (б == 0) {
        вернуть ошибка("деление на ноль");
    }
    вернуть успех(а / б);
}

функция главная() -> целое {
    результат<целое> итог = разделить(10, 2);
    если (итог.успешно) {
        вывести(целое_в_текст(итог.значение));
    } иначе {
        вывести("Ошибка: " + итог.сообщение);
    }
    вернуть 0;
}
```

Многие встроенные функции (`подстрока`, `найти`, `прочитать_файл` и
другие) сами возвращают `результат<Т>` — обязательно проверяй
`.успешно` перед использованием `.значение`.

## Опциональный тип — `тип?`

Для "значение либо есть, либо его нет" (без сопутствующего сообщения об
ошибке — этим он отличается от `результат<Т>` выше) есть отдельный,
более простой опциональный тип: `тип?`. Внутри — та же обёртка из двух
псевдополей: `.есть` (`верно`) и `.значение` (валидно, только если
`.есть` истинно):

```
целое? возраст = 25;       // "поднимается" неявно — просто пиши обычное значение
целое? неизвестно = неуказано;   // явное отсутствие значения

если (возраст.есть) {
    вывести(целое_в_текст(возраст.значение));
}

// Переприсваивание работает так же:
неизвестно = 30;       // теперь есть
неизвестно = неуказано;  // снова нет
```

В отличие от `результат<Т>` (требующего явного `успех(x)`/`ошибка(msg)`),
опциональный тип **неявно поднимает** обычное значение до `тип?` —
короче для частого случая "значение почти всегда есть".

### ⚠️ Честные ограничения v1

- `T` ограничен скалярными типами — целочисленные любого размера,
  дробные, `верно`. **Текст и структуры как `T` не поддержаны** — они
  потребовали бы той же ARC-инфраструктуры владения (копирование при
  обёртывании, освобождение при перезаписи/выходе из области видимости),
  что и `результат<текст>`/`результат<Структура>`, которая для
  опционального типа пока не реализована.
- Опциональный тип поддержан **только для локальных переменных** —
  как параметр функции, тип возврата функции или поле структуры он пока
  честно отклоняется с понятной ошибкой, а не падает молча.
- Нет `?`-оператора автоматического распространения (как у
  `результат<Т>` внутри функций, объявленных `-> результат<...>`) —
  разворачивать нужно вручную через `.есть`/`.значение`.

## Обобщённые типы

### Список\<T\>

```
Список<целое> числа = Список<целое>();
числа.добавить(10);
числа.добавить(20);

целое первое = числа.получить(0);
целое количество = числа.размер();

числа.удалить(0);   // удаляет элемент по индексу, сдвигая хвост влево

числа.освободить(); // как и Словарь — не освобождается автоматически, нужно явно
```

`удалить(индекс)` корректно уменьшает `размер()` на 1 и, если элементы —
структуры, освобождает (ARC) удаляемый элемент.

⚠️ Сам `Список<T>` (как и `Словарь`) не освобождается автоматически при
выходе из области видимости — вызывай `.освободить()` явно, если список
больше не нужен раньше конца программы. Для элементов-**структур**
`.освободить()` дополнительно корректно отпускает (ARC-release) счётчик
ссылок каждого элемента — если на элемент нет других ссылок (например,
через ранее сохранённый `.получить(i)`), он тоже освободится; если есть
— останется жить у той, другой ссылки. Для элементов-**текста**
(`Список<текст>`) отдельные элементы НЕ освобождаются (та же
двусмысленность литерал/malloc, что и у `Словарь.освободить()`,
см. ниже) — освобождается только сам список-контейнер.

### Словарь\<Ключ, Значение\>

```
Словарь<текст, целое> возрасты = Словарь<текст, целое>();
возрасты.положить("Аня", 25);

результат<целое> возраст = возрасты.получить("Аня");   // ключ может отсутствовать!
если (возраст.успешно) {
    вывести(целое_в_текст(возраст.значение));
}

целое количество = возрасты.размер();
возрасты.освободить();   // Словарь не участвует в ARC — освобождать явно
```

⚠️ В отличие от `Список.получить(индекс)` (возвращает значение
напрямую), `Словарь.получить(ключ)` возвращает `результат<Значение>` —
ключа может не быть в словаре, обязательно проверяй `.успешно`.

⚠️ **Важное синтаксическое ограничение**: `Список<Т>`/`Словарь<Ключ,
Значение>` нельзя объявить через вывод типа (простое присваивание без
явного типа слева) — всегда указывай тип явно, как в примерах выше.

⚠️ **`Словарь<Ключ, Значение>` не участвует в ARC** — ни как локальная переменная,
ни как поле структуры, он никогда не освобождается автоматически.
`.освободить()` — честный, явный способ вернуть память (два внутренних
массива и структуру-заголовок); отдельные текстовые ключи/значения, если
были динамически выделены, освобождает вызывающий код сам, до этого
вызова (язык не может безопасно отличить их от статических строковых
литералов).

`Список<T>`/`Словарь<Ключ, Значение>` можно использовать как поле
пользовательской структуры, с цепочками доступа вида
`это.поле.метод(...)` — см. пример в структуре `Хранилище`
(`стандартная_библиотека/хранилище.код`).

✅ **Гарантия детерминированности**: несмотря на название, `Словарь`
НЕ является настоящей хеш-таблицей с бакетами — внутри это два
параллельных массива (ключи и значения, растущие вместе) и линейный
поиск по ним (см. `сгенерировать_метод_словаря` в `src/codegen.rs`).
Хеширования, бакетов и какого-либо источника случайности (в духе
защиты от DoS-коллизий у некоторых языков) в реализации нет вовсе —
значит, порядок элементов внутри `Словаря` всегда РАВЕН порядку их
первой вставки (`положить` с новым ключом добавляет его строго в
конец) и гарантированно одинаков от запуска к запуску для одной и той
же последовательности операций, без какой-либо зависимости от ASLR,
случайного сида хеширования или платформы. Честно: сегодня в языке
ещё нет способа НАБЛЮДАТЬ этот порядок из кода на Сфере напрямую (у
`Словаря` нет ни `для каждого`, ни `.ключи()`/`.значения()` — см. выше
и честные ограничения `метрики.код`/`трейсинг.код`/`профилировщик.код`,
которые из-за этого же хранят порядок отдельным `Список<текст>`) — но
когда такая возможность появится, она унаследует эту детерминированность
БЕСПЛАТНО, если будет реализована как перебор тех же двух массивов по
индексу (а не как переход на настоящую хеш-таблицу с бакетами, что
само по себе было бы серьёзной сменой реализации, а не просто
добавлением одного метода).

### Обобщённые структуры (пользовательские)

```
структура Коробка<Т> {
    Т содержимое;
}

коробка = Коробка<целое>(42);              // вывод типа
Коробка<целое> другая = Коробка<целое>(7); // явный тип — тоже работает
вывести(целое_в_текст(коробка.содержимое));
```

Раньше явный тип слева (`Коробка<целое> коробка = ...;`) не работал —
семантика не умела сопоставить его с результатом конструктора. Снято:
теперь оба способа объявления равноценны.

**Многопараметрические обобщённые структуры (`Пара<А, Б>`)** тоже
поддержаны — любое число параметров типа, не только один:

```
структура Пара<А, Б> {
    А первый;
    Б второй;

    функция первый_значение() -> А {
        вернуть это.первый;
    }
}

Пара<целое, текст> п = Пара<целое, текст>(42, "привет");
вывести(целое_в_текст(п.первый_значение()));  // 42
вывести(п.второй);                             // привет

пара2 = Пара<целое, целое>(1, 2);              // вывод типа тоже работает
вывести(целое_в_текст(пара2.первый + пара2.второй)); // 3
```

Параметров может быть и больше двух (`структура Тройка<А, Б, Ц> { ... }`),
и они могут сами быть обобщёнными контейнерами:
`структура ПараСписков<А, Б> { Список<А> первые; Список<Б> вторые; }`.

Использование с неверным числом параметров — честная ошибка семантики
(не крах и не молчаливое усечение списка), например:
`Пара<целое>` при объявлении `Пара<А, Б>` → `'Пара<...>' объявлена с 2
параметром(ами) типа, а использована с 1 — например: 'Пара<А, Б>'`.

⚠️ **Честно унаследованное ограничение (было и раньше, не новое для
многопараметрических)**: методы шаблона проверяются семантически СРАЗУ
для КАЖДОЙ встреченной инстанциации, независимо от того, вызывается ли
конкретно этот метод на этой инстанциации. Если тело метода годится
только для НЕКОТОРЫХ конкретных типов параметра (например, использует
`целое_в_текст(это.поле)`, а поле подставляется текстом в одной из
инстанциаций), компилятор честно провалится на этой инстанциации, даже
если сам метод там ни разу не вызывается. Обходной путь — не писать в
общем шаблоне методы, зависящие от конкретного типа параметра, либо
использовать разные структуры для разных комбинаций.

### Обобщённые функции

```
функция макс_из_двух<Т>(Т а, Т б) -> Т {
    если (а > б) {
        вернуть а;
    }
    вернуть б;
}

функция главная() -> целое {
    целое итог_целое = макс_из_двух<целое>(3, 7);        // 7
    дробное итог_дробное = макс_из_двух<дробное>(2.5, 1.5); // 2.5
    вернуть 0;
}
```

⚠️ **Честные ограничения этой версии**:
- Только **один** обобщённый параметр (как и у обобщённых структур)
- Тип нужно указывать **явно** при вызове (`имя<тип>(...)`) — вывод
  типа из аргументов без явного указания не реализован
- Только функции **главного файла** — обобщённые функции из
  подключённых модулей пока не поддержаны

### Обобщённые методы структур

Отдельный от свободных обобщённых функций метод — метод СТРУКТУРЫ может
иметь собственный параметр типа, не связанный с самой структурой:

```
структура Коробка {
    целое счётчик;

    функция обернуть<Т>(Т значение) -> Т {
        это.счётчик = это.счётчик + 1;
        вернуть значение;
    }
}

функция главная() {
    Коробка к = Коробка(0);
    целое а = к.обернуть<целое>(42);       // 42, счётчик = 1
    дробное б = к.обернуть<дробное>(3.5);  // 3.5, счётчик = 2
    верно  в = к.обернуть<верно>(да);      // да, счётчик = 3
}
```

Внутри обобщённого метода можно вызывать и другие обобщённые методы той
же структуры, в том числе сам себя рекурсивно или из цикла:
`это.обернуть<Т>(значение)`.

⚠️ **Честные ограничения этой версии** (намеренно те же, что и у
обобщённых свободных функций):
- Только **один** обобщённый параметр на метод
- Тип нужно указывать **явно** при вызове (`объект.метод<тип>(...)`) —
  вывод типа из аргументов не реализован
- **Структура, которой принадлежит метод, сама не должна быть
  обобщённой** — комбинация "обобщённая структура + обобщённый метод
  внутри неё" (`структура Коробка<А> { функция м<Б>(...) {...} }`) не
  поддержана и честно отклоняется ошибкой компиляции. Обычный метод
  обобщённой структуры (без своего, ОТДЕЛЬНОГО параметра — опирающийся
  только на параметр самой структуры) работает как и раньше, без
  ограничений — ограничение именно на ВТОРОЙ, независимый уровень
  обобщения.

## Контракты и полиморфизм

Контракт — описание требуемых методов, аналог интерфейса:

```
контракт Печатаемый {
    функция напечатать() -> текст;
}

структура Кот : Печатаемый {
    функция напечатать() -> текст {
        вернуть "Мяу";
    }
}

структура Собака : Печатаемый {
    функция напечатать() -> текст {
        вернуть "Гав";
    }
}
```

Компилятор на этапе сборки проверяет, что структура, заявляющая `:
Контракт`, реально имеет все требуемые методы с совпадающими
сигнатурами.

### Настоящий полиморфизм

Контракт можно использовать как тип параметра функции или переменной —
один и тот же код тогда работает с *любой* структурой, реализующей
контракт (динамический выбор нужной реализации в момент выполнения):

```
функция озвучить(Печатаемый существо) -> целое {
    вывести(существо.напечатать());
    вернуть 0;
}

функция главная() -> целое {
    Кот кот = Кот();
    Собака пёс = Собака();

    озвучить(кот);   // выведет "Мяу"
    озвучить(пёс);   // выведет "Гав" — та же функция, другая реализация

    вернуть 0;
}
```

⚠️ **Важно**: аргумент-структуру нужно сначала сохранить в переменную —
`озвучить(Кот())` (временный экземпляр напрямую, без промежуточной
переменной) **не работает**.

### Список\<Контракт\>

Коллекция разнотипных объектов через общий интерфейс — та же идея, что
выше, но много объектов сразу:

```
Список<Печатаемый> зоопарк = Список<Печатаемый>();
зоопарк.добавить(кот);
зоопарк.добавить(пёс);

целое индекс = 0;
пока (индекс < зоопарк.размер()) {
    Печатаемый существо = зоопарк.получить(индекс);
    вывести(существо.напечатать());   // "Мяу", затем "Гав"
    индекс = индекс + 1;
}
```

✅ **Исправлено (раньше было настоящим use-after-free, не просто
утечкой)**: структуры, добавленные в `Список<Контракт>` через
`добавить(...)`, и прочитанные через `получить(...)`, теперь корректно
захватываются (ARC-retain) — счётчик ссылок объекта учитывает и
исходную переменную, и копию внутри списка. Раньше, если исходная
переменная (`Кот кот = Кот();`) выходила из области видимости раньше
списка (например, внутри функции, добавляющей объект в список,
переданный аргументом), объект освобождался, а список продолжал
хранить указатель на уже освобождённую память — реальный крах/порча
данных при следующем обращении, воспроизведённый и подтверждённый
через valgrind ("Invalid read... freed"), не просто "утечка", как это
раньше (неточно) утверждала документация. ⚠️ Теперь, раз объект
корректно захватывается, у этого честно появляется ОБРАТНАЯ сторона —
настоящая утечка (не крах): `Список<Контракт>` пока не освобождает
захваченные им ссылки — ни через `удалить()`, ни через `.освободить()`
(в отличие от обычного `Список<Структура>`, см. выше) — держать
исходные переменные (`кот`, `пёс`) живыми столько же, сколько и сам
список, по-прежнему хорошая практика, но теперь как способ не терять
память, а не как способ избежать краха.

### Контракт как тип возврата функции

Функция может быть объявлена возвращающей контракт — вызывающий код
получает объект, не зная заранее, какая именно структура за ним стоит:

```
функция создать_питомца() -> Печатаемый {
    Кот кот = Кот();
    вернуть кот;
}

функция главная() -> целое {
    Печатаемый питомец = создать_питомца();
    вывести(питомец.напечатать());   // "Мяу"
    вернуть 0;
}
```

✅ Этот случай, в отличие от `Список<Контракт>` выше, проверен и
оказался УЖЕ безопасным без дополнительных исправлений: `вернуть кот;`
не освобождает `кот` при выходе из функции (та же "переезжающая"
семантика владения, что и у обычного возврата структуры без контракта)
— владение просто переходит вызывающей стороне, без двойного счётчика
и без use-after-free. Подтверждено тестом с тремя последовательными
вызовами `создать_питомца(...)` — вывод корректен, valgrind не находит
ни одной ошибки чтения/записи (объекты-контракты, впрочем, тоже пока
не освобождаются при выходе локальной переменной из области видимости
— та же самая, уже известная категория утечки, что и у `Список<T>` без
`.освободить()`).

## Многопоточность

### параллельно

Запускает блок кода в отдельном потоке операционной системы:

```
параллельно {
    вывести("Работаю в фоне");
}
```

⚠️ **Важное ограничение**: тело блока `параллельно` **не может
использовать переменные из окружающей области видимости** (защита от
обращения к уже освобождённой памяти) — единственное исключение,
описанное ниже.

### дождаться_все_потоки()

Ждёт завершения **всех** потоков, запущенных через `параллельно` с
начала программы (или с прошлого вызова этой же функции):

```
параллельно {
    вывести("Поток 1");
}
параллельно {
    вывести("Поток 2");
}

дождаться_все_потоки();   // гарантированно оба потока уже завершились
вывести("Оба потока точно закончили работу");
```

⚠️ **Честное ограничение**: ждёт **все** потоки разом. Чтобы дождаться
одного конкретного — см. `дождаться_поток(номер)` ниже. Максимум 256
потоков, запущенных без вызова `дождаться_все_потоки()` между ними.

### дождаться_поток(номер)

Ждёт **один конкретный** поток — `номер` это порядковый индекс среди
запущенных через `параллельно` с начала программы (или с последнего
`дождаться_все_потоки()`): `0` для первого, `1` для второго и так
далее. Возвращает `целое` (0 при успехе).

```
параллельно {
    вывести("Поток 0");
}
параллельно {
    вывести("Поток 1");
}

дождаться_поток(0);   // ждёт только первый — второй мог ещё работать
вывести("Поток 0 точно закончил");
дождаться_поток(1);
вывести("Поток 1 тоже закончил");
```

⚠️ **Честные, узкие ограничения** (не проверяются во время выполнения):
- вызывать **до** `дождаться_все_потоки()` для той же партии потоков —
  тот сбрасывает внутренний учёт, после него `дождаться_поток(N)` для
  уже дождавшихся потоков ссылался бы не туда;
- не вызывать дважды с одним и тем же номером — повторное ожидание уже
  завершённого (joined) потока — неопределённое поведение POSIX.

### канал\<T\>

Безопасный способ передать одно значение из фонового потока обратно:

```
функция главная() -> целое {
    канал<целое> канал_результата = создать_канал();

    параллельно {
        целое вычислено = 2 + 2;
        канал_результата.отправить(вычислено);
    }

    целое значение = канал_результата.получить();   // ждёт, пока не придёт значение
    вывести(целое_в_текст(значение));

    вернуть 0;
}
```

Поддерживаются только целочисленные и указательные типы значения (не
дробные, не встроенные напрямую структуры).

✅ `канал<текст>` безопасен: `отправить(...)` всегда делает независимую
копию текста перед передачей (раньше это был настоящий use-after-free
между потоками — см. "Известные ограничения"). ✅ Полученный через
`получить()` текст освобождается автоматически, как и любой другой
свежий текст, а сам объект канала можно освободить явно через
`.освободить()` — подробности там же.

## Управление памятью (ARC)

Структуры управляются автоматически через подсчёт ссылок (ARC) —
писать `free`/`delete` не нужно, память освобождается сама, когда на
объект больше никто не ссылается.

Текст **частично** под управлением ARC — простые локальные переменные,
цепочки конкатенации, результаты некоторых функций и **текстовые поля
структур** отслеживаются и освобождаются автоматически.

⚠️ **Как именно устроено для полей структур**: каждое текстовое поле,
при записи (в конструкторе или прямым присваиванием `объект.поле =
...;`), автоматически получает **свою собственную копию** переданного
текста — независимо от того, был это литерал (`"Аня"`) или уже готовое,
вычисленное значение. Это гарантирует, что структура всегда владеет
содержимым своего текстового поля и может безопасно освободить его при
уничтожении — за счёт одного лишнего копирования памяти при каждой
записи такого поля.

Переприсваивание внутри циклов тоже корректно отслеживается — решение
"освобождать ли старое значение" принимается в рантайме через скрытый
флаг владения, а не один раз при компиляции (см. подробности в
`ИСТОРИЯ_РАЗРАБОТКИ.md`). Полный, честный список того, что ещё не
покрыто — в разделе "Известные ограничения" выше.

## Модули

```
подключить утилиты;
```

Подключает файл `утилиты.код` — поиск идёт по трём уровням, по порядку:

1. Рядом с текущим файлом (для разбиения своего же проекта на файлы).
2. В папке `пакеты/` в корне проекта (простое, локальное место для
   стороннего кода — сюда `сфера_пакеты` ставит зависимости, см. раздел
   "Пакетный менеджер" ниже; можно и вручную положить чужой `.код`-файл).
3. **В системной стандартной библиотеке**, установленной рядом с самим
   компилятором — именно этот уровень позволяет `подключить сеть;` (или
   `хранилище`, `база_данных`, `графика`) работать в ЛЮБОМ новом проекте,
   в любой папке, без ручного копирования файлов стандартной библиотеки
   — та же модель, что `import os` в Python: язык сам знает, где лежит
   его собственная библиотека.

⚠️ Уровень 3 требует, чтобы компилятор был установлен через `собрать.sh`
(macOS/Linux) или `установить-windows.ps1` (Windows) — они синхронно
копируют актуальную стандартную библиотеку в системное место при каждой
сборке. При разработке самого компилятора (бинарник запущен прямо из
`target/release/` внутри репозитория) поиск тоже работает — находит
`стандартная_библиотека/` в корне репозитория автоматически.

Доступ к содержимому — либо напрямую по имени, либо явно, через имя
модуля:

```
целое итог = удвоить(21);              // обычный вызов
целое итог2 = утилиты.удвоить(21);     // то же самое, но с указанием модуля
```

### Составное имя — файл внутри подпапки

```
подключить пакет.файл;
```

Каждая точка в имени — это папка: `пакет.файл` ищет `пакет/файл.код`
(на каждом из трёх уровней поиска выше — рядом с файлом, в `пакеты/`,
в системной стандартной библиотеке). Это то же самое имя `пакет.файл`,
которое парсер понимал ещё до этого изменения (`подключить а.б.в;`
разбирается на любое число частей), но раньше точка становилась частью
искомого имени файла буквально — теперь это настоящий путь. Основное
применение — как раз пакеты, установленные `сфера_пакеты` (см. ниже):
каждый пакет живёт в своей собственной папке `пакеты/ИМЯ_ПАКЕТА/`, и
файл `утилиты.код` внутри него подключается как `подключить
ИМЯ_ПАКЕТА.утилиты;`.

Имя МОДУЛЯ для квалифицированного доступа (`модуль.имя(...)`) в этом
случае — `ИМЯ_ПАКЕТА_файл` (с подчёркиванием, одно слово): `подключить
геометрия_доп.векторы;` даёт доступ через `геометрия_доп_векторы.длина(...)`.
Исключение — самый частый случай, когда у пакета один файл с тем же
именем, что и сам пакет (`пакеты/геометрия/геометрия.код`): тогда можно
писать просто `подключить геометрия;` (без точки — компилятор сам находит
файл внутри одноимённой папки пакета) и обращаться как `геометрия.площадь(...)`
— без дублирования имени.

Именно это (разные модули, `подключить`нные из разных пакетов, но с
ОДИНАКОВЫМ именем файла, например `утилиты.код` у двух не связанных друг
с другом пакетов) раньше было главной дырой в изоляции: один пакет молча
перезаписывал файл другого на диске при установке, а даже если бы не
перезаписывал — оба зарегистрировались бы под одним и тем же именем
модуля `утилиты`, и совпадение имени функции внутри них стало бы
неотличимой ошибкой "функция объявлена повторно". Составное имя
закрывает оба уровня разом: и файлы на диске, и имена модулей для
`модуль.имя(...)`, теперь действительно изолированы по пакету.

## Пакетный менеджер (`сфера_пакеты`)

Отдельный инструмент (не часть самого компилятора) для установки
стороннего кода — **git как реестр**, без собственной инфраструктуры
вроде crates.io/npm: зависимость — это просто ссылка на git-репозиторий.

Манифест `сфера.зависимости` в корне проекта (простой построчный текст):

```
геометрия = git https://github.com/кто-то/геометрия-сфера.git
графика_доп = git https://github.com/кто-то/графика-доп.git ветка=разработка описание="Доп. примитивы рисования"
```

Команды:

```
сфера_пакеты установить     # клонирует и ставит все зависимости из манифеста
сфера_пакеты список         # показывает установленные пакеты и как их подключать
сфера_пакеты удалить ИМЯ    # убирает пакет целиком
```

**Изоляция пространств имён.** Каждый пакет устанавливается в СВОЮ
собственную папку — `пакеты/ИМЯ_ПАКЕТА/`, куда копируются все `.код`
файлы из корня его репозитория. Два разных пакета могут содержать
одноимённые файлы (например, оба — `утилиты.код`) без какого-либо
конфликта: физически они лежат в разных папках, и подключаются они по
составному имени — `подключить ИМЯ_ПАКЕТА.файл;` (см. "Модули" выше).
Команда `список` для каждого пакета сразу подсказывает точную строку
`подключить ...;` для каждого его файла.

### Транзитивные зависимости

Если у самого устанавливаемого пакета внутри его репозитория тоже есть
файл `сфера.зависимости`, `сфера_пакеты установить` подхватывает и его —
не только один уровень корневого манифеста, а весь граф, обходом в
ширину. Пакет `А`, зависящий от `Б`, который зависит от `В`, ставит все
три, без ручного перечисления `Б` и `В` в манифесте `А`.

Команда `список` честно показывает, какие пакеты установлены напрямую, а
какие — транзитивно и через кого именно (`поставлен как зависимость
пакета: ...`).

Циклы (`А` зависит от `Б`, `Б` — от `А`) корректно обрываются — каждое
имя пакета обрабатывается ровно один раз.

### Разрешение версионных конфликтов

Необязательное поле `версия=X.Y.Z` в манифесте (вместо `ветка=` — они
взаимоисключающие на одной строке):

```
утилиты = git https://github.com/кто-то/утилиты-сфера.git версия=1.4.0
```

Технически это по-прежнему просто имя git-тега (передаётся в
`git clone --branch`, должно точно совпадать с тегом в репозитории
пакета — `сфера_пакеты` не подбирает варианты вроде «с `v` или без»).
Но, в отличие от `ветка`, оно ДОПОЛНИТЕЛЬНО разбирается как простая
семантическая версия (major.minor.patch) для сравнения:

Если один и тот же пакет (тот же адрес) транзитивно запрошен несколько
раз с разными версиями — требования **пересекаются как диапазоны версий**
(настоящий constraint solving, а не «побеждает большая» — см. подробнее в
разделе "Диапазоны версий" ниже): итоговая версия обязана удовлетворять
ВСЕМ требованиям, встреченным в дереве зависимостей, одновременно. Если
уже выбранная версия по-прежнему подходит под сузившийся интервал —
переустановка не нужна; если нет — пакет переустанавливается на версию,
попадающую в итоговый, пересечённый интервал. Результат не зависит от
порядка, в котором зависимости встречаются в дереве.

**Конфликт имён.** Если пакет с одним и тем же именем запрошен из
разных АДРЕСОВ (не версий одного и того же репозитория, а буквально
разных URL) — это не версионный конфликт: два разных места дерева
буквально хотят разный код под одним именем, и `сфера_пакеты` не выбирает
между ними молча. Вся установка честно проваливается с ошибкой,
называющей оба адреса и через какие пакеты каждый из них был запрошен
(корневой манифест или конкретное имя транзитивного пакета) — например:

```
Ошибка: пакет 'утилита' запрошен из двух РАЗНЫХ адресов в дереве зависимостей — ...
  - https://github.com/кто-то/утилита-а.git (запрошен напрямую в корневом сфера.зависимости)
  - https://github.com/кто-то/утилита-б.git (запрошен через пакет 'сеть')
```

Разработчик разрешает это сам — например, переименовав один из пакетов в
том `сфера.зависимости`, где он объявлен (имя пакета — это просто ключ
слева от `=`, оно не обязано совпадать с именем репозитория). Если версии
есть, но хотя бы одну из них не удалось разобрать как `X.Y.Z` — это
отдельный, более мягкий случай (тот же URL, просто версии несравнимы) —
он по-прежнему честно предупреждает и оставляет уже выбранную, а не
проваливает установку (см. выше).

### Диапазоны версий (`^X.Y.Z`, `~X.Y.Z`)

Поле `версия=` понимает не только точный тег, но и два вида диапазонов
в стиле npm/cargo:

```
сеть = git https://github.com/кто-то/сеть-сфера.git версия=^1.2.0
утилиты = git https://github.com/кто-то/утилиты-сфера.git версия=~1.2.0
```

В отличие от точной версии (которая — это по-прежнему буквально имя
git-тега), диапазон — это ТРЕБОВАНИЕ, которое нужно разрешить в
конкретный тег ПЕРЕД клонированием. Для этого `сфера_пакеты` вызывает
`git ls-remote --tags URL` (лёгкая сетевая операция, без полного
клонирования), разбирает имена всех тегов как `X.Y.Z` (необязательный
префикс `v` снимается — `v1.2.0` и `1.2.0` равнозначны) и выбирает
САМУЮ БОЛЬШУЮ версию, удовлетворяющую диапазону. Дальше эта конкретная
версия используется точно так же, как если бы она была указана
напрямую (клонируется как `--branch НАЙДЕННЫЙ_ТЕГ`, участвует в
разрешении конфликтов наравне с точными версиями).

Семантика диапазонов:

- **`^X.Y.Z`** («каре», совместимые версии): при `X > 0` разрешено
  любое `>=X.Y.Z` с тем же `X` (например `^1.2.0` допускает `1.5.0`,
  но не `2.0.0`). При `X == 0, Y > 0` — совместимость сужается до
  того же `Y` (`^0.3.1` допускает `0.3.4`, но не `0.4.0`) — как и в
  npm, версии `0.x` считаются нестабильными, поэтому даже минорная
  цифра ломает совместимость. При `X == 0, Y == 0` — разрешён только
  точно тот же `Z` (`0.0.x` считается настолько нестабильным, что
  ничего, кроме точного совпадения, не считается совместимым).
- **`~X.Y.Z`** («тильда», только патчи): разрешено `>=X.Y.Z` при тех
  же `X` и `Y` — то есть только патч-версии внутри одного минора.

Если ни один тег не удовлетворяет диапазону (либо у пакета вообще нет
тегов в формате семвера), установка честно завершается ошибкой с
объяснением, а не тихо берёт что попало.

### Настоящее пересечение диапазонов (constraint solving)

Каждое требование версии (точная версия, `^X.Y.Z` или `~X.Y.Z`)
внутренне представляется как полуоткрытый интервал версий `[ниж, верх)`
— нижняя граница включена, верхняя исключена (например, `^1.2.0` — это
`[1.2.0, 2.0.0)`, а точная версия `1.2.0` — вырожденный интервал
`[1.2.0, 1.2.1)`, содержащий ровно одну версию).

Если один и тот же пакет (тот же адрес) запрошен из разных мест дерева
зависимостей, `сфера_пакеты` не выбирает между требованиями («какое
победит»), а **пересекает** их интервалы — на каждый новый запрос
интервал становится ⊆ прежнему (или остаётся тем же, если новое
требование шире уже накопленного). Итоговый, суженный интервал должен
удовлетворять ВСЕМ требованиям, встреченным до сих пор, одновременно.

- Если уже выбранная версия пакета попадает в суженный интервал —
  ничего не происходит, переустановка не нужна (только запоминается
  более узкий интервал — на случай, если дерево зависимостей попросит
  этот пакет ещё раз, с ещё одним требованием).
- Если уже выбранная версия перестала попадать в суженный интервал —
  пакет разрешается заново (`git ls-remote --tags`, либо, если
  подходящий тег уже есть в `сфера.блокировка`, без похода в сеть — см.
  ниже), но уже в пределах нового, суженного интервала.
- Если пересечение интервалов оказывается **пустым** — то есть не
  существует версии, которая устраивала бы оба требования одновременно
  — это доказуемый, настоящий конфликт версий. Установка честно
  проваливается с ошибкой, называющей оба требования (в виде интервала
  и версии, если она уже была выбрана) и через какие пакеты каждое из
  них было запрошено, например:

```
Ошибка: настоящий конфликт версий пакета 'лог': требования из разных мест дерева
зависимостей не пересекаются — уже выбран интервал >=1.2.0, <2.0.0 (версия v1.4.0)
(запрошен через пакет 'сеть'), а новый запрос требует интервал >=1.1.0, <1.2.0
(запрошен транзитивно через пакет 'утилиты') — не существует версии, удовлетворяющей
ОБОИМ требованиям одновременно. Разрешите это вручную — ослабьте одно из требований
версии в 'сфера.зависимости', или явно зафиксируйте нужную версию.
```

Разработчик разрешает такой конфликт сам — ослабив одно из требований
версии в соответствующем `сфера.зависимости`, либо явно зафиксировав
одну и ту же совместимую версию в обоих местах.

### ⚠️ Честные ограничения v1

- Пересечение диапазонов реализовано только для версий вида `X.Y.Z`
  (major.minor.patch), точных или заданных через `^`/`~`, у пакетов с
  ОДНОГО И ТОГО ЖЕ адреса. Нет пререлизов/build-метаданных в сравнении
  (`1.2.0-rc1` сравнивается как `1.2.0`), и нет `>=`, `<=`, `*` или
  hyphen-диапазонов (`1.2.0 - 2.0.0`) из npm — только `^`, `~` и точная
  версия. Диапазоны работают только если у пакета в git реально есть
  теги вида `X.Y.Z`/`vX.Y.Z` — `сфера_пакеты` не подбирает версию по
  коммитам или веткам. Если хотя бы одно из двух требований к одному и
  тому же пакету несравнимо как семвер (например, одно место дерева
  просит `ветка=...` или версию вообще не указывает) — пересекать
  нечего: `сфера_пакеты`, как и раньше, честно предупреждает в консоль и
  оставляет уже выбранную версию, вместо того чтобы гадать.
- Разные адреса под одним именем пакета не разрешаются — да и не могут:
  это не версия, а разный код. Реакция — честный отказ всей установки с
  ошибкой (см. выше), а не молчаливый выбор. Нет автоматического способа
  «подружить» два таких пакета (например, через алиасы) — только ручное
  переименование одного из них разработчиком.
- `сфера_пакеты удалить` и `список` также узнают старый, плоский формат
  установки (`пакеты/файл.код` напрямую, без подпапки — как ставилось
  ДО появления изоляции пространств имён) — для плавного перехода, но
  предупреждают переустановить зависимость, чтобы получить изоляцию;
  для этого старого формата защита при удалении (см. ниже) не работает.

### Защита при удалении

`удалить ИМЯ` проверяет, не требуется ли этот пакет другим уже
установленным пакетам, и по умолчанию отказывает, если да:

```
$ сфера_пакеты удалить утилита
Ошибка: пакет 'утилита' требуется другим установленным пакетам: б, с — ...
        повтори команду с флагом --force.
```

Список требователей собирается во время последнего `установить` — при
обходе дерева зависимостей (BFS) фиксируется КАЖДЫЙ пакет, объявивший
данный своей зависимостью (не только первый — если и `б`, и `с`
одновременно требуют `утилита`, оба попадут в список, даже если `утилита`
была установлена/переустановлена только один раз). Список сохраняется в
метаданные пакета (поле `требуется_пакетами=`, видно и в `список`). При
удалении из него отфильтровываются те требователи, что уже сами удалены
(если у `имя_требователя` больше нет своей папки в `пакеты/` — он не
живой, предупреждать не о чем).

Если предупреждение — осознанный выбор (переустановишь или сам поправишь
зависимости требователей), команда принимается с флагом `--force` —
удаление проходит, но с явным предупреждением в консоль о том, кто
по-прежнему требует удаляемый пакет.

**Честная граница:** это снимок на момент последнего `установить`, а не
живой, постоянно поддерживаемый граф зависимостей — `сфера_пакеты` не
хранит такой граф между запусками вообще. Если зависимости поменяли
вручную (не через `сфера_пакеты установить`) после этого снимка, список
требователей может быть неточным (устаревшим или неполным). Для старого,
плоского формата установки (см. выше) защита не работает вовсе — там
метаданные о требователях никогда не записывались.

### Файл блокировки (`сфера.блокировка`)

Диапазоны версий (`^`/`~`) намеренно нестабильны во времени — у пакета
могут появиться новые теги, и `git ls-remote` в следующий раз найдёт уже
другой, более новый максимум. Это удобно для разработки, но плохо для
воспроизводимости: тот же `сфера_пакеты установить` на другой машине (или
через неделю) мог бы тихо поставить другую версию. `сфера.блокировка`
решает это — после каждого успешного `установить` она перезаписывается
целиком, тем же построчным форматом, что и у `сфера.зависимости`, но
версия в ней всегда УЖЕ разрешённый конкретный тег, никогда `^`/`~`:

```
утилита = git https://github.com/кто-то/утилита-сфера.git версия=1.8.0
```

При следующем `установить`, встретив диапазон в манифесте, `сфера_пакеты`
сначала смотрит в блокировку: если для этого имени и АДРЕСА там уже есть
тег, и он всё ещё удовлетворяет ТЕКУЩЕМУ диапазону из манифеста —
используется он напрямую, без обращения к `git ls-remote` (экономия сети
и, главное, гарантия того же результата, а не более новой версии внутри
того же диапазона). Если тег из блокировки диапазону больше не
удовлетворяет (диапазон в манифесте сознательно сузили) — версия
разрешается заново, и блокировка перезаписывается новым результатом. Флаг
`--обновить-блокировку` игнорирует файл целиком и разрешает все диапазоны
заново (например, чтобы сознательно перейти на новейшие версии,
удовлетворяющие текущим диапазонам).

Пакеты, установленные через `ветка=` (или вовсе без поля `версия=`), в
блокировку не попадают — ветка не семвер, фиксировать её как "версию"
было бы нечестной подменой понятий; `git clone --branch` для них всегда
берёт актуальную голову ветки, блокировки для них попросту нет.

**Честные ограничения:**
- Блокировка хранит только ОДНУ, ИТОГОВУЮ версию на имя пакета — ту, что
  победила при разрешении конфликтов (см. выше). Если несколько мест в
  дереве запрашивают один и тот же пакет с разными диапазонами, и один из
  них проигрывает (побеждает БОЛЬШАЯ версия) — для проигравшего диапазона
  блокировка не поможет напрямую (итоговая версия может не удовлетворять
  ЕГО исходному диапазону), и разрешение для него всё равно пойдёт через
  `git ls-remote`; результат всё равно сойдётся к тому же итогу, просто
  без экономии сети для этого конкретного места.
- Не защищает от переименования/удаления самого тега в репозитории
  пакета (если тег `1.8.0` потом удалили и создали заново на другом
  коммите — блокировка знает только имя тега, не хэш коммита).
- Файл предполагается коммититься в git проекта (как `Cargo.lock` /
  `package-lock.json`) — `сфера_пакеты` сама этого не делает.

### Публичный индекс пакетов (`искать` / `добавить` / `индекс-*`)

Раньше, чтобы поставить чужой пакет, нужно было заранее знать его
git-адрес — взять его было решительно неоткуда. Индекс закрывает именно
это: один git-репозиторий с одним каталог-файлом внутри (`имя = git URL
описание="..."`, тот же формат, что и у `сфера.зависимости`), который
можно искать и добавлять из него в свой проект.

Настраивается один раз на машину (не на проект):

```
сфера_пакеты индекс-настроить URL_ИНДЕКСА   # запоминает адрес в ~/.сфера/
сфера_пакеты индекс-обновить                # клонирует/обновляет локальный кэш
```

Дальше — в любом проекте:

```
сфера_пакеты искать математика     # ищет по имени и описанию в каталоге
сфера_пакеты добавить математика   # дописывает готовую строку в сфера.зависимости
сфера_пакеты установить            # как обычно — реально ставит
```

`добавить` только правит `сфера.зависимости` (не устанавливает сам
пакет) — намеренно: между «нашёл и добавил в манифест» и «реально
поставил в `пакеты/`» всегда остаётся отдельный, явный шаг, так же, как
`установить` уже отдельно от `искать`/`добавить`.

Публикация своего пакета в индекс — pull request с одной новой строкой
в его `каталог.пакеты` (или прямое редактирование, если репозиторий
свой), не загрузка на какой-то сервер: сам индекс — это только git,
никакой новой инфраструктуры `сфера_пакеты` не запускает.

⚠️ **Честно, сознательно временное решение, не финальное.** Это первый,
самый лёгкий шаг к полноценному реестру. Следующий, гораздо больший шаг
(когда будет куплен домен и сервер) — настоящий веб-сервис с базой
данных и HTTP API для поиска и публикации, полностью заменяющий этот
git-индекс, а не дополняющий его.

## Отладчик

Флаг `-g` (или `--отладка`) встраивает в объектный файл настоящую
DWARF-отладочную информацию через LLVM `DebugInfoBuilder` — тот же
самый механизм, которым пользуется clang для C/C++. Никакого
собственного, отдельного инструмента отладки при этом не появляется —
запускается уже установленный **lldb** или **gdb**, как для любой
другой скомпилированной программы:

```bash
запустить программа.код -g -c
lldb ./программа
# (b программа.код:10   — точка останова по номеру строки
#  run                  — запустить
#  next / step          — шаг с обходом/входом в вызовы
#  bt                   — стек вызовов
#  continue)
```

Работает без каких-либо ограничений:

- Точки останова по номеру строки (`b файл.код:N`) — для любой функции
  и метода программы, включая тело `параллельно { ... }`.
- Пошаговое выполнение (`next`/`step`/`continue`).
- Полноценный стек вызовов (`bt`) с настоящими именами функций/методов
  «Сферы» на каждом уровне.
- Просмотр исходного кода прямо в отладчике (строка `-> N` перед
  текущей позицией).

✅ Проверено напрямую в этой среде разработки: и lldb (18.1.3), и gdb
(15.1) корректно останавливаются на нужной строке, шагают по коду и
строят стек вызовов через несколько функций подряд, включая переход из
потока `параллельно` обратно в породившую его функцию. Каждый
собранный с `-g` объектный файл дополнительно прогоняется через
`opt -passes=verify` в рамках тестирования — эта проверка поймала (и
позволила исправить) два реальных бага в самой генерации debug-info,
прежде чем они попали бы к пользователю языка (см. подробности и то,
как именно они проявлялись, в ИСТОРИЯ_РАЗРАБОТКИ.md).

⚠️ **Честно осталось на будущее (не реализовано в этой версии)**:
просмотр значений локальных переменных ПО ИМЕНИ (`print х`,
`frame variable`) пока не поддержан — компилятор не описывает точный
DWARF-тип для локальных переменных и параметров. Причина не в лени, а
в объёме: для этого понадобилось бы построить полноценное
DWARF-описание (`DIType`) для КАЖДОГО типа языка — не только `целое`/
`дробное`/`верно`, но и `текст` (показывать как C-строку или как сырой
указатель?), пользовательские структуры (с именами и типами полей,
включая вложенные и рекурсивные поля), `Список<T>`/`Словарь<К,З>`
(обобщённые контейнеры) и контракты (толстые указатели
`{данные, vtable}`) — то есть отдельная, довольно большая по объёму
работа, а не расширение уже сделанного. lldb/gdb всё равно способны
показать сырые байты по известному адресу (`x/8xb $rsp+...`), просто
не «красиво», по имени переменной с типом «Сферы».

На **macOS** дополнительно нужен шаг `dsymutil` после сборки — формат
Mach-O, в отличие от Linux/ELF, не встраивает debug-info прямо в
исполняемый файл, оставляя её в `.o`; `dsymutil` собирает из неё
отдельный `.dSYM`-бандл, без которого lldb на Mac не найдёт номера
строк. Компилятор делает это автоматически при `-g` на macOS (см.
`слинковать_исполняемый_файл` в `src/main.rs`) — ⚠️ этот шаг физически
не тестировался (песочница для разработки компилятора — Linux, без
доступа к macOS); сам механизм — стандартный, документированный Apple
инструмент, но перепроверить его на реальном Mac ещё стоит.

## Компиляция под другую архитектуру процессора

По умолчанию компилятор собирает программу под ту же архитектуру, на
которой сам запущен. Флаг `--целевая-платформа` позволяет указать
любую другую — компилятор построен поверх LLVM, который уже умеет
генерировать код для множества архитектур, не только для той, что "под
рукой":

```bash
запустить программа.код -c --целевая-платформа aarch64-linux-gnu
```

Полученный файл — самый обычный, настоящий исполняемый файл под
указанную архитектуру (можно проверить командой `file имя_программы`).
Для запуска на машине с другой архитектурой нужен либо компьютер с
реальным таким процессором, либо эмуляция (например, `qemu-aarch64`
для ARM64 на Linux).

⚠️ **Честное ограничение**: для итоговой линковки нужен установленный
кросс-компилятор под целевую платформу (например,
`gcc-aarch64-linux-gnu` для ARM64 на Debian/Ubuntu) — сам компилятор
Сферы это не устанавливает автоматически.

### Компиляция под Android

Требует дополнительно флаг `--android-sysroot ПУТЬ` — путь к папке
`sysroot` из настоящего Android NDK
(`toolchains/llvm/prebuilt/linux-x86_64/sysroot/`), плюс номер
API-уровня прямо в тройке платформы:

```bash
запустить программа.код -c --целевая-платформа aarch64-linux-android21 \
    --android-sysroot /путь/к/ndk/toolchains/llvm/prebuilt/linux-x86_64/sysroot
```

✅ Проверено полностью, включая реальный запуск на физическом
Android-устройстве через Termux (не только структура файла) —
программа со структурой, методом и циклом отработала корректно.

#### Компиляция, линковка и запуск прямо внутри APK (без root, без Termux)

Кросс-компиляция описанным выше способом даёт исполняемый файл, но
чтобы его на Android ещё и **запустить**, обычно нужен root или
Termux — у обычного приложения нет прав исполнять файл, скачанный или
созданный во время работы (политика W^X). Это решено без root и без
Termux: сам компилятор `запустить`, линковщик `ld.lld` и небольшая
Sfera-замена `clang` (переводит вызов вида `clang ...` в правильный
вызов `ld.lld` с нужными путями) кросс-собраны под ARM64 и зашиты в
APK как файлы `lib/arm64-v8a/*.so` — Android распаковывает всё, что
лежит в `lib/<abi>/` и называется `lib*.so`, с правом на исполнение,
это и используется (легальный, документированный приём, не эксплойт).
Дальше внутри приложения `запустить` вызывается как обычная внешняя
команда (через `выполнить_команду`, то есть `system()` — на Android
это работает, вопреки более раннему предположению в этом файле и в
комментариях `панель_android.код`, что прямого доступа к оболочке
нет), с явно выставленным `LD_LIBRARY_PATH` и заранее подготовленным
`--android-sysroot` (символьные ссылки на `crtbegin`/`crtend` и
системные `.so` из собственного каталога библиотек приложения — сам
NDK на устройстве не нужен).

Подводных камней два, оба честно стоят того, чтобы их упомянуть:

- Имя файла в `lib/arm64-v8a/` обязано заканчиваться ровно на `.so`
  — иначе Android его при установке вообще не распакует, и линковка
  падает с `library ... not found`, даже если `LD_LIBRARY_PATH`
  указан правильно. Любой файл тулчейна, у которого родное имя не
  оканчивается на `.so` (например, `libunwind.so.1`, объектные файлы
  `crtbegin`/`crtend`), нужно переименовать/пересобрать с
  `.so`-суффиксом и поправить `SONAME`/`DT_NEEDED` через `patchelf`.
- Путь до собственного каталога библиотек приложения на устройстве
  заранее не известен (зависит от установки) — он находится изнутри
  самой Сферы, без единой строчки на C, через чтение
  `/proc/self/maps` и поиск подстроки `/lib/arm64/libmain.so`.

✅ Подтверждено самим `adb logcat`, многократно: полный цикл
компиляция → линковка → **запуск** результата, целиком на устройстве,
с настоящим выводом собранной программы. Эта возможность встроена в
основную панель-приложение (`панель_android.код`, вкладка «Запуск»,
функция `выполнить_код_сферы`) — компиляция и запуск в ней проверены
по отдельности, но именно эта, собранная вместе с интерфейсом панели
сборка ⚠️ ещё не проверена вживую на устройстве.

## Работа с сетью (TCP-сокеты)

Прямой доступ к системным сетевым функциям (POSIX) через тот же FFI-механизм,
что используется для графики (`подключить сеть;`, аналогично `графика.код`).
Нет отдельного, встроенного HTTP-клиента — вместо этого даны сами
"кирпичики" (сокеты), из которых HTTP собирается на самой Сфере, тем же
способом, каким `Список`/`Словарь` — просто библиотечный код, а не магия
компилятора.

```
подключить сеть;

функция главная() -> целое {
    целое32 сокет = создать_сокет(целое32(2), целое32(1), целое32(0));

    текст адрес_сервера = построить_адрес_сервера("93.184.216.34", целое32(80));
    подключиться(сокет, адрес_сервера, целое32(16));

    текст запрос = "GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n";
    отправить_данные(сокет, запрос, длина(запрос), целое32(0));

    текст буфер = выделить_память(4096);
    целое получено = получить_данные(сокет, буфер, 4090, целое32(0));
    записать_целое32(буфер, получено, целое32(0));   // нуль-терминатор
    вывести(прочитать_текст_по_смещению(буфер, 0));

    закрыть_сокет(сокет);
    вернуть 0;
}
```

⚠️ **Важно про `получить_данные` (`recv`)** — TCP не гарантирует, что все
отправленные сервером данные придут за один вызов. Для полного ответа
нужно читать **в цикле**, пока `получить_данные` не вернёт `0`
(соединение закрыто — гарантированно произойдёт, если запрос содержал
`Connection: close`):

```
текст полный_ответ = "";
верно продолжать = да;
пока (продолжать) {
    текст буфер = выделить_память(4096);
    целое получено = получить_данные(сокет, буфер, 4090, целое32(0));
    если (получено > 0) {
        записать_целое32(буфер, получено, целое32(0));
        полный_ответ = полный_ответ + прочитать_текст_по_смещению(буфер, 0);
    } иначе {
        продолжать = нет;
    }
}
```

⚠️ **`построить_адрес_сервера` принимает только числовой IP-адрес**, не
доменное имя ("93.184.216.34", не "example.com") — настоящий DNS-резолвинг
(превращение домена в IP) пока не реализован, это честно названный
следующий шаг.

### Серверная сторона — простой HTTP-сервер

`bind`/`listen`/`accept` — то, что нужно, чтобы не только подключаться к
чужим серверам, но и принимать подключения самому:

```
подключить сеть;

// AF_INET = 2, SOCK_STREAM = 1 (TCP), SOL_SOCKET = 1, SO_REUSEADDR = 2.
функция главная() -> целое {
    целое32 слушающий_сокет = создать_сокет(целое32(2), целое32(1), целое32(0));

    текст включено = выделить_память(4);
    записать_целое32(включено, 0, целое32(1));
    настроить_сокет(слушающий_сокет, целое32(1), целое32(2), включено, целое32(4));

    текст адрес = построить_адрес_сервера("0.0.0.0", целое32(8080));
    привязать_сокет(слушающий_сокет, адрес, целое32(16));
    слушать_сокет(слушающий_сокет, целое32(10));

    целое32 клиент = принять_подключение(слушающий_сокет, нулевой_указатель_сети(), нулевой_указатель_сети());

    текст буфер_запроса = выделить_память(2048);
    получить_данные(клиент, буфер_запроса, 2047, целое32(0));

    текст тело = "<html><body><h1>Привет!</h1></body></html>";
    текст ответ = "HTTP/1.1 200 OK\r\nContent-Type: text/html\r\nContent-Length: "
        + целое_в_текст(длина(тело)) + "\r\n\r\n" + тело;
    отправить_данные(клиент, ответ, длина(ответ), целое32(0));

    закрыть_сокет(клиент);
    закрыть_сокет(слушающий_сокет);
    вернуть 0;
}
```

Полный, рабочий пример (с параллельной обработкой каждого подключения в
своём потоке и простой маршрутизацией по пути — разные страницы для
разных адресов, честная страница `404` для остального) —
`examples/веб/http_сервер.код`. Проверено объективно: несколько
НАСТОЯЩИХ одновременных запросов через `curl` (в фоне, параллельно)
получают разные, корректные HTTP-ответы, не дожидаясь друг друга по
очереди.

⚠️ Пока нет URL-декодирования — маршруты держатся на ASCII (`/about`, не
кириллические), так как браузеры и `curl` всегда %-кодируют не-ASCII
символы в пути запроса — это следующий, отдельный шаг в сторону
настоящего веб-сервера.

## Работа с базой данных (SQLite)

`стандартная_библиотека/база_данных.код` — обёртка над SQLite через
прямой FFI, тем же способом, каким `графика.код` обёрнута вокруг SDL2.
SQLite выбрана как стартовая база данных сознательно — она встраиваемая
(вся база — один файл, без отдельно запущенного сервера, без сети, без
пароля), что прямо совпадает с уже проверенной моделью FFI к SDL2.

⚠️ Честно, открыто: это временное, стартовое решение — стратегическая
цель куда амбициознее: собственная, написанная на самой "Сфере" система
хранения данных, без зависимости от какой-либо внешней библиотеки.

```
подключить база_данных;

функция главная() -> целое {
    результат<текст> бд_результат = открыть_базу("пример.db");
    текст бд = бд_результат.значение;

    выполнить_sql(бд, "CREATE TABLE IF NOT EXISTS пользователи (id INTEGER PRIMARY KEY, имя TEXT);");

    // Параметризованная вставка через "?" — безопасно, без риска
    // SQL-инъекции (в отличие от склейки строк).
    текст stmt_буфер = выделить_память(8);
    sqlite_подготовить(бд, "INSERT INTO пользователи (имя) VALUES (?);", целое32(-1), stmt_буфер, нулевой_указатель_бд());
    текст stmt = прочитать_указатель(stmt_буфер, 0);
    sqlite_привязать_текст(stmt, целое32(1), "Никита", целое32(-1), целое(-1));
    sqlite_шаг(stmt);
    sqlite_завершить(stmt);

    sqlite_закрыть(бд);
    вернуть 0;
}
```

Полный, рабочий пример (с CREATE TABLE, параметризованной вставкой и
чтением через SELECT) — `examples/веб/база_данных_пример.код`. Проверено
объективно: реальная утилита `sqlite3` командной строки подтверждает
записанные данные в файле базы; `valgrind` — 0 ошибок, 0 утечек.

⚠️ Пятый аргумент `sqlite_привязать_текст` (деструктор) обязательно
`целое` (64-битный тип), не `целое32` — это специальное значение
указателя `SQLITE_TRANSIENT`, а не число; при 32-битном типе SQLite
получает неверное значение и падает при освобождении подготовленного
выражения.

## Собственное хранилище данных (без внешних зависимостей)

`стандартная_библиотека/хранилище.код` — в отличие от `база_данных.код`
(обёртка над SQLite), это простое хранилище "ключ → значение", полностью
написанное на самой "Сфере", без единой внешней библиотеки. Формат —
append-only лог (как в Bitcask): каждое изменение дописывается в конец
файла, ничего не перезаписывается на месте; поиск сканирует файл целиком
(`O(n)` на запрос) — простое, честное первое решение, не самое быстрое.

```
подключить хранилище;

функция главная() -> целое {
    сохранить("данные.db", "имя", "Никита");

    результат<текст> итог = получить("данные.db", "имя");
    если (итог.успешно) {
        вывести(итог.значение);
        освободить_память(итог.значение);   // свежая копия, не ссылка
    }

    удалить("данные.db", "имя");
    вернуть 0;
}
```

Полный, рабочий пример (сохранение, чтение, обновление значения,
удаление, несуществующий ключ) — `examples/хранилище/хранилище_пример.код`.
Проверено объективно: все операции дают правильный результат, `valgrind`
— 0 ошибок, 0 утечек (при аккуратном освобождении возвращённых значений
вызывающей стороной — как и для `прочитать_файл`).

⚠️ Два новых, отдельных встроенных инструмента для этого понадобились и
добавлены в сам компилятор: `размер_файла(путь)` (размер в байтах, без
чтения содержимого) и `дописать_в_файл_бинарно(путь, буфер, размер)`
(append с явным размером, не через `strlen` — безопасно для данных с
нулевыми байтами внутри, в отличие от уже существующей `записать_файл`).

### Ускоренный доступ — структура `Хранилище` с индексом в памяти

Свободные функции выше сканируют файл целиком на каждый запрос — честно,
просто, но `O(n)`. Структура `Хранилище` строит индекс "ключ → позиция в
файле" один раз при открытии, дальше `.получить(ключ)` находит запись
мгновенно (обращение к `Словарь` в памяти) и читает с диска РОВНО нужный
диапазон байт (через новую `прочитать_часть_файла`), не файл целиком.

```
подключить хранилище;

функция главная() -> целое {
    результат<Хранилище> хр_результат = открыть_хранилище("данные.db");
    если (!хр_результат.успешно) { вернуть 1; }
    Хранилище хр = хр_результат.значение;

    хр.сохранить("имя", "Никита");
    результат<текст> итог = хр.получить("имя");
    если (итог.успешно) {
        вывести(итог.значение);
        освободить_память(итог.значение);
    }

    закрыть_хранилище(хр);   // освобождает индекс в памяти
    вернуть 0;
}
```

Полный пример — `examples/хранилище/хранилище_с_индексом_пример.код`.
Проверено объективно: `valgrind` — 0 ошибок, 0 утечек.

⚠️ **Значимое, общее расширение самого компилятора понадобилось для
этого** — раньше `Словарь<Ключ, Значение>`/`Список<T>` нельзя было использовать как
поле пользовательской структуры (цепочки доступа вида `это.поле.метод()`
не поддерживались, только простые переменные) — это универсальное
ограничение убрано, теперь работает для любой структуры, не только
`Хранилище`.

⚠️ Новый метод `Словарь<...>.освободить()` — `Словарь` никогда не
участвует в ARC автоматически (ни как переменная, ни как поле), поэтому
нужен явный способ вернуть память. Честно, узко: освобождает только то,
что сам `Словарь` гарантированно выделил (два внутренних массива,
структуру-заголовок) — НЕ освобождает отдельные текстовые ключи/значения
по одному (первая попытка сделать так крашилась: язык не различает
динамически выделенный текст и статический строковый литерал — оба
выглядят одинаково на уровне типов, и `free()` на литерале — падение).
Если ключи/значения сами были динамически выделены, их освобождение —
ответственность вызывающего кода, как и для `текст` вообще везде в языке.

### Компактификация — `сжать_хранилище`

Append-only лог растёт со временем даже для небольшого числа ключей —
каждое обновление добавляет новую запись, не заменяет старую на месте.
`сжать_хранилище` переписывает файл, оставляя только самые свежие записи
(по одной на ключ), выбрасывая устаревшие значения и tombstone от
удалённых ключей.

```
результат<Хранилище> хр_сжатое = сжать_хранилище(хр);
если (хр_сжатое.успешно) {
    Хранилище хр2 = хр_сжатое.значение;
    // ... хр (старое значение) больше не используется
}
```

Полный пример — `examples/хранилище/хранилище_сжатие_пример.код`.
Проверено объективно: файл сокращается с 196 до 58 байт при сохранении
корректности всех данных.

⚠️ Не требует перебора самого `Словаря` (язык этого пока не умеет) —
вместо этого пересканирует файл и для каждой записи проверяет, совпадает
ли её смещение с тем, что сейчас в индексе для этого ключа — совпадает
значит это самая свежая версия. Добавлена ещё одна новая встроенная
функция — `переименовать_файл(старый, новый)` (портативная замена через
C `rename()`) — заменяет исходный файл только что собранным.

⚠️ Та же узкая утечка ключей, что и у `Словарь<...>.освободить()` выше,
применима и здесь — каждый ключ индекса, построенного заново при сжатии,
это свой malloc-буфер, который `закрыть_хранилище` не освобождает
(честное следствие уже описанного ограничения, не отдельная проблема).

⚠️ Честно: это простое хранилище "ключ → значение", не полноценная
реляционная база — для SQL-запросов, индексов, транзакций всё ещё нужен
`база_данных.код`.

| `переименовать_файл(старый, новый)` | Портативная замена файла (C `rename()`) |
| `выполнить_команду(команда)` | Запуск команды операционной системы |
| `аргументы_командной_строки()` | Аргументы запуска программы → `Список<текст>` |

### Память "по смещению" (для низкоуровневой работы)

| Функция | Описание |
|---|---|
| `прочитать_целое32(буфер, смещение)` | Чтение 4 байт из буфера |
| `записать_целое32(буфер, смещение, значение)` | Запись 4 байт в буфер |
| `прочитать_текст_по_смещению(буфер, смещение)` | Чтение строки по адресу |
| `байт_текста(текст, индекс)` | Чтение одного байта текста (0-255) |
| `прочитать_указатель(буфер, смещение)` | Чтение 8-байтового указателя из памяти |

### Время

| Функция | Описание |
|---|---|
| `юникс_время()` | Текущее unix-время — целые секунды с 1970-01-01 UTC |
| `монотонное_время_нс()` | Монотонные часы, наносекунды — НЕ календарная дата (точка отсчёта произвольная), не переводятся назад при коррекции системного времени; полезна только РАЗНИЦА двух вызовов. Для измерения длительности (см. `трейсинг.код` ниже), не для меток времени в логах. |

## Отслеживание: логи, метрики, трейсинг, профилировщик

Система наблюдаемости языка — постепенно наращиваемые модули поверх
одной идеи (см. ИСТОРИЯ_РАЗРАБОТКИ.md, где подробно описан замысел):
**логи**, **метрики**, **трейсинг**, **профилировщик**.

### Логи (стандартная_библиотека/лог.код)

```
подключить лог;

функция главная() -> целое {
    Логгер логгер = создать_логгер(уровень_инфо(), да, "приложение.log");

    лог_инфо(логгер, "сервер запущен");
    лог_предупреждение(логгер, "конфиг не найден, используются значения по умолчанию");
    лог_ошибка(логгер, "не удалось подключиться к базе данных");

    вернуть 0;
}
```

`создать_логгер(минимальный_уровень, в_консоль, путь_к_файлу)`:
- `минимальный_уровень` — сообщения строже этого уровня отбрасываются
  молча (обычная модель "что видно в проде" / "что видно при отладке");
  задаётся одной из именованных функций `уровень_отладка()` /
  `уровень_инфо()` / `уровень_предупреждение()` / `уровень_ошибка()` /
  `уровень_критическая()`, а не магическим числом напрямую.
- `в_консоль` — печатать ли через `вывести(...)`.
- `путь_к_файлу` — куда дописывать строки лога; `""` отключает запись
  в файл (дописывается через `дописать_в_файл_бинарно`, то есть
  безопасно для одновременной записи из нескольких запусков программы —
  каждая запись это отдельный `write()` в конец файла).

Пять функций записи — `лог_отладка`/`лог_инфо`/`лог_предупреждение`/
`лог_ошибка`/`лог_критическая(логгер, сообщение)` — каждая строка
получает метку времени и уровень автоматически:

```
[2026-09-29 19:42:46] ОШИБКА: не удалось подключиться к базе данных
```

Метка времени — **собственная реализация** (без вызова C
`strftime`/`localtime` — тот же принцип "без внешней зависимости",
что и у `хранилище.код`): раскладывает unix-время на год/месяц/день/
час/минуту/секунду напрямую, алгоритмом Говарда Хиннанта
"civil_from_days" — тот же алгоритм, что лежит в основе `<chrono>` из
C++20. Функции `время_из_unix(unix_секунды) -> ДатаВремя` и
`дата_время_в_текст(ДатаВремя) -> текст` доступны и отдельно, не
только внутри логгера.

⚠️ **Честно, узко (v1)**:
- Время всегда **UTC**, не местный часовой пояс — учёт часового пояса
  и перехода на летнее/зимнее время конкретного региона отдельная,
  более сложная задача.
- Поддержаны только даты **после 1970-01-01** (неотрицательные
  unix-времена).
- Пока нет структурированных полей (`ключ=значение`) сверх самого
  текста сообщения, и нет вывода в JSON — только человекочитаемая
  строка. Запланировано следующим шагом.
- Как и у любой строки, построенной через `+`/интерполяцию и не
  сохранённой в переменную, промежуточные буферы форматирования одной
  записи лога честно утекают (тот же принятый во всём языке компромисс
  "утечка, не крах" — см. раздел про ARC выше) — при активном
  логировании это стоит иметь в виду до тех пор, пока не будет
  отдельного решения для этого класса утечек в масштабах всего языка.

### Метрики (стандартная_библиотека/метрики.код)

Второй кирпич системы наблюдаемости — счётчики и измерители, та же
модель, что в Prometheus/StatsD/большинстве промышленных систем:

- **счётчик** (counter) — только растёт (запросов обработано, ошибок
  случилось). Сбрасывается в ноль только перезапуском программы.
- **измеритель** (gauge) — текущее значение, может расти и падать
  (открытых соединений сейчас, занято памяти, температура датчика).

```
подключить метрики;

функция главная() -> целое {
    Метрики м = создать_метрики();

    счётчик_увеличить_на_единицу(м, "запросы_всего");
    счётчик_увеличить(м, "ошибок_всего", 2);

    измеритель_установить(м, "открытых_соединений", 5.0);
    измеритель_увеличить(м, "открытых_соединений", 2.0);
    измеритель_уменьшить(м, "открытых_соединений", 1.0);

    метрики_напечатать(м);

    вернуть 0;
}
```

API:
- `создать_метрики() -> Метрики`
- `счётчик_увеличить(м, имя, на)` / `счётчик_увеличить_на_единицу(м, имя)`
  / `счётчик_значение(м, имя) -> целое` — счётчик заводится с нуля при
  первом обращении, дальше только прибавляет; не может убывать.
- `измеритель_установить(м, имя, значение)` (устанавливает РОВНО в
  значение) / `измеритель_увеличить(м, имя, на)` /
  `измеритель_уменьшить(м, имя, на)` / `измеритель_значение(м, имя) -> дробное`
- `метрики_снимок(м) -> текст` — снимок ВСЕХ метрик в текстовом формате
  [Prometheus exposition format](https://prometheus.io/docs/instrumenting/exposition_formats/)
  (`# TYPE имя counter\nимя значение\n`) — тот же формат, который отдаёт
  любой настоящий `/metrics`-эндпоинт, значит его понимает реальный
  Prometheus-сервер без переделки. Строки идут в порядке РЕГИСТРАЦИИ
  метрики (первого обращения к её имени).
- `метрики_напечатать(м)` — печатает снимок через `вывести(...)`.
- `метрики_записать_файл(м, путь) -> результат<верно>` — ПЕРЕЗАПИСЫВАЕТ
  файл целиком (не дописывает, в отличие от `лог.код`) — снимок метрик
  это текущее состояние на момент вызова, а не история событий.

⚠️ **Честно, узко (v1)**:
- Нет **гистограмм** (распределение величины — например, "сколько
  запросов уложилось в 10мс, сколько в 100мс, сколько дольше" — нужно
  для процентилей задержки) — задумано отдельным следующим шагом.
- Нет **меток** (labels — Prometheus умеет
  `запросы{путь="/логин", код="200"}`, здесь только плоское имя
  метрики).
- ✅ **Отдача снимка по HTTP** — рабочий пример
  `examples/веб/наблюдаемость_http.код`: `/metrics` отдаёт
  `метрики_снимок(...)` с заголовком `Content-Type: text/plain;
  version=0.0.4; charset=utf-8` — тем же, по которому настоящий
  Prometheus-сервер узнаёт формат и может скрейпить эндпоинт без
  дополнительной настройки. См. подробности (и честное упрощение —
  обработка запросов строго последовательная, не параллельная, из-за
  отсутствия потокобезопасности у `Метрики`/`Трейсер`) в разделе про
  трейсинг ниже.

### Трейсинг (стандартная_библиотека/трейсинг.код)

Третий и последний из первоначально задуманных кирпичей — "спаны"
(span, именованные, размеченные по времени участки выполнения,
вложенные друг в друга, как скобки), с человекочитаемым деревом
длительностей на выходе. Та же модель, что в реальных системах
трассировки (OpenTelemetry, Jaeger, Zipkin, "flame graph").

```
подключить трейсинг;

функция обработать_запрос(Трейсер т) {
    спан_начать(т, "обработать_запрос");

    спан_начать(т, "прочитать_бд");
    // ... работа с базой данных ...
    спан_завершить(т);

    спан_начать(т, "сформировать_ответ");
    // ... формирование ответа ...
    спан_завершить(т);

    спан_завершить(т);
}

функция главная() -> целое {
    Трейсер т = создать_трейсер();
    обработать_запрос(т);
    трейс_напечатать(т);
    вернуть 0;
}
```

Вывод (отступ — вложенность, длительности посчитаны по монотонным
часам, `монотонное_время_нс()`):

```
  прочитать_бд: 5.096 мс
  сформировать_ответ: 4.949 мс
обработать_запрос: 10.064 мс
```

API:
- `создать_трейсер() -> Трейсер`
- `спан_начать(т, имя)` — отмечает вход в именованный участок кода.
- `спан_завершить(т)` — закрывает **самый последний из открытых**
  спанов (не принимает имя — как закрывающая скобка не указывает, какой
  открывающей она соответствует, порядок сам это определяет).
- `трейс_снимок(т) -> текст` — накопленный текст всех уже ЗАВЕРШЁННЫХ
  спанов, деревом, в порядке закрытия. Спаны, которые ещё не дошли до
  `спан_завершить()`, в снимок не попадают.
- `трейс_напечатать(т)` — печатает снимок через `вывести(...)`.
- `трейс_очистить(т)` — сбрасывает накопленный журнал (например, между
  запросами HTTP-сервера); не трогает ещё открытые спаны.
- `трейс_записать_файл(т, путь) -> результат<верно>` — перезаписывает
  файл целиком накопленным журналом (та же причина, что у
  `метрики_записать_файл` — см. выше).

⚠️ **Честно, узко (v1)**:
- Спаны обязаны закрываться в строго обратном порядке открытия ("(а(б)в)"
  законно, перекрёстное "(а[б)в]" — нет) — `спан_завершить()` не
  проверяет, ЧТО именно закрывается, только "самый последний из
  открытых". Настоящий span_id/родитель (как в OpenTelemetry, для
  произвольного/асинхронного/межпоточного порядка) — не реализован.
- Один `Трейсер` — один линейный синхронный поток выполнения; для
  трассировки нескольких потоков `параллельно` нужен отдельный
  `Трейсер` на поток (`Трейсер`, как `Список`/`Словарь`, не
  потокобезопасен).
- `спан_завершить()` без соответствующего `спан_начать()` не крашит
  программу — в журнал попадает явная строка-предупреждение
  (`⚠️ спан_завершить() без соответствующего спан_начать()`).
- Нет отправки трейсов по сети (распределённая трассировка между
  сервисами, протокол передачи контекста между процессами) — только
  локальный снимок одного процесса, хоть и уже доступный по HTTP (см.
  ниже).

### Метрики и трейсинг по HTTP (examples/веб/наблюдаемость_http.код)

Рабочий пример, объединяющий `сеть.код` + `метрики.код` + `трейсинг.код`:
HTTP-сервер на порту 9090 с двумя эндпоинтами —

- `GET /metrics` — снимок `метрики_снимок(...)` с заголовком
  `Content-Type: text/plain; version=0.0.4; charset=utf-8` (тот самый,
  по которому настоящий Prometheus-сервер узнаёт формат — эндпоинт можно
  напрямую указать в `scrape_configs` без дополнительной настройки).
- `GET /trace` — снимок `трейс_снимок(...)`, дерево уже обработанных
  запросов (сам HTTP-запрос к `/trace` — тоже спан, но попадёт в
  снимок только со СЛЕДУЮЩЕГО обращения — снимок это история уже
  случившегося на момент вызова, см. честные ограничения выше).

```
$ curl http://localhost:9090/metrics
# TYPE http_запросов_всего counter
http_запросов_всего 3
...

$ curl http://localhost:9090/trace
  маршрутизация: 0.009 мс
http_запрос: 2.182 мс
```

⚠️ **Честное, сознательное упрощение**: в отличие от
`examples/веб/http_сервер.код` (каждое подключение — свой поток
`параллельно`), здесь подключения обрабатываются строго
ПОСЛЕДОВАТЕЛЬНО, одно за другим. Причина — прямое следствие уже
указанного выше ограничения: `Метрики`/`Трейсер` не потокобезопасны,
параллельная запись из нескольких потоков в общий экземпляр была бы
гонкой данных. Сделать это безопасным (например, один поток-владелец
метрик и канал для запросов на обновление, тем же приёмом, что уже
применён в `http_сервер.код` для передачи сокета клиента в поток) —
отдельный, более сложный следующий шаг, сознательно не взятый здесь
ради ясности примера.

### Профилировщик (стандартная_библиотека/профилировщик.код)

В отличие от `трейсинг.код` (дерево ОДНОГО прохода выполнения — "что
происходило и в каком порядке"), профилировщик **агрегирует**: сколько
раз был вызван именованный участок кода и сколько суммарно/в среднем
времени он занял за ВЕСЬ прогон программы — вопрос "куда уходит
время", на который дерево одного запроса не отвечает. Ручной API — тот
же дух, что у `начать_замер`/`закончить_замер`, расставляемых вручную
вокруг измеряемого кода (а не автоматическая инструментация каждой
функции компилятором — тот путь требует поддержки в кодогенераторе и
накладных расходов на каждый вызов каждой функции, отдельный, гораздо
больший шаг на будущее).

```
подключить профилировщик;

функция главная() {
    Профилировщик п = создать_профилировщик();

    начать_замер(п, "обработка_запроса");
    // ... код ...
    закончить_замер(п, "обработка_запроса");

    профиль_напечатать(п);
    // обработка_запроса: вызовов=1, всего=1.156 мс, среднее=1.156 мс
}
```

- `создать_профилировщик() -> Профилировщик`
- `начать_замер(п, имя)` — отмечает начало измеряемого участка.
- `закончить_замер(п, имя)` — отмечает конец и прибавляет прошедшее
  время к накопленной статистике этого имени (вызовов, всего, среднее
  считается из вызовов/всего).
- `замер_вызовов(п, имя) -> целое`, `замер_всего_нс(п, имя) -> целое` —
  текущая статистика одного имени напрямую (без отчёта целиком).
- `профиль_отчёт(п) -> текст` / `профиль_напечатать(п)` — сводка по
  всем измеренным участкам, в порядке их ПЕРВОГО измерения (сортировки
  по убыванию времени в языке пока нет — самый затратный участок
  приходится искать глазами по колонке "всего").

⚠️ **Честно, узко (v1)**:
- `начать_замер`/`закончить_замер` для ОДНОГО И ТОГО ЖЕ имени не
  поддерживают вложенность/рекурсию — повторный `начать_замер(п, "а")`
  без `закончить_замер` между вызовами молча перезаписывает время
  начала, первый вызов "теряется" (засчитается только внешний
  интервал). Для вложенных участков с РАЗНЫМИ именами всё работает
  нормально. Если нужна именно вложенность как таковая — для этого
  существует `трейсинг.код` (спаны); разумно использовать оба модуля
  вместе: трейсинг — "что происходило и в каком порядке в этом
  запуске", профилировщик — "куда суммарно ушло время за всю
  программу".
- `закончить_замер()` без предшествующего `начать_замер()` того же
  имени молча ничего не делает (не крашит программу, но и не пишет
  предупреждение, в отличие от `спан_завершить()` в трейсинге — писать
  было бы некуда без отдельного текстового журнала; для диагностики
  таких ошибок используйте `лог.код` рядом).
- Та же причина, что и в `метрики.код`/`трейсинг.код`: `Словарь` не
  поддерживает перечисление ключей, поэтому имена измеряемых участков
  хранятся дважды — в `Словаре` (быстрый доступ) и параллельно в
  `Списке` (порядок перебора при отчёте).
- Не потокобезопасен — как и `Список`/`Словарь`/`Метрики`/`Трейсер`,
  один `Профилировщик` на один поток `параллельно`.

## Графика и UI (стандартная_библиотека/графика.код)

Отдельная, необязательная библиотека поверх SDL2 — требует установленных
`SDL2`/`SDL2_ttf` и флагов `--линковать SDL2 --линковать SDL2_ttf --линковать m`
при компиляции. Подключается через `подключить графика;`.

### Окно, холст, события

```
инициализировать(беззнак32(32));
инициализировать_шрифты();
текст окно = создать_окно("Заголовок", целое32(0), целое32(0), целое32(400), целое32(700), беззнак32(0));
текст рендерер = создать_холст(окно, целое32(-1), беззнак32(2));
```

### Кнопка

Цветной прямоугольник со скруглёнными углами и необязательной, автоматически
центрированной текстовой подписью (пустая строка `""` — кнопка без текста).

```
Кнопка моя_кнопка = Кнопка(целое32(20), целое32(15), целое32(160), целое32(50),
    беззнак8(70), беззнак8(130), беззнак8(230), "Нажми меня");
моя_кнопка.нарисовать(рендерер, шрифт);
если (моя_кнопка.содержит_точку(х_клика, у_клика)) { ... }
```

### Панель (навбар)

Фон на всю ширину плюс список кнопок внутри — то, что нужно для верхнего
или нижнего навбара. Каждая кнопка несёт свои собственные координаты —
панель их не вычисляет автоматически, только рисует фон и все кнопки
по очереди.

```
Список<Кнопка> кнопки = Список<Кнопка>();
кнопки.добавить(кнопка1);
кнопки.добавить(кнопка2);
Панель навбар = Панель(целое32(0), целое32(0), целое32(400), целое32(80),
    беззнак8(40), беззнак8(45), беззнак8(60), кнопки);
навбар.нарисовать(рендерер, шрифт);
целое32 индекс = навбар.кнопка_под_точкой(х_клика, у_клика); // -1, если мимо
```

### Якоря — адаптивное расположение под реальный размер экрана

⚠️ **Честная, найденная реальной проверкой на Android причина**: размер,
переданный в `создать_окно`, лишь ориентировочный — на Android (и iOS) ОС
всегда даёт приложению полноэкранное окно, запрошенный размер игнорируется.
Жёстко зашитая координата вроде `целое32(630)` для нижнего навбара была бы
верна только случайно, если экран устройства окажется точно того же
размера, что был запрошен при разработке — на реальном устройстве экран
почти всегда другой.

```
текст окно = создать_окно("Моё приложение", целое32(0), целое32(0), целое32(400), целое32(700), беззнак32(0));
РазмерЭкрана размер = размер_окна(окно);   // РЕАЛЬНЫЙ размер, не запрошенный

Панель нижний_навбар = Панель(целое32(0), целое32(620), целое32(400), целое32(80), ...);
нижний_навбар.закрепить_снизу(размер, целое32(0));   // ровно у низа экрана
нижний_навбар.растянуть_по_ширине(размер);            // на всю ширину экрана
```

`закрепить_снизу(размер, отступ)` — пересчитывает `у` панели и **сдвигает
все её кнопки на ту же величину**, сохраняя их взаимное расположение (кнопки
хранят свои координаты абсолютно, не относительно панели — без сдвига
кнопок панель переместилась бы, а кнопки внутри остались бы на старом
месте). Симметричный `закрепить_сверху(отступ)` — для отступа под системную
область (вырез камеры, статус-бар).

⚠️ Честное, узкое ограничение: `растянуть_по_ширине` меняет только ширину
фона самой панели — не переставляет и не растягивает кнопки внутри неё
(равномерное распределение N кнопок по новой ширине — отдельная, более
сложная задача, не решена).

### Картинки

Только формат `.bmp` — встроен в сам SDL2, без дополнительных библиотек.
⚠️ Честное, узкое ограничение: PNG/JPG потребовали бы отдельной библиотеки
SDL2_image, которую пришлось бы собирать отдельно. Конвертировать нужные
картинки в `.bmp` можно любым графическим редактором.

```
текст поверхность = загрузить_картинку("иконка.bmp");
текст текстура = создать_текстуру(рендерер, поверхность);
нарисовать_картинку_текстурой(рендерер, текстура, целое32(20), целое32(160), целое32(64), целое32(64));
```

### Поле ввода — `ПолеВвода`

Фон со скруглёнными углами (тот же вид, что и у `Кнопка`), поверх
которого рисуется введённый текст и мигающий текстовый курсор. Само поле
не подписывается на события самостоятельно — программа сама решает,
когда вызывать `добавить_текст`/`удалить_символ`, реагируя на события
`ввод_текста`/`нажатие_клавиши` в своём собственном цикле:

```
ПолеВвода поле = ПолеВвода(целое32(20), целое32(20), целое32(300), целое32(40),
    беззнак8(255), беззнак8(255), беззнак8(255), "", да);

// внутри цикла обработки событий:
если (тип_события == целое32(771)) {  // ввод_текста
    текст кусок = прочитать_текст_по_смещению(буфер_события, целое32(12));
    поле.добавить_текст(кусок);
}
если (тип_события == целое32(768)) {  // нажатие_клавиши
    целое32 код = прочитать_целое32(буфер_события, целое32(20));
    если (код == целое32(8)) {  // backspace
        поле.удалить_символ();
    }
}

поле.нарисовать(рендерер, шрифт, кадр);  // "кадр" — счётчик кадров, для мигания курсора
```

`удалить_символ()` корректно удаляет ровно один символ, а не байт —
важно для кириллицы (2 байта на символ в UTF-8): встроенная функция
`байт_текста(текст, индекс)` и вспомогательная `удалить_последний_символ`
находят правильную границу символа перед обрезкой строки.

## Детерминированность

Для встроенных (embedded) сценариев и станков с ЧПУ, для которых
задуман язык в перспективе, повторяемость результата запуска в запуск —
не абстрактное пожелание, а требование: одна и та же программа с одними
и теми же входными данными обязана дать БИТ-В-БИТ одинаковый результат
каждый раз. Ниже — то, что уже проверено и честно гарантировано, и то,
что сознательно оставлено на будущее.

### ✅ Арифметика `дробное` (f32/f64) — строгая IEEE754, без FMA и без fast-math

Кодогенератор не выставляет никаких fast-math флагов на
`fadd`/`fsub`/`fmul`/`fdiv` (`build_float_add` и соседние в
`src/codegen.rs` используют значения по умолчанию у inkwell/LLVM — то
есть строгую, не ослабленную IEEE754 семантику: никакого допущения на
перегруппировку (`reassoc`), на слияние умножения со сложением в одну
FMA-инструкцию (`contract`) или другие вольности). Объектный код
собирается с `inkwell::OptimizationLevel::None` (`src/codegen.rs`,
`create_target_machine`) — единственный существующий в компиляторе
режим, никакого отдельного "оптимизированного" пути сборки, который
мог бы случайно дать другой результат, не существует вовсе.

Проверено вживую и на уровне сгенерированного машинного кода, не
только "на словах":
- Один и тот же `.код`-файл с `a * b + c` (классический FMA-чувствительный
  паттерн) и с накоплением суммы в цикле на миллион итераций — запущен
  5 раз подряд, результат бит-в-бит одинаков каждый раз.
- Дизассемблирование скомпилированного бинарника (`objdump -d`)
  подтверждает: `a * b + c` даёт РАЗДЕЛЬНЫЕ `vmulsd` и `vaddsd` —
  компилятор НЕ слил их в одну `vfmadd`-инструкцию (которая дала бы
  другое промежуточное округление). Инструкций `fma`/`vfmadd` в
  скомпилированной программе нет вовсе.
- `дробное` по умолчанию — `f64` (двойная точность), `дробное32`/
  `дробное64` — явные варианты; на x86-64 используются SSE2-регистры
  (`vmulsd`/`vaddsd`), а не 80-битная x87-арифметика с её известной
  проблемой двойного округления — отдельный, самостоятельный источник
  недетерминированности в некоторых старых компиляторах, здесь
  структурно отсутствующий.

Честно: это гарантия ОДНОЙ программы на ОДНОЙ и той же машине/
архитектуре между запусками — не гарантия побитового совпадения
результата МЕЖДУ разными процессорными архитектурами или разными ОС
(это отдельный, гораздо более широкий вопрос воспроизводимости между
платформами, не рассматривался в этом заходе).

### ✅ Порядок элементов `Словаря` — см. раздел [Словарь\<Ключ, Значение\>](#словарьключ-значение) выше

Коротко: `Словарь` — не хеш-таблица, а два параллельных массива с
линейным поиском, без хеширования и какой-либо случайности — порядок
элементов всегда равен порядку вставки и одинаков от запуска к
запуску. Подробности и честная оговорка (в языке пока нет способа
наблюдать этот порядок — нет `для каждого`/`.ключи()` по словарю) — в
разделе про `Словарь` выше.

### Многопоточность (`параллельно`)

✅ **Исправлен настоящий баг компилятора, найденный именно при
исследовании этой темы**: `параллельно` безусловно (даже БЕЗ флага
`-g`) вызывал `get_current_debug_location()`/`set_current_debug_location()`
на LLVM-билдере — без включённой отладочной информации это "прилипало"
заглушечной (пустой) debug-локацией ко ВСЕМ последующим инструкциям
программы, что при определённых условиях (два отдельных блока
`параллельно`, каждый с конкатенацией текста) приводило к настоящему
`SIGSEGV` **самого компилятора** на этапе эмиссии машинного кода
(`SelectionDAGISel`). Исправлено: debug-локация теперь сохраняется и
восстанавливается только тогда, когда отладочная информация
действительно включена. Подробности и то, как было найдено и
проверено (включая дизассемблирование и backtrace через `gdb`) — в
ИСТОРИЯ_РАЗРАБОТКИ.md.

⚠️ **Порядок побочных эффектов между потоками НЕ детерминирован — и не
может быть иначе без отдельного, гораздо более крупного планировщика**:
`параллельно` запускает настоящий поток ОС (`pthread_create`), и
относительный порядок, в котором выполняются/печатают/завершаются
НЕСКОЛЬКО одновременно запущенных потоков, зависит от планировщика
операционной системы — он не контролируется языком и меняется от
запуска к запуску. Проверено вживую: программа с двумя `параллельно`
блоками, каждый печатает 5 строк — при повторном запуске одного и того
же скомпилированного бинарника порядок чередования строк между двумя
потоками менялся от прогона к прогону (иногда один поток полностью
обгонял другой, иногда строки чередовались). Это не баг — это честное,
фундаментальное свойство использования настоящих потоков ОС без
собственного детерминированного планировщика (отдельная, значительно
более крупная задача, сознательно вынесенная за рамки этого захода).

✅ **При этом канал `канал<T>` (один отправитель → один получатель,
ровно то использование, что и документировано выше) передаёт ЗНАЧЕНИЕ
детерминированно** — проверено вживую: поток считает сумму 100 000
чисел в цикле и отправляет её в канал, главный поток её получает —
результат бит-в-бит одинаков при 5 повторных запусках. Это ожидаемо:
внутри `отправить`/`получить` — честная пара mutex+condition variable,
гонки по значению здесь нет, недетерминирован только ОТНОСИТЕЛЬНЫЙ
порядок побочных эффектов между независимыми потоками (пример выше), а
не содержимое того, что передаётся через канал.

**Как получить детерминированное поведение уже сегодня, имеющимися
средствами**: если нужен предсказуемый порядок между несколькими
потоками — используйте `дождаться_поток(номер)`/`дождаться_все_потоки()`
для явной синхронизации стадий (поток B не начинает читать то, что
посчитал поток A, пока A не дождались), и `канал<T>` для передачи
результата без гонки по данным. Не давайте нескольким потокам писать в
один и тот же `Список`/`Словарь`/`Метрики`/`Трейсер`/`Профилировщик`
одновременно — они не потокобезопасны (см. соответствующие разделы) —
заводите отдельный экземпляр на поток, как и рекомендовано в каждом из
них.

### ✅ `параллельно детерминировано { ... }` — опциональный детерминированный планировщик ("эстафета")

Начиная с этой версии, у `параллельно` есть опциональный модификатор —
`параллельно детерминировано { ... }`. Он не меняет поведение ОБЫЧНОГО
`параллельно` (оно по-прежнему честные, неупорядоченные потоки ОС, см.
выше) — это отдельный, явно запрашиваемый режим для случаев, когда
нужен ПРЕДСКАЗУЕМЫЙ, воспроизводимый порядок чередования между
несколькими потоками, без переписывания логики под `канал<T>`/
`дождаться_поток`.

**Идея** ("эстафета", она же баtton): все потоки, запущенные с
`детерминировано` в пределах одной "партии" (см. ниже), по очереди,
строго по кругу, передают друг другу право выполняться — как эстафетную
палочку. Каждый поток выполняет свой код ТОЛЬКО пока палочка у него, и
обязан отдать её следующему на ближайшей "точке передачи" (yield-point).
Реальной параллельности между `детерминировано`-потоками поэтому НЕТ —
в каждый момент физически работает ровно один из них (это сознательный
компромисс honest v1: простой, проверяемый протокол ценой
производительности, а не попытка повторить настоящий параллелизм с
детерминированным результатом — такая задача несравнимо труднее и не
ставилась).

**Пример** (ровно `test_детерм_планировщик.код` из `tests/`):
```
функция главная() {
    параллельно детерминировано {
        целое i = 0;
        пока (i < 5) {
            вывести("А" + целое_в_текст(i));
            i = i + 1;
        }
    }
    параллельно детерминировано {
        целое i = 0;
        пока (i < 5) {
            вывести("Б" + целое_в_текст(i));
            i = i + 1;
        }
    }
    дождаться_все_потоки();
}
```
Вывод этой программы **бит-в-бит одинаков при ЛЮБОМ числе повторных
запусков** (проверено — см. ниже): `А0 Б0 А1 Б1 А2 Б2 А3 Б3 А4 Б4`.
Без `детерминировано` порядок строк между `А*`/`Б*` был бы случайным
(см. предыдущий раздел).

**Точки передачи (yield-points) — честно ограниченный, узкий список
v1**: палочка передаётся следующему участнику ТОЛЬКО в эти моменты:
- в начале КАЖДОЙ итерации цикла `пока` (перед телом цикла);
- сразу после каждого вызова `вывести(...)`;
- сразу после `канал.отправить(...)` и `канал.получить()`.

⚠️ **`для каждого` НЕ является точкой передачи в этой версии** — цикл
`для каждого` внутри `детерминировано`-блока выполнится целиком без
передачи палочки между итерациями (детерминированный ПОРЯДОК ВНУТРИ
одного такого потока от этого не нарушается — просто другие
`детерминировано`-потоки не получат слово, пока этот `для каждого` не
закончится полностью). Если нужна передача хода на каждой итерации
коллекции — перепишите цикл через `пока` с ручным счётчиком.

**"Партия" (батч) — те же правила, что уже были у обычного
`дождаться_все_потоки()`**: все `детерминировано`-потоки, запущенные
между двумя соседними вызовами `дождаться_все_потоки()` (или от начала
функции до первого такого вызова), образуют одну партию и участвуют в
одной общей эстафете; `дождаться_все_потоки()` ждёт (`pthread_join`)
всех и обнуляет счётчики для следующей партии — следующая партия, даже
если она в том же `главная()`, начинает новую, независимую эстафету.
Максимум — 256 `детерминировано`-потоков на партию (тот же лимит, что
и у обычных потоков через `дождаться_поток`).

✅ **Главный поток не участвует в эстафете** — он просто вызывает
`дождаться_все_потоки()` и ждёт снаружи, как и для обычных потоков.

✅ **Обычный (не `детерминировано`) `параллельно` можно свободно
запускать в той же партии рядом с `детерминировано`-потоками** — он не
участвует в эстафете, не блокирует её и не блокируется ею (его
собственный порядок, как и раньше, недетерминирован).

**Как проверялось** (живым запуском, не умозрительно — см. подробности,
включая оба найденных и исправленных дедлока/гонки, в
ИСТОРИЯ_РАЗРАБОТКИ.md):
- 4 разных сценария (два потока одинаковой длины; три потока РАЗНОЙ
  длины, включая досрочный выход из эстафеты; соло-поток (N=1) сам по
  себе; смешанная партия — соло-батч, затем обычный `параллельно` рядом
  с двумя `детерминировано`-потоками) — **каждый прогонялся минимум
  30–300 раз подряд, результат бит-в-бит одинаков во ВСЕХ прогонах, ни
  одного зависания**.
- Отдельный, намеренно минимальный тест (2 потока, по 2 оператора
  `вывести` без цикла, обычный `параллельно` в той же партии) —
  **300/300 чистых запусков** и **8/8 чистых запусков под
  `valgrind --leak-check=full`** (0 ошибок, 0 утечек в каждом) после
  финального исправления.
- `opt -passes=verify` — пройден на сгенерированном `.ll` всех
  тестовых сценариев, и с `-g`, и без.

**Честно о найденных и исправленных по дороге багах** (три подряд,
каждый найден исключительно живым тестированием, не умозрительно —
подробный, технический разбор каждого — в ИСТОРИЯ_РАЗРАБОТКИ.md):
1. Счётчик эстафеты не сбрасывался между партиями — вторая партия
   зависала навсегда.
2. Запись родителя в общий флаг активности потока делалась без мьютекса
   — редкая (~1 из 5 запусков) гонка видимости памяти приводила к
   зависанию.
3. Даже после (2) быстрый поток мог полностью отработать и покинуть
   эстафету ДО того, как родитель успевал зарегистрировать следующего
   участника партии — не зависание, а молчаливая потеря самого
   чередования (один поток печатал всё подряд, затем другой). Исправлено
   добавлением барьера регистрации всей партии внутри входа в эстафету.

Все три исправления объединены общим принципом: родитель и
новосозданные потоки выполняются по-настоящему параллельно друг с
другом, и ЛЮБОЕ состояние, которое читает больше одного потока, должно
и писаться, и читаться под одним и тем же мьютексом — "обычно работает
на x86" не равно "формально гарантировано", а редкие гонки по
определению не находятся одним прогоном.

## Известные ограничения

Список ниже — то, что **пока не работает или работает не полностью**,
на момент написания этого документа:

- ⚠️ `параллельно детерминировано { ... }` (детерминированный планировщик,
  "эстафета", см. раздел [Детерминированность](#детерминированность)
  выше) — честные v1-ограничения: нет НАСТОЯЩЕЙ параллельности между
  `детерминировано`-потоками одной партии (строго по очереди, один
  физически работает в каждый момент); точки передачи хода — только
  начало итерации `пока`, `вывести(...)`, `канал.отправить/получить` —
  `для каждого` НЕ является точкой передачи; статический подсчёт размера
  партии (нужен для барьера регистрации, см. там же) работает только
  для `параллельно детерминировано`-операторов, лежащих НЕПОСРЕДСТВЕННО
  друг за другом в одном блоке (не внутри `если`/цикла) — иначе
  действует честный, менее надёжный запасной вариант без барьера;
  максимум 256 потоков на партию; главный поток в эстафете не участвует.
- ✅ `результат<Список<T>>` и `результат<Словарь<К,З>>` — раньше цепочечный
  вызов метода прямо на поле `.значение` результата (`р.значение.метод(...)`)
  падал с ошибкой кодогенерации ("не является структурой — у неё нет
  полей"), а объявление такой переменной через вывод типа падало с
  ошибкой "нельзя объявить через вывод типа". Обе проблемы исправлены:
  `ДополнительнаяИнформация::Результат` теперь хранит LLVM-тип элемента/
  ключа/значения вложенного контейнера, что даёт кодогенератору
  отдельный путь диспетчеризации для `р.значение.метод(...)`, а для
  объявлений через вывод типа добавлен отдельный, узко ограниченный путь,
  не затрагивающий исходный принципиальный запрет на вывод типа для
  голого `Список<T>`/`Словарь<К,З>`. Подтверждено тестами, в т.ч. со
  структурными элементами (`результат<Список<Точка>>`) и мутирующими
  методами (`.добавить`). `Массив<Список<T>>` отдельно этим исправлением
  не тестировался.
- ✅ "для каждого" по коллекции, выраженной как цепочка доступа к полю
  (`для каждого х в к.элементы { ... }` — поле структуры-Список, или
  `для каждого х в р.значение { ... }` — `.значение` результата
  `результат<Список<T>>`) — раньше падало с ошибкой "индексация
  поддержана пока только для простых переменных", потому что внутренняя
  кодогенерация цикла принимала коллекцию только как простую переменную-
  идентификатор. Исправлено: добавлен метод, распознающий оба случая
  (поле структуры — по уже существующей карте `списочные_поля_структур`,
  и `.значение` результата — по уже существующей `ДополнительнаяИнформация::
  Результат` из исправления `результат<Список<T>>` выше) — та же логика,
  что уже применяется для `объект.поле.метод(...)`, просто переиспользована
  для получения указателя на список вместо диспетчеризации вызова.
  Подтверждено тестами, в т.ч. с элементами-структурами. Обходной путь
  (промежуточная переменная) по-прежнему работает, но больше не нужен.
- ✅ Индексация (`[...]`, включая "для каждого") настоящего фиксированного
  массива (`целое[N]`), когда он — поле СТРУКТУРЫ, а не простая локальная
  переменная (`д.числа[0]`, `для каждого х в д.числа`) — раньше падала с
  ошибкой "индексация поддержана пока только для простых переменных",
  как для ЧТЕНИЯ, так и для ЗАПИСИ (`д.числа[1] = 99;`). Исправлено:
  добавлена карта `массивные_поля_структур` (точное зеркало уже
  существующей `списочные_поля_структур`, только для `РешённыйТип::Массив`,
  без промежуточного `build_load` — фиксированный массив, в отличие от
  `Список<T>`, встроен прямо в память структуры, а не лежит за отдельным
  heap-указателем), и оба соответствующих внутренних пути (`получить_
  массив_из_выражения` для чтения, `получить_массив_из_места` для
  записи) расширены случаем "поле структуры" — тем же паттерном
  `build_struct_gep`, что уже использовался для Список/Словарь-полей.
  Заодно, при тестировании этого исправления, найден и устранён смежный
  ПАРСЕРНЫЙ пробел: объявление ЛОКАЛЬНОЙ переменной — фиксированного
  массива ПОЛЬЗОВАТЕЛЬСКОГО (структурного) типа (`Точка[2] точки = ...;`)
  — падало с ошибкой парсера, хотя то же самое объявление внутри ПОЛЯ
  структуры уже работало (`разобрать_тип` уже умел строить `Тип::Массив`
  для пользовательских типов) — диспетчер операторов просто никогда не
  пробовал этот путь для "Идентификатор [ ... ]" на старте оператора,
  путая его с индексацией переменной. Добавлена симметричная проверка
  (`похоже_на_объявление_массива_пользовательского_типа`, по образцу уже
  существующей проверки для generic-объявлений) с тем же приёмом отката
  позиции парсера. Подтверждено тестами: чтение и запись поля-массива
  (примитивные элементы), "для каждого" по полю-массиву, и объявление
  локального массива пользовательского типа.
- ✅ Фиксированные массивы ЭЛЕМЕНТОВ-СТРУКТУР (`Точка[2]`) — раньше не
  работали вообще ни в каком контексте (не через поле структуры, не как
  локальная переменная): ни индексация (`точки[0].х`), ни "для каждого"
  по такому массиву не распознавали элемент как структуру — индексация
  падала с "доступ к полю поддержан пока только для простых переменных",
  а переменная цикла "для каждого" регистрировалась без метаданных о
  структуре (`ДополнительнаяИнформация::Нет` безусловно, для любого типа
  элемента) — обращение к полю переменной цикла падало с "не является
  структурой — у неё нет полей". Исправлено: `ДополнительнаяИнформация::
  Массив` теперь хранит `имя_структуры_элемента` (тот же принцип, что
  уже был у `Список.имя_структуры_элемента`), вычисляемое на всех трёх
  местах, где эта структура создаётся; `получить_массив_из_выражения`/
  `...из_места` и `массивные_поля_структур` прокидывают его дальше;
  `точки[0].х` работает через новую ветку `Выражение::ДоступПоИндексу` в
  `получить_структуру_из_выражения`; "для каждого" регистрирует
  переменную цикла как `ДополнительнаяИнформация::Структура`, когда
  элемент — структура. ⚠️ **Тот же класс use-after-free, что уже был
  найден и исправлен для `Список<Структура>.получить()`**, был здесь
  СРАЗУ учтён (не как отдельная находка, а как часть этого же
  исправления, по аналогии): и при чтении по индексу
  (`сгенерировать_доступ_по_индексу`), и в переменной цикла "для
  каждого" элемент-структура теперь `retain`-ится (тот же принцип
  "утечка предпочтительнее краха", что и у Список — retain без
  соответствующего release, как и у Список.получить()). Подтверждено
  тестами и `valgrind` (0 ошибок, "definitely lost: 0 bytes"). Осталось
  честно НЕ исправлено — уже существовавшее, не новое ограничение:
  запись в поле элемента массива через индекс (`точки[0].х = 99;`) по-прежнему
  не поддержана (то же явное сообщение об ошибке, что было и раньше).
  **UPD: это ограничение снято** — см. следующий пункт.
- ✅ Запись в поле элемента массива структур через индекс
  (`точки[0].х = 99;`) — предыдущее ограничение выше. Исправлено:
  `получить_структуру_из_места` (сторона ЗАПИСИ) получила новую ветку
  `МестоЗаписи::Индекс { .. }` — точное зеркало уже работавшей на ЧТЕНИЕ
  ветки `Выражение::ДоступПоИндексу` в `получить_структуру_из_выражения`,
  только через `получить_массив_из_места` вместо `..._из_выражения`.
  Единственное содержательное отличие от чтения: `retain` (`self.
  захватить(...)`) здесь не нужен — полученный указатель на структуру
  используется сразу же, чтобы записать в его поле (`build_struct_gep`),
  а не сохраняется как новая владеющая ссылка. Работает в цикле
  (`точки[i].х = точки[i].х + 1000;`), любой индекс, любая глубина
  вложенности массива (через уже существующую рекурсию `получить_
  массив_из_места`). Подтверждено тестами и `valgrind`
  ("ERROR SUMMARY: 0 errors" — есть ожидаемая утечка в 96 байт при
  выходе из `главная()`, та же, что и раньше для массивов структур:
  локальный `Точка[N]` не освобождается при выходе из области видимости
  — известное, отдельное, не новое ограничение ARC для фиксированных
  массивов структур, не относящееся к записи через индекс как таковой).
- ✅ Раньше текст под ARC не покрывал результат, переданный напрямую в
  вызов функции без промежуточной переменной (`вывести(целое_в_текст(42));`)
  — теперь исправлено широко: `вывести(...)`, обычные и квалифицированные
  (`модуль.функция(...)`) вызовы функций, вызовы МЕТОДОВ (в т.ч.
  динамические вызовы через контракт), и `длина`, `содержит`, `найти`,
  `подстрока`. ✅ Отдельно устранено для `Список<текст>.добавить(...)`:
  раньше список для текстовых элементов хранил СЫРОЙ указатель как есть
  — если аргумент был заимствованным (литерал, существующая переменная),
  а не свежим буфером, `Список<текст>.освободить()` не мог его
  освободить безопасно (не отличить литерал от malloc — краш или
  двойное освобождение). Решение: `добавить(...)` теперь ВСЕГДА
  сохраняет самостоятельно владеемую копию — `strdup()` заимствованного
  значения (когда оно не является гарантированно свежим буфером) или
  прямая передача владения (когда является) — тот же принцип, что уже
  применяется для структурных элементов (`захватить`/retain), просто
  ролью "увеличить счётчик" здесь играет "сделать независимую копию" (у
  текста нет счётчика ссылок). После этого `Список<текст>.освободить()`
  безопасно освобождает каждый элемент.
- ✅ То же самое перенесено на `Словарь<Ключ, Значение>.положить(...)`: ключ и/или
  значение типа `текст` теперь тоже всегда независимая, самостоятельно
  владеемая копия (`strdup()` заимствованного значения). Ключ копируется
  НЕ сразу, а непосредственно перед сохранением НОВОГО ключа (после
  поиска существующего) — иначе при ОБНОВЛЕНИИ уже существующего ключа
  (значение переписывается, ключ — нет) свежая копия ключа немедленно
  терялась бы, утечка на каждое такое обновление; честно найдено и
  устранено ДО поставки, при проектировании этого исправления. Заодно
  устранена ОТДЕЛЬНАЯ, независимая от текста-под-ARC утечка: раньше
  ОБНОВЛЕНИЕ значения по уже существующему ключу просто затирало старое
  значение новым, без освобождения — при текстовом значении это была
  тихая утечка на каждый повторный `положить(...)` с тем же ключом
  (например, в цикле) — теперь старое текстовое значение освобождается
  перед перезаписью. После этих изменений `Словарь<Ключ, Значение>.освободить()`
  безопасно освобождает каждый текстовый ключ/значение (раньше это было
  сознательно не сделано — Словарь не мог отличить свежий буфер от
  литерала).
- ✅ **Исправлен настоящий use-after-free между потоками** (не просто
  утечка, как для Список/Словарь выше — это оказалось СЕРЬЁЗНЕЕ):
  `канал<текст>.отправить(значение)` копировал только 8 байт битового
  представления указателя, без какого-либо копирования содержимого. Это
  означало, что отправленный текст физически оставался ТЕМ ЖЕ буфером,
  на который продолжает ссылаться локальная переменная отправляющего
  потока (`текст сообщение = "привет" + " из потока"; канал.отправить(сообщение);`)
  — а эта переменная освобождается как обычно при выходе из области
  видимости потока, СОВЕРШЕННО НЕ ЗНАЯ, что её значение было отправлено
  куда-то ещё. Получатель в другом потоке читает уже освобождённую
  память — гонка данных, а не детерминированная утечка. Найдено сначала
  РАССУЖДЕНИЕМ (до всякого запуска — сам факт отсутствия копирования при
  пересечении границы потоков это гарантирует), затем ЭМПИРИЧЕСКИ
  подтверждено специально написанным тестом
  (`тест_канал_текст.код`) — под valgrind воспроизводились многократные
  "Invalid read" в `printf`/`strlen` главного потока на памяти, которую
  `free()`-нул именно поток-отправитель. Исправлено: `отправить(...)`
  теперь ВСЕГДА (безусловно, не только для "заимствованных" значений)
  делает независимую копию (`strdup()`) перед записью в канал — в
  отличие от `Список`/`Словарь`, где "свежее" (заведомо только что
  порождённое) значение можно передать во владение без копии, для
  канала это небезопасно ДАЖЕ для свежего значения, потому что оно всё
  равно может быть привязано к переменной, живущей в исходном потоке.
  Для этого у `ДополнительнаяИнформация::Канал` появился статический
  признак "элемент — именно текст" (аналог `ключ`/`ключ_типа` у
  Список/Словарь), которого раньше не было — opaque-указатели LLVM не
  позволяют отличить текстовый указатель от любого другого на уровне
  самого LLVM-типа. Проверено под valgrind — краш исчез (10 повторных
  запусков подряд, ноль "Invalid read"/"Invalid free"). ⚠️ Честно
  остающиеся, уже НЕ краши, а обычные утечки (сознательно принятый
  компромисс "утечка лучше краха", тот же принцип, что и у
  `Список<T>.получить()`/`Словарь<Ключ, Значение>.получить()`, результат которых
  тоже не отслеживается как владеющее значение):
  - ✅ **Оба честно отложенных пункта из предыдущей версии этого списка
    (см. историю) теперь тоже устранены**:
    - Текст, полученный через `канал<текст>.получить()`, теперь
      распознаётся как владеющее значение: раз `отправить(...)` (см.
      выше) ВСЕГДА кладёт в канал независимую strdup-копию, получатель
      — единственный, кто на неё ссылается, и `является_текст_
      порождающим` теперь признаёт `канал<текст>.получить()`
      текст-порождающим вызовом — той же веткой, что уже применяется к
      функциям и методам, — освобождается автоматически при сохранении
      в переменную и выходе из области видимости, как и любой другой
      свежий текст.
    - У `канал<T>` появился метод `.освободить()` — раньше не
      существовало вообще никакого способа освободить память самого
      объекта канала (`создать_канал()`, ~272 байта — мьютекс +
      условная переменная + флаг + слот). Метод вызывает
      `pthread_mutex_destroy`/`pthread_cond_destroy` (обратная операция
      `_init`, освобождает не только память, но и ОС-ресурсы мьютекса/
      условной переменной) перед `free()` самого буфера — та же
      "парность", что у `pthread_create`/`pthread_join`.
    - ⚠️ Честно осталось: если в канале лежит неполученный текст на
      момент `.освободить()` (отправлено, но ни разу не вызвано
      `получить()`), эта конкретная копия текста всё равно утечёт —
      контракт "за временем жизни следит программист", тот же, что и у
      `Список`/`Словарь`
- ✅ **Отдельно, скорее всего самый часто задеваемый случай из всех**:
  результат ПОЛЬЗОВАТЕЛЬСКОЙ функции, возвращающей `текст`
  (`функция сгенерировать(...) -> текст { ... }`), раньше вообще не
  распознавался как владеющее значение — утекал и при `текст с =
  сгенерировать(x);`, и при прямой передаче (`вывести(сгенерировать(x));`).
  Теперь распознаётся и освобождается корректно, включая переприсваивание
  внутри цикла (`с = сгенерировать(i);` на каждой итерации), а с недавних
  пор — и для МЕТОДОВ структур, возвращающих текст (`объект.метод()`),
  когда статический тип `объект` известен как конкретная структура.
  ⚠️ **Важная честная поправка**: ПЕРВАЯ версия этого распознавания (и
  для функций, и для методов) полагалась только на ОБЪЯВЛЕННЫЙ тип
  возврата (`-> текст`) — этого оказалось НЕДОСТАТОЧНО и приводило к
  настоящему краху (`free(): invalid pointer` / "double free or
  corruption"): функция или метод вида
  `функция сказать() -> текст { вернуть "Мяу"; }` возвращает СТРОКОВЫЙ
  ЛИТЕРАЛ (статическая константа в `.rodata`, никогда не malloc'нутая),
  но кодогенератор, поверив декларации типа, пытался освободить (`free`)
  этот указатель при каждом использовании результата — разрушая
  аллокатор. Обнаружено воспроизведённым крахом на одном из регрессионных
  тестов (структура с методом, буквально возвращающим текстовый литерал).
  Исправлено переходом на анализ ТЕЛА функции/метода: теперь функция или
  метод считаются "гарантированно возвращающими новый буфер" только если
  КАЖДЫЙ достижимый `вернуть <выражение>;` в её теле сам является
  заведомо текст-порождающим выражением в узком смысле (конкатенация
  `+` или вызов одной из конкретных built-in функций, которые сами
  гарантированно делают malloc) — декларации типа возврата теперь
  недостаточно. Это осторожный анализ: он может НЕ распознать функцию,
  которая на самом деле всегда возвращает новый буфер, но делает это
  через вызов ДРУГОЙ пользовательской функции (`вернуть
  другая_функция();`) — такой случай честно не покрывается (упущенная
  утечка предпочтительнее краха). ✅ **Устранено и это, последнее в этой
  категории**: метод, возвращающий текст, вызванный через ДИНАМИЧЕСКУЮ
  диспетчеризацию контракта (`объект.метод()`, где `объект` статически
  имеет тип контракта, а не конкретной структуры), теперь тоже
  распознаётся как текст-порождающий и освобождается. Кодогенератор
  по-прежнему не знает во время компиляции, КАКАЯ именно структура
  выполнит вызов в рантайме — но это и не требуется: список ВСЕХ
  структур, реализующих данный контракт, известен статически (все их
  vtable уже сгенерированы к этому моменту компиляции). Если КАЖДАЯ из
  них уже признана "гарантированно возвращающей новый буфер" для этого
  метода (по анализу тела — см. выше), то и результат динамического
  вызова гарантированно свежий буфер, НЕЗАВИСИМО от того, какая
  конкретно реализация исполнится — освобождать безопасно. Если хотя бы
  ОДНА реализация не проходит проверку (например, у неё метод
  возвращает литерал), вызов честно НЕ считается текст-порождающим, как
  и раньше (утечка вместо риска краха). Проверено: `тест_контракт_
  список_освободить.код` (уже существующий тест с `.напечатать()` через
  контракт) — утечка результата этого вызова (33 байта, 3 блока)
  полностью исчезла; `тест_контракт_возврат.код` — та же утечка (11
  байт × 3) тоже исчезла. Полная регрессия под valgrind и `привет.код`
  — без единого нового падения или утечки (побайтово идентично, не
  считая PID в заголовках valgrind)
- ✅ `Список<Контракт>` раньше содержал настоящий use-after-free (не

  выше). ✅ **Устранена и честная утечка, появившаяся взамен**: элементы
  `Список<Контракт>` теперь не только корректно захватываются
  (`захватить`), но и корректно освобождаются — как через `.удалить(...)`
  (удаляемый элемент), так и через `.освободить()` (все оставшиеся
  элементы перед освобождением самого буфера). Решение — тот же принцип
  рантайм-сравнения vtable, что уже применялся для освобождения
  локальных переменных контрактного типа при выходе из области
  видимости (см. чуть ниже): конкретная структура за толстым указателем
  элемента неизвестна на этапе компиляции, поэтому она определяется в
  рантайме сравнением адреса vtable элемента с адресами всех известных
  vtable этого контракта. Код освобождения вынесен в отдельный
  переиспользуемый метод (принимающий уже загруженное значение толстого
  указателя, а не адрес ячейки — списку не нужна отдельная alloca для
  каждого элемента). Проверено под valgrind (`тест_контракт_список_

  самих объектов-элементов исчезла полностью; на момент этого
  исправления оставалась ещё одна, ОТДЕЛЬНАЯ утечка (33 байта, 3 блока)

  падения или утечки (побайтово

- ✅ **Исправлена утечка локальных переменных КОНТРАКТНОГО типа**
  (например `Печатаемый а = создать_питомца(1);`) — раньше такая
  переменная, хранящая структуру, обёрнутую в "толстый указатель"
  {данные, vtable}, никогда не освобождалась (ARC release) при выходе
  из области видимости, в отличие от локальной переменной КОНКРЕТНОГО

  ARC-кадров регистрировал для освобождения только `РешённыйТип::

  проверке под valgrind (`тест_контракт_возврат.код`) во время работы

  КОНКРЕТНАЯ структура за конкретным значением неизвестна во время
  компиляции (в этом и смысл динамической диспетчеризации), она
  определяется в рантайме — сравнением адреса vtable из толстого
  указателя с адресами ВСЕХ известных vtable этого контракта (список
  кандидатов известен статически). ⚠️ Попутно, при добавлении этого
  освобождения, был обнаружен и исправлен ДОПОЛНИТЕЛЬНЫЙ риск двойного
  освобождения: копирование существующей переменной в контрактную

  всё равно утечёт
- ✅ **Устранены оба честных, узких ограничения `дождаться_поток(номер)`**:
  раньше его нужно было вызывать СТРОГО до `дождаться_все_потоки()` для
  той же партии потоков (иначе поток был бы `pthread_join`-нут дважды —
  неопределённое поведение POSIX), и нельзя было вызвать дважды с одним
  и тем же номером (та же причина). Решение — после успешного join
  ячейка массива для этого номера обнуляется (маркер "уже
  присоединён"), а перед ЛЮБЫМ join (в обеих функциях) сначала
  проверяется, не `NULL` ли уже ячейка — если да, join просто
  пропускается как безопасный no-op вместо передачи `NULL` в
  `pthread_join`. Порядок вызовов `дождаться_поток(...)` и
  `дождаться_все_потоки()` друг относительно друга, а также повторные
  вызовы `дождаться_поток(...)` с одним и тем же номером, теперь
  безопасны в любом сочетании. Проверено под valgrind (5 повторных
  запусков) на двух новых тестах: `дождаться_поток(...)` дважды с одним
  номером, и `дождаться_поток(...)` уже после `дождаться_все_потоки()`
  для той же партии — ноль ошибок, ноль утечек в обоих случаях. ⚠️
  Осталось не проверяемое во время выполнения, более узкое ограничение:
  номер не должен ссылаться на поток из УЖЕ СБРОШЕННОЙ (после
  `дождаться_все_потоки()`) партии, чья ячейка могла быть перезаписана
  новым потоком следующей партии
- ✅ **Исправлен настоящий use-after-free** (не просто утечка):

  контрактного типа (`Кот а = Кот(1); а = Кот(2);` или `Печатаемый а =
  кот1; Печатаемый б = кот2; а = б;` — в отличие от НОВОГО объявления
  переменной, которое уже было исправлено раньше в этой сессии) вообще
  не трогало ARC: старое значение не освобождалось (честная утечка сама
  по себе — единственная ссылка на объект пропадала бесследно), а если
  новое значение было КОПИЕЙ другой существующей переменной — не
  захватывалось (retain), из-за чего обе переменные впоследствии
  освобождали ОДИН И ТОТ ЖЕ объект при выходе из области видимости.
  Найдено не багрепортом, а целенаправленной проверкой ("а если
  попробовать вот так?") в рамках общего наведения языка на
  стабильность — воспроизведено под valgrind как "Invalid read"/"Invalid
  write" на уже освобождённой памяти (настоящий краш, не абстрактный
  риск). Исправлено для ОБОИХ типов (структура и контракт) — порядок
  действий: сначала вычислить новое значение, затем ЗАХВАТИТЬ его (если
  оно оказалось копией существующей переменной) и только ПОТОМ
  ОТПУСТИТЬ старое — такой порядок (retain-до-release) заодно делает
  безопасным даже самоприсваивание (`а = а;`: счётчик временно
  увеличивается на 1, тут же уменьшается обратно тем же вызовом — риска
  обратиться к уже освобождённой памяти нет, даже если старое и новое
  значение физически совпадают). Для контрактных переменных
  переиспользован уже существующий механизм рантайм-сравнения vtable
  (`отпустить_контрактное_значение`). Проверено под valgrind (отдельные
  тесты на переприсваивание структуры, самоприсваивание структуры и
  переприсваивание контрактной переменной другой контрактной

  идентично, не считая PID в заголовках valgrind)
